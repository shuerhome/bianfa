关于「多种形态」，我的判断

上面三个形态用的是同一个组件、同一份状态，切换时没有新建任何窗口 —— 这正是它们便宜的原因。真正贵的是需要新窗口类或新 OS 集成的那些。

形态成本建议
桌面散落 / 停靠侧栏 / 便笺墙同一窗口换布局，靠 container queryv1 就做
折叠胶囊同一窗口改高度，动效章已有v1 就做
置顶三档两平台各一行 APIv1 就做，零风险
贴桌面（沉到图标之下）要写 native，未文档化，随系统更新可能失效D1–D3 生死判定，做不出就降级
侧边停靠 AppBar（真正抢占屏幕空间）Windows 有 SHAppBarMessage，macOS 没有等价物推后，双平台天然不对等
自由画布拖拽/缩放/层叠/多选/视口虚拟化/坐标同步4–6 周，推到 v1.2
独立 AI 窗第五个要管理的窗口类型不做（第 13 章已否决）

一个容易被忽略的代价：每多一个真正的窗口类型，就多一整套「位置记忆 / 多显示器 / DPI 变化 / 关闭语义 / 快捷键作用域 / 崩溃恢复」。这不是 UI 工作量，是状态机工作量，而且它只在用户换了显示器、改了缩放、或者程序崩溃之后才暴露 —— 那时候修的成本是现在的十倍。

还有一条产品层面的：便笺用户的心智是「双击就写」。形态给太多，第一屏就要做选择题，会稀释掉这个品类唯一的优势。建议默认只给「桌面散落」，其余藏在托盘菜单里让愿意折腾的人自己找。

注：这是浏览器里的模拟。真实产品里每张便笺是独立的操作系统窗口（各自的 webview），不是一个页面里的 div —— 所以才有 20 窗口内存要压在 350MB 以内、skipTaskbar 要开、窗口 chrome 要按平台分叉这些约束。

# R2：三个桶、三把 key、CORS

## 0. 一页结论

| 桶 | 可见性 | 法域 / 位置 | 谁写 | 谁读 | 生命周期 / 保护 |
|---|---|---|---|---|---|
| `bianfa-releases` | **公开读**，只通过自定义域 `cdn.<REPLACE_ME:domain>` | 无法域限制；位置提示 `weur`（可选） | GitHub Actions release 工作流（token `bianfa-releases-ci`） | 全世界（安装包）、更新 Worker（binding，读 `latest.json`） | 版本目录按约定不可变；7 天清理未完成的分片上传 |
| `bianfa-backups` | 私有 | **法域 `eu`**（个人数据） | postgres 容器内的 pgBackRest（token `bianfa-backups-rw`） | 同上 + 每月 restore 演练的 CI | **不能开 bucket lock**（原因见 §4.2）；不可变副本放 `bianfa-backups-vault`（§4.3，Phase 2） |
| `bianfa-attachments` | 私有 | **法域 `eu`** | 桌面端凭 API 签发的 presigned PUT 直传（token `bianfa-attachments-rw` 只在 api/worker 进程） | 桌面端凭 presigned GET | CORS 允许 Tauri 的三个 webview origin；GC 由 pg-boss mark-and-sweep（C10），不用 R2 lifecycle 过期 |

三把 key 对应 S5：`releases`、`backups`、`attachments`。R2 的 token 权限只有 4 档（§6），**没有「只写」这一档**，所以 S5/第 9 章写的「只写」在 R2 上不可达；最小可达权限是「Object Read & Write，且只限定到该一个桶」。这一点已在 §6 逐桶说明为什么可以接受。

**R2 没有对象版本控制。** cloudflare-docs 里没有任何 R2 versioning 页面，bucket-locks 页也未提及（[待核实]：仅能证明「文档中不存在」，不能证明功能不存在）。因此 S5 的「对象锁定/版本控制」只能靠 **bucket lock**（已核实 r2/buckets/bucket-locks.mdx：阻止**删除与覆盖**，可按前缀、按天数/日期/无限期，一个桶最多 1,000 条规则，有规则时桶不能被清空；**与 lifecycle 冲突时 lock 优先**——lifecycle 30 天删、lock 90 天留，对象 90 天后才会被删）。而 bucket lock 与 pgBackRest 的工作方式冲突（§4.2），所以「锁」不能直接开在 pgBackRest 的仓库桶上。

## 1. 前置

1. **账号级 token 而不是用户级**：R2 的 API token 分「Account API token」（跟随账号、只有 Super Administrator 能建、手动吊销前一直有效）与「User API token」（跟随个人用户，用户被移出账号即失效）。三把生产 key 一律建 **Account API token**，避免人员变动时静默失效（已核实 r2/api/tokens.mdx）。
2. **法域（jurisdiction）与位置提示（location hint）不能同时给**：`wrangler r2 bucket create` 源码（r2/bucket.ts）显式互斥："Provide either a jurisdiction or location hint - not both."
   - 法域 = 硬约束（数据只存该法域内），可选 `eu` / `us` / `fedramp`（fedramp 仅 Enterprise），**建桶后不可更改**。**法域桶的 S3 端点不同**：`https://<REPLACE_ME:account-id>.eu.r2.cloudflarestorage.com`；Worker 绑定与所有 wrangler 命令都要带 `jurisdiction = "eu"` / `-J eu`（已核实 r2/reference/data-location.mdx）。
   - 位置提示 = 尽力而为，取值 `wnam` `enam` `weur` `eeur` `apac` `oc`（同页已核实）。
   - 第 10 章要求的「R2 桶设 EU 位置提示 `[待核实]`」到此核实完毕：应该用的是**法域 `eu`**，不是位置提示。
   - 与 VPS 所在地的关系：第 10 章说 VPS 开在德国/立陶宛，第 9 章 8.12 说优先新加坡，两章冲突，本文件不裁定；R2 出网免费，跨洲推备份只影响吞吐不影响费用。
3. 本文件命令基于 **wrangler 4.129.0**（npm `latest`，engines `node>=22.0.0`），在 `infra/cloudflare/update-worker/` 里 `npm ci && npx wrangler …` 即可复用同一份依赖。首次需 `npx wrangler login`（OAuth，不产生长期 token）。wrangler 4 的 `r2 bucket lifecycle/lock/cors/domain` 子命令在改配置前都会交互确认，CI 里加 `-y`（`--force`）。

## 2. 创建

> **法域是可选项**（2026-09-06 补）：EU 法域是为「个人数据只存欧盟」的合规姿态，功能上普通桶完全一样。首台机器实际用控制台建成了
> 「自动」位置的普通桶，直接沿用；`.env.prod` 的 `R2_BACKUPS_JURISDICTION` 留空即可（填 `eu` 才走 `.eu.` 端点）。下面 `-J eu` /
> `--jurisdiction eu` 的命令是选了法域时才需要的。什么时候值得改成法域桶：有欧盟用户且要在隐私政策里承诺数据驻留时——那时建新桶、
> 改这个变量、重做一次全量即可。

```sh
# 公开分发桶：无法域限制（自定义域 + 法域桶的组合文档未提及 [待核实]，安装包也不含个人数据，没必要冒这个险）
npx wrangler r2 bucket create bianfa-releases --location weur

# 两个含个人数据的桶：法域 eu
npx wrangler r2 bucket create bianfa-backups     --jurisdiction eu
npx wrangler r2 bucket create bianfa-attachments --jurisdiction eu

# Phase 2（§4.3）：备份的不可变副本
npx wrangler r2 bucket create bianfa-backups-vault --jurisdiction eu
```

`--location` / `--jurisdiction` / `--storage-class` 为 r2/bucket.ts 已核实的 flag。

## 3. `bianfa-releases`

### 3.1 公开读只走自定义域

```sh
npx wrangler r2 bucket domain add bianfa-releases \
  --domain cdn.<REPLACE_ME:domain> \
  --zone-id <REPLACE_ME:zone-id> \
  --min-tls 1.2
```

- flag 名（`--domain` `--zone-id` `--min-tls`，取值 `1.0|1.1|1.2|1.3`，不写默认 **1.0**——所以要显式给 1.2）来自 wrangler 源码 `r2/domain.ts`；该命令会自动在 zone 里创建 DNS 记录，不要手工加 CNAME。域必须是**同一 Cloudflare 账号下的 zone**（已核实 r2/buckets/public-buckets.mdx）。
- **不要开启 `r2.dev` 公共 URL**：官方文档明确它有速率限制、仅供开发；也不要用 CNAME 指向 r2.dev（"unsupported access path"）。
- 走自定义域才能套 WAF custom rules、Cache Rules、Bot Management。

### 3.2 对象布局（与第 9 章 8.9、更新 Worker 的 `MANIFEST_PREFIX=releases` 对齐）

```
bianfa-releases/
  releases/stable/latest.json                                   ← Worker 读；Cache-Control: no-store
  releases/stable/1.4.2/bianfa_1.4.2_x64-setup.exe              ← NSIS per-user（第 3 章 2.4.4）
  releases/stable/1.4.2/bianfa_1.4.2_x64-setup.exe.sig          ← 可选：minisign 签名原文（latest.json 里已内嵌）
  releases/stable/1.4.2/bianfa_1.4.2_universal.dmg              ← 官网下载
  releases/stable/1.4.2/bianfa_1.4.2_universal.app.tar.gz       ← updater 用
  releases/stable/1.4.2/bianfa_1.4.2_universal.app.tar.gz.sig
  releases/beta/…                                               ← 同结构
  releases/stable/flags.json                                    ← 第 17 章 #28 的 feature flag（与 updater 同一哈希分桶）
```

- **版本目录一旦上传视为不可变**；改错了就发下一个 patch 版本，不覆盖。
- `latest.json` 的平台 key：Tauri 先查 `{os}-{arch}-{installer}` 再查 `{os}-{arch}`（已核实 updater.rs）。**macOS universal 包必须同时登记 `darwin-aarch64` 与 `darwin-x86_64`**（url 与 signature 相同）：`{{arch}}` 取的是正在运行的那个 slice，updater 没有 "universal" 兜底 key。Windows 用 `windows-x86_64`；等第 17 章 #56 的 ARM 构建上线再加 `windows-aarch64`。
- Cloudflare 默认按扩展名缓存：`EXE` `DMG` `GZ` `ZIP` 在默认列表里（所以 `.app.tar.gz` 会被缓存），`.json` 明确不缓存、`.sig` 不在列表（已核实 cache/concepts/default-cache-behavior.mdx）。Free/Pro/Business 单文件最大可缓存 **512 MB**（已核实）—— 100 MB 安装包没问题。想让 `.sig` 也被缓存，加一条 Cache Rule：`hostname eq "cdn.<REPLACE_ME:domain>" and starts_with(http.request.uri.path, "/releases/")` → Eligible for cache，Edge TTL「respect origin」。

### 3.3 CI 上传（GitHub Actions release 工作流）

```sh
export AWS_ACCESS_KEY_ID="$R2_RELEASES_ACCESS_KEY_ID"          # GitHub Environment "release" 的 secret
export AWS_SECRET_ACCESS_KEY="$R2_RELEASES_SECRET_ACCESS_KEY"
export AWS_DEFAULT_REGION=auto
# 必须：R2 的 S3 兼容表把 x-amz-sdk-checksum-algorithm / x-amz-checksum-algorithm 标为「未实现」，CRC32 等只支持 COMPOSITE 类型
# （已核实 r2/api/s3/api.mdx）。2025 年起的 AWS CLI/SDK 默认给每个 PUT 加 CRC 校验头，不关掉会报错或静默失败。
export AWS_REQUEST_CHECKSUM_CALCULATION=when_required
export AWS_RESPONSE_CHECKSUM_VALIDATION=when_required
EP="https://<REPLACE_ME:account-id>.r2.cloudflarestorage.com"   # releases 桶无法域 → 用默认端点

aws s3 cp dist/ "s3://bianfa-releases/releases/${CHANNEL}/${VERSION}/" --recursive --endpoint-url "$EP" \
  --cache-control "public, max-age=31536000, immutable"
aws s3 cp latest.json "s3://bianfa-releases/releases/${CHANNEL}/latest.json" --endpoint-url "$EP" \
  --content-type application/json --cache-control "no-store"
```

工作流文件本身（`.github/workflows/desktop.yml`）由 CI 模块产出；这里对它的硬要求：所有 `uses:` **pin 到 commit SHA**；只在 `push: tags: ['v*']` 上触发，**不用 `pull_request_target`**；R2 secrets 只放 GitHub **Environment** `release`（required reviewers），不放仓库级 secrets——fork PR 拿不到 Environment secrets。

**发版顺序（写进 RUNBOOK，顺序不能换）**

1. `npx wrangler kv key put --namespace-id <id> --remote ROLLOUT_PERCENT 5`（首个灰度批次；第 17 章 #29 的健康闸门以后接在这里）。
2. 上传二进制到 `releases/<channel>/<version>/`，逐个 `curl -I https://cdn.<REPLACE_ME:domain>/releases/<channel>/<version>/<file>` 确认 200。
3. `jq -e '.version and (.platforms|to_entries|all(.value.url and .value.signature))' latest.json` 校验 —— Worker 对坏清单只会静默 204 并记 error 日志，CI 这一步是发现坏清单的主要手段。
4. 最后上传 `latest.json`。
5. 观察 `npx wrangler tail bianfa-update` 与 Sentry，按 5 → 25 → 100 放量。
6. 出事：`KILL_SWITCH=1`（≤ 60 s 生效，只保护**未升级**用户）；已升级用户只能前滚 hotfix（第 17 章 #30）。

### 3.4 Lifecycle

```sh
# 清理 7 天未完成的分片上传（否则占存储且看不见）
```

## 4. `bianfa-backups`（以及为什么要有 `bianfa-backups-vault`）

### 4.1 pgBackRest 侧（第 9 章 8.7 的补充）

```ini
repo1-type=s3
repo1-s3-endpoint=<REPLACE_ME:account-id>.eu.r2.cloudflarestorage.com   # 法域桶 → eu 端点（已核实端点格式）
repo1-s3-bucket=bianfa-backups
repo1-s3-region=auto
repo1-s3-uri-style=path
repo1-s3-key=${R2_BACKUPS_ACCESS_KEY_ID}                                # 由 CI 从 GitHub Environment secrets 渲染进 VPS 的
repo1-s3-key-secret=${R2_BACKUPS_SECRET_ACCESS_KEY}                     #   /srv/bianfa/pg/pgbackrest.conf，root:root 600，不进 git
repo1-cipher-type=aes-256-cbc
repo1-cipher-pass=…                                                     # 见下面的说明
```

关于 `repo1-cipher-pass`：第 9 章写「不存 VPS」。**这在字面上不成立** —— `archive_command` 由 Postgres 进程在 VPS 上每分钟执行，pgBackRest 必须能拿到口令才能加密 WAL。正确表述是：**口令的备份副本存在 VPS 之外**（密码管理器 + 离线介质，第 17 章 #74 的巴士因子文档），VPS 上那一份与 `.env.prod` 同等保护。丢了 VPS 上的副本不可怕，丢了 VPS 之外的副本 = 备份全部不可解密。（这是对裁定文字的技术性修正，见本文件 notes；需要裁定方确认。）

对象在桶里的位置（prod 的 `pgbackrest.conf` 显式 `repo1-path=/pgbackrest`；pgBackRest 内建默认其实是 `/var/lib/pgbackrest` 而非 `/`，restore-drill.yml 必须与 prod 一致）：

```
backup/bianfa/backup.info(.copy)            ← 每次备份都被重写
backup/bianfa/20260907-030000F/…            ← 备份集，写入后不再改
backup/bianfa/20260907-030000F.manifest(.copy)
backup/bianfa/backup.history/2026/…
archive/bianfa/archive.info(.copy)          ← 会被重写
archive/bianfa/18-1/0000000100000000/…      ← WAL 段，写入后不再改
```

### 4.2 为什么**不能**在这个桶上开 bucket lock

bucket lock 的已核实语义是「阻止对象被删除**和被覆盖**」。pgBackRest 的正常运行需要两者：

- `expire`（每次 backup 后自动跑）要**删除**超出 `repo1-retention-full=4` 的旧备份集与旧 WAL；
- `backup.info` / `archive.info` 每次备份都被**覆盖**；
- 上一次备份中途失败时，下一次 backup 会先删除或（resume 模式下）覆盖残留的备份目录。

任何一条被 lock 拒绝，pgBackRest 都会报错退出 —— 结果是**备份链静默中断**，正好是第 9 章 8.7 说的「archive 阶段不报错、restore 时才暴露」的反面：这里是 backup 阶段就一直报错，但没人看日志就等于没报。所以：**`bianfa-backups` 不加 lock 规则**，只加 lifecycle 清理分片上传：

```sh
npx wrangler r2 bucket lifecycle add bianfa-backups abort-stale-mpu "" --abort-multipart-days 2 -J eu
```

Phase 1（M2 上线前）对「VPS 被攻破后备份被删」的兜底就是第 9 章已有的第二层：Hostinger 每周整机快照（VPS 上没有 Hostinger 的 API key）。

### 4.3 Phase 2：不可变副本桶 `bianfa-backups-vault`

在有付费用户之前（建议 M3）补上真正的「对象锁定」，做法是把锁开在一个**VPS 完全拿不到凭据**的副本桶上：

```sh
npx wrangler r2 bucket create bianfa-backups-vault --jurisdiction eu
# 全桶 35 天不可删不可覆盖（位置参数：bucket name prefix；"" = 全部前缀；flag 来自 r2/lock.ts，三种 retention 互斥）
npx wrangler r2 bucket lock add bianfa-backups-vault keep-35d "" --retention-days 35 -J eu
# 45 天后自动过期。已核实：lock 与 lifecycle 冲突时 lock 优先，所以 45 > 35 只是为了让两条规则语义清晰，写 35 也不会提前删
npx wrangler r2 bucket lifecycle add bianfa-backups-vault expire-45d "" --expire-days 45 -J eu
```

每天一次 GitHub Actions（与第 9 章 8.7 每月 restore 演练同一套 runner 环境）用 **只读** token 读 `bianfa-backups`、用 **读写** token 写 vault：

```sh
# rclone：--immutable = 目标已存在且内容不同就报错而不是覆盖；不带 --delete，永不删除
rclone copy backups:bianfa-backups/backup/bianfa  vault:bianfa-backups-vault/backup/bianfa  --immutable \
  --exclude "backup.info*" --exclude "backup.history/**"
rclone copy backups:bianfa-backups/archive/bianfa vault:bianfa-backups-vault/archive/bianfa --immutable \
  --exclude "archive.info*"
# 会变化的元数据文件按日期快照，永不覆盖（体积只有 KB 级）
D=$(date -u +%F)
rclone copy backups:bianfa-backups/backup/bianfa/backup.info        "vault:bianfa-backups-vault/meta/$D/backup/bianfa/"
rclone copy backups:bianfa-backups/backup/bianfa/backup.info.copy   "vault:bianfa-backups-vault/meta/$D/backup/bianfa/"
rclone copy backups:bianfa-backups/archive/bianfa/archive.info      "vault:bianfa-backups-vault/meta/$D/archive/bianfa/"
rclone copy backups:bianfa-backups/archive/bianfa/archive.info.copy "vault:bianfa-backups-vault/meta/$D/archive/bianfa/"
```

- rclone 的两个 R2 remote 都要设 `endpoint = https://<REPLACE_ME:account-id>.eu.r2.cloudflarestorage.com`（法域桶端点），`provider = Cloudflare`。
- 保留期算术：pgBackRest 保 4 个周全量 ≈ 28 天，vault 锁 35 天 ≥ 28 天，所以 vault 里永远有一份完整、不可篡改的近 4 周备份；45 天 lifecycle 在锁到期后清掉过期数据。
- 从 vault 恢复：把 `backup/`、`archive/` 与最新 `meta/<D>/` 拉到 restore runner 的本地目录，`repo1-type=posix repo1-path=/restore/repo` 跑 `pgbackrest restore`。每月演练**单双月交替**从主仓与 vault 恢复，否则 vault 是没验证过的备份。
- 此方案的 RPO 在「VPS 被攻破且主仓被删」这条路径上是 24 小时（每日同步），常规故障路径仍是第 9 章的 60 秒。
- 代价：多一把 CI-only token（§6 第 4 行）、多一个桶的存储费（备份体积级别，可忽略）。

## 5. `bianfa-attachments`

### 5.1 访问模型（第 1 章 S1 的 R2 侧）

- 桶私有，**没有自定义域、没有 r2.dev**。所有访问都是 API 用 `bianfa-attachments-rw` 签出的 presigned URL：PUT 15 分钟、GET 5 分钟；签发前必须过 `authorize(user, note_id, 'viewer')`。
- presigned PUT 把 `content-length` 与 `content-type` 一并签进去（客户端在 `/v1/attachments/presign` 时已声明 size/mime），否则上限只能靠事后 HEAD 校验。
- presigned URL 的 host 是 **S3 端点** `https://<REPLACE_ME:account-id>.eu.r2.cloudflarestorage.com/bianfa-attachments/...`，**不在你的 zone 上**，所以 WAF/rate limit 管不到它（限流靠 presign 接口本身），Tauri 的 CSP 也必须把这个 host 加进 `connect-src` 与 `img-src`（第 10 章 9.2 的 CSP 目前没有，需回改）。
- 对象 key 的命名（S1 的 `content_hash` 去重 vs 第 10 章的 UUIDv7 key）是 API 侧决定，本文件不裁定；无论哪种，都不要把 key 当作访问控制。
- E2EE（保险箱）附件由客户端加密后上传，`content_hash` 取密文，不参与去重（S1）。

### 5.2 CORS

Tauri v2 的 webview origin（已核实 `tauri-utils/src/config.rs` 的 `use_https_scheme` 文档注释）：

| 平台 | 生产 origin | 说明 |
|---|---|---|
| Windows（及 Android） | `http://tauri.localhost` | 默认；若 `app.windows[].useHttpsScheme=true` 则为 `https://tauri.localhost`。**发版后不要改这个开关**：会换掉 IndexedDB/localStorage/cookie 的位置 |
| macOS（及 Linux / iOS） | `tauri://localhost` | 固定，不可配置 |
| 开发模式（Vite devUrl） | `http://localhost:1420` 之类 | 只允许出现在开发用桶，**绝不加进生产桶** |

文件 `infra/cloudflare/attachments-cors.json` 用的是 **R2 API 的形状**（`rules[].allowed.{origins,methods,headers}` + `rules[].exposeHeaders` + `rules[].maxAgeSeconds`，类型见 workers-sdk `r2/helpers/bucket.ts` 的 `CORSRule`）。**不要**用 dashboard 文档里 S3 风格的 `AllowedOrigins/AllowedMethods`：wrangler `r2 bucket cors set --file` 检测到 `CORSRules` 或 `AllowedOrigins` 会直接报错拒绝（已核实 r2/cors.ts）。

```json
{
  "rules": [
    {
      "id": "tauri-webview-presigned-put-get",
      "allowed": {
        "origins": ["tauri://localhost", "http://tauri.localhost", "https://tauri.localhost"],
        "methods": ["PUT", "GET", "HEAD"],
        "headers": ["content-type", "content-md5", "x-amz-content-sha256", "x-amz-date"]
      },
      "exposeHeaders": ["ETag"],
      "maxAgeSeconds": 3600
    }
  ]
}
```

```sh
npx wrangler r2 bucket cors set  bianfa-attachments --file infra/cloudflare/attachments-cors.json -J eu
npx wrangler r2 bucket cors list bianfa-attachments -J eu
```

已核实的要点：origin **精确匹配**、格式 `scheme://host[:port]` 不能带路径；presigned URL 从浏览器/webview 发起时**仍然需要** CORS（"you still need to configure CORS when making requests from a browser"）；变更最多 30 秒生效。presigned URL 的签名在 query string 里，浏览器不会发 `x-amz-date` 等头，`headers` 里列出它们只是为 Rust 侧改用 header 签名时留余地。

一个会省事的判断：如果上传由 **Rust 侧 reqwest** 发起（S1 的 BLAKE3 已经在 Rust 里算了，顺手上传是自然选择），**CORS 根本不参与**（CORS 只约束浏览器/webview 内的 fetch/XHR）；`<img src=presignedGET>` 是 no-cors 请求也不受影响。上面的配置是为 WebView 内 `fetch()` 直传这条路径准备的，两条路径都能跑。

### 5.3 Lifecycle

```sh
npx wrangler r2 bucket lifecycle add bianfa-attachments abort-stale-mpu "" --abort-multipart-days 1 -J eu
```

不设对象过期：删除只能由 pg-boss 的 mark-and-sweep（C10：`last_referenced_at + 30d` 反连接）发起，R2 自己过期会删掉仍被引用的图片。

## 6. API token 最小权限矩阵

R2 token 的四档权限（已核实 r2/api/tokens.mdx，逐字）：

| 档 | 官方描述 |
|---|---|
| Admin Read & Write | create, list, and delete buckets, edit bucket configuration, read, write, and list objects |
| Admin Read only | list buckets and view bucket configuration, read and list objects |
| Object Read & Write | read, write, and list objects **in specific buckets** |
| Object Read only | read and list objects **in specific buckets** |

只有 Object 级两档能限定到指定桶；**没有 write-only，也没有「不能删除」的档**。Object 级权限只对 S3 兼容 API 有效（Workers binding 不需要 token）。

| # | token 名（建成 Account API token） | 权限 | 桶 | 持有者 | 存放 | 轮换 | 为什么这是最小 |
|---|---|---|---|---|---|---|---|
| 1 | `bianfa-releases-ci` | Object Read & Write | 仅 `bianfa-releases` | GitHub Actions `release` 工作流 | GitHub **Environment** `release` 的 secrets（required reviewers，第 10 章 9.3.5），名 `R2_RELEASES_ACCESS_KEY_ID` / `R2_RELEASES_SECRET_ACCESS_KEY` | 每 180 天；成员变动立即 | 读权限在公开桶上是零增量；删除权限的风险由「版本目录不可变 + git tag 可重建任意版本 + latest.json 由 KV 兜底」覆盖。第 10 章「GitHub → R2 用 OIDC」：R2 **没有**接受 GitHub OIDC 的联合身份入口 [待核实：本轮未在文档中找到]；可行的替代是 §6.1 的临时凭据代理 |

### 6.1 可选加固：临时凭据代理（把 #1 变成 15 分钟有效）

R2 支持由父 token 派生**临时凭据**（已核实 r2/api/s3/temporary-credentials.mdx）：必填 `bucket` + `parentAccessKeyId`，可限 `permission`（`object-read-only` / `object-read-write` / `admin-read-only` / `admin-read-write`）、`prefixes`、`objects`、`ttlSeconds`；父 token 吊销则全部立即失效。**注意**：按 S3 操作名精确放行的 `actions`（如只给 PutObject 不给 DeleteObject）文档写的是 "currently supported via local signing only. Support in the Temporary Credentials API is coming soon" —— 所以这条加固目前能做到的是「GitHub 里不再有长期 R2 key + 凭据只在 `releases/` 前缀 + 15 分钟」，**做不到「发布凭据无法删除对象」**。做法：一个 ~80 行的 Worker 校验 GitHub Actions 的 OIDC JWT（`iss=https://token.actions.githubusercontent.com`、`repository`、`ref`、`environment`），然后用 Temporary Credentials API 换凭据返回给 CI。M5 之后再做；现在先用 #1。

## 7. 额度与费用（沿用初稿对 r2/pricing.mdx 的核实，本轮未重新抓取）

Free：10 GB-月存储、100 万 Class A（Put/List/Copy…）、1,000 万 Class B（Get/Head…）/月，出网免费，Delete 免费。估算：安装包 100 MB × 2 平台 × 保留 10 个版本 ≈ 2 GB；备份几 GB（zst 压缩）；附件随用户增长，超出 10 GB 后 $0.015/GB-月。更新检查每次 1 个 Class B（Worker 读 latest.json），1 万用户每小时一次 ≈ 720 万/月，仍在免费额度内。

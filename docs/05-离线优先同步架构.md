## 第 4 章　离线优先同步架构与冲突解决

> 本章的唯一验收标准：**用户在任何断网 / 崩溃 / 多设备并发场景下，都不会发现自己写过的字消失了。** 原版 Windows 便笺的差评几乎全部指向这一点（`plum.sqlite` 损坏、账号重登后本地库被云端空库覆盖、多设备编辑后整条便笺被回滚）。以下所有设计围绕这一条展开。
>
> **核实说明（2026-09-04 本轮实测）**：本章所有版本号、体积、下载量均来自 `registry.npmjs.org` / `crates.io` API 与包内文件实测（下载 tarball、`gzip -9` 实测、读 `.d.ts` 与 Rust 源码）。**凡本轮网络受限无法核实的（各家云服务定价、Cloudflare 计费比例、厂商收购传闻），一律显式标注"需自行核实"，不写成确定结论。**

### 4.1 先定性：便笺是怎么丢的

丢失只有三种物理成因，架构必须分别封堵：

| 成因 | 典型触发 | 封堵手段 |
|---|---|---|
| **合并覆盖**：整条记录级 LWW，晚到的旧版本盖掉新内容 | 手机改了标题、电脑离线改了正文，重连后二选一 | 字符级 CRDT（正文）+ 字段级 LWW（元数据），见 4.2 / 4.3.1 |
| **落盘丢失**：内存里有、磁盘上没有就崩了 | 进程被杀、断电、SQLite 无 WAL | 本地 append-only update log + WAL + fsync 策略，见 4.5 |
| **同步逻辑丢失**：客户端把"服务端没有"理解成"应该删除" | 首次登录、换账号、bootstrap 竞态 | bootstrap 只做 union，删除必须携带显式 tombstone，见 4.3.4 |

还有第四种，初稿漏了，而且它在中文产品里是**最容易真实发生**的一种：

| **编码错位**：Rust 侧与 JS 侧对"第 N 个字符"的定义不一致 | 中文正文经 Rust 后台合并后串位、乱码 | 强制 `OffsetKind::Utf16`，见 4.2.4 |

### 4.2 同步范式与库选型

#### 4.2.1 三种范式

| 维度 | 记录级 LWW + 服务端时间戳 | 操作日志 / OT | CRDT |
|---|---|---|---|
| 实现成本（1-3 人） | 1 周 | 6-10 周（变换函数必须自证正确） | 2-3 周（用现成库） |
| 并发编辑同一条便笺 | **丢字**（整条覆盖） | 字符级正确 | 字符级正确 |
| 需要中央服务器排序 | 是 | **是（OT 的硬约束）** | 否，可 P2P / 哑中继 |
| 离线数天后重连 | 大概率丢一整边 | 需服务端保留完整 op 历史 | 天然收敛 |
| 存储放大 | 1× | 1×（可截断） | 1.5-3×（tombstone） |
| E2EE 兼容 | 是 | **否**（服务端要变换 = 要看明文） | **是**（服务端可只当哑中继） |

**结论：正文用 CRDT，元数据用字段级 LWW（HLC 定序）。** OT 排除——它要求服务端在线且能读明文，与 4.6 的 E2EE 分层和"服务端零解析"的成本目标直接冲突。

**结论：Yjs（JS 端）+ yrs（Tauri Rust 端）。** 三条决定性理由：

1. **编辑器绑定是最大的集成成本，而它只有 Yjs 一条成熟路径。** `@tiptap/extension-collaboration` 昨天（2026-09-03）还在发版；`loro-prosemirror` 还是 0.4.4。为 Loro 的性能优势自维护一个 ProseMirror 绑定，对 1-3 人团队是净亏。
2. **`yrs` 让 Tauri 的 Rust 侧在不启动 WebView 的情况下完成合并与落盘**——便笺窗口全关时后台仍能同步，这是"贴在桌面"类产品的刚需。yrs 近期下载量是 loro 的 **2.88 倍**、automerge 的 **5.40 倍**。
3. **体积**：便笺是多窗口应用，62.5 KB gz 纯 JS 与 1.05 MB gz WASM（外加 34 KB glue）在冷启动上差一个数量级，且 WASM 每个 WebView 实例都要重新编译。

Loro 的 shallow snapshot 确实解决了 Yjs 的 tombstone 痛点——**但便笺正文通常 < 2 KB，单文档 tombstone 增长在这个量级不构成问题**（见 4.5.3 的兜底）。若将来做"共享白板 / 长文档"，Loro 才值得重新评估。

**切换成本对冲**：把 CRDT 引擎藏在 `NoteBodyEngine` 抽象之后（`load(bytes) -> Doc` / `apply(update)` / `snapshot() -> bytes` / `to_plain_text()` / `to_markdown()`），并规定**任何时刻都能从任意引擎导出规范 JSON**。切到 Loro 的代价 ≈ 2 人周（重写绑定 + 一次性迁移：读旧快照 → 导出结构 → 写新文档），协议层、表结构、UI 全不动。这是本章唯一"为未来买保险"的地方。

#### 4.2.4 ⚠️ yrs 双端互通的两个真实地雷（初稿完全漏了）

**地雷一：`OffsetKind` 默认值与 Yjs 不一致——对中文产品是致命的。**

实测 `yrs-0.27.4/src/doc.rs`：`Options` 的 `offset_kind` **默认为 `OffsetKind::Bytes`（UTF-8 字节计数）**，而 Yjs 只有 UTF-16 计数。源码里甚至留着这行注释：

```rust
// yrs-0.27.4/src/doc.rs:590
OffsetKind::Utf16 => 0, // 0 for compatibility with Yjs, which doesn't have this option
```

同文件的测试断言了后果：同一字符串 `s.len(OffsetKind::Bytes) == 34` 而 `s.len(OffsetKind::Utf16) == 21`。一个汉字 UTF-8 占 3 字节、UTF-16 占 1 单位——**用默认 Options 在 Rust 侧做任何按索引的文本操作，中文正文都会串位**。修法只有一行，但必须写进项目模板：

```rust
use yrs::{Doc, Options, OffsetKind};

fn new_note_doc(client_id: u64) -> Doc {
    let mut opts = Options::with_client_id(client_id);
    opts.offset_kind = OffsetKind::Utf16;  // 必须显式设置，默认是 Bytes = 与 Yjs 不兼容
    Doc::with_options(opts)
}
```
**CI 必须有一条测试**：Rust 侧对含 emoji 与中文的文档做 `insert(idx, ..)`，JS 侧 `applyUpdate` 后断言字符串完全相等。

**地雷二：特性并非 100% 对等。** y-crdt README 自述目标是"maintain behavior and binary protocol compatibility with Yjs"，但其对照表显示 **YMap weak links 与部分 observer 实现在 yrs 侧未完成**。工程纪律：**Rust 侧只用 `merge_updates_v2` / `diff_updates_v2` / `encode_state_vector` / `apply_update` 这几个已稳定的二进制层能力，一切富文本结构操作留在 JS 侧。**

**顺带一个正面发现（初稿低估了 Rust 侧）**：`yrs 0.27.4` 的 `src/sync/` 目录里已经有 `protocol.rs`（`DefaultProtocol` / `Message` / `SyncMessage` / `MessageReader`）和 `awareness.rs`（`Awareness`）——**完整的 y-sync 协议与 awareness 在 Rust 侧是现成的**。这直接影响 4.7 的"服务端用 Node 还是 Rust"决策：自己用 axum + yrs 写房间，不是从零实现协议，工作量比初稿估的"3 人周"低得多。

### 4.3 同步协议设计

#### 4.3.1 数据分层（本章最重要的一个决策）

**不要把整条便笺塞进 CRDT。** 拆成三层：

| 层 | 内容 | 存储 | 合并策略 |
|---|---|---|---|
| **meta** | 标题、颜色、坐标 x/y/w/h、置顶、分组、排序、删除标记 | Postgres 行 / SQLite 行（明文） | **字段级 LWW，HLC 定序** |
| **body** | 富文本正文 | 不透明 blob（Yjs update v2） | **CRDT，字符级** |
| **blob** | 图片、附件 | 内容寻址对象存储（BLAKE3） | 不可变，只增引用 |

收益：便笺列表 / 搜索 / 权限校验全走明文 SQL，服务端**不加载任何 CRDT 就能渲染列表**；1000 条便笺的工作区首屏只拉 meta，body 按需懒加载。

#### 4.3.2 表结构

```sql
-- ===== 服务端 Postgres =====
create sequence global_lsn;                       -- 全局单调版本，同步的唯一权威顺序

create table notes (
  id            uuid primary key,                 -- 客户端生成 uuidv7
  workspace_id  uuid not null,
  -- 每个 LWW 字段配一个 HLC 串（"物理毫秒-逻辑计数-节点id"，定长零填充，字典序可比）
  title text, title_hlc text,
  color text, color_hlc text,
  geom  jsonb, geom_hlc text,                     -- {x,y,w,h,z} 作为一个原子字段
  pinned bool, pinned_hlc text,
  encryption   text not null default 'server',    -- 'server' | 'e2ee'
  wrapped_dek  bytea,                             -- 仅 e2ee 时非空
  deleted_at   timestamptz,
  purge_after  timestamptz,                       -- deleted_at + 30d
  body_seq     bigint not null default 0,
  lsn          bigint not null
);
create index notes_feed on notes (workspace_id, lsn);

-- 正文：append-only。服务端对个人便笺不做语义解析。
create table note_updates (
  note_id     uuid   not null,
  seq         bigint not null,
  device_id   uuid   not null,
  payload     bytea  not null,                    -- Yjs update v2，或 E2EE 密文
  is_snapshot boolean not null default false,
  is_milestone boolean not null default false,    -- 每日里程碑，压缩时永不删
  lsn         bigint not null,
  created_at  timestamptz not null default now(),
  primary key (note_id, seq)
);
create index nu_feed on note_updates (lsn);

-- 幂等：同一 (device, key) 重放直接返回上次结果
create table client_ops (
  device_id uuid, idempotency_key text,
  lsn bigint, result jsonb, created_at timestamptz default now(),
  primary key (device_id, idempotency_key)
);

create table blobs (
  hash text primary key,                          -- blake3-256 hex
  size_bytes bigint, mime text, storage_key text,
  last_referenced_at timestamptz not null default now()
);

-- ===== 客户端 SQLite（PRAGMA journal_mode=WAL; synchronous=NORMAL; busy_timeout=5000）=====
create table outbox (
  id integer primary key autoincrement,
  kind text not null,                             -- meta|body|blob_ref|delete
  note_id blob not null,
  payload blob not null,
  idem_key text not null unique,                  -- uuidv7，重试时不变
  created_at integer not null,
  attempts integer not null default 0,
  next_retry_at integer not null default 0
);
create table sync_state (k text primary key, v text);   -- last_lsn / bootstrap_done
```

> **对初稿的一处减法**：初稿的 `blobs.refcount int` 是一个跨设备维护的分布式引用计数——1-3 人团队做不对（漏减 = 永久垃圾，多减 = 删掉在用的图）。改为 **mark-and-sweep**：`last_referenced_at`，每晚扫描所有存活 note 的正文提取 `blob://` 引用刷新时间戳，**超过 30 天无人引用**才删对象。慢，但不会误删。

#### 4.3.3 协议

```ts
type Pull   = { t:'pull'; since_lsn:number; limit:number };   // limit 默认 500
type PullOk = { t:'pull_ok'; changes:Change[]; next_lsn:number; has_more:boolean };

type Push   = { t:'push'; ops:Op[] };
type PushOk = { t:'push_ok';
                applied:{ idem_key:string; lsn:number }[];
                rejected:{ idem_key:string; code:'forbidden'|'too_large'|'gone'|'quota' }[] };

// 服务端主动推：只是"有新东西"的信号，客户端自己回来 pull
type Bump   = { t:'bump'; workspace_id:string; lsn:number };
// 仅 E2EE 便笺需要：服务端看不懂密文，只能请客户端代劳压缩
type Compact = { t:'compact_request'; note_id:string; upto_seq:number };
```

**关键不变量**：客户端**只信任 `lsn`，不信任任何时间戳做同步定序**。`last_lsn` 只在 `pull_ok` 全量落盘成功后才推进（同一个 SQLite 事务里写 changes + 写 `sync_state`），杜绝"拉到一半崩溃 → 游标已推进 → 数据永久丢失"。

#### 4.3.4 Bootstrap / 重连 / 退避

- **首次 bootstrap**：`since_lsn = 0` 分页拉全量。**bootstrap 期间禁止执行任何本地删除**——只做 union。本地已有而服务端没有的便笺，一律当作"待上传"塞进 outbox。这一条直接封堵原版便笺"重登后本地被清空"的事故。
- **退避**（full jitter，上限 60 s，网络恢复事件立即重置）：

```ts
const delay = Math.random() * Math.min(60_000, 1000 * 2 ** Math.min(attempt, 6));
```

- **WebSocket 断线**：立刻降级为 30 s 轮询 `pull`，重连成功后取消轮询。

#### 4.3.5 文档粒度：每张便笺一个 Y.Doc

| | 每便笺一个 Doc ✅ | 整 workspace 一个 Doc ❌ |
|---|---|---|
| 内存 | 只加载当前显示的 3-10 个窗口 | 1000 条便笺全量反序列化才能显示列表 |
| 权限 | 共享一条 = 开一个房间，天然隔离 | **共享一条就泄露整个更新流** |
| E2EE | 每便笺一个 DEK，可单条开关保险箱 | 只能整库一把钥匙 |
| 代价 | 列表字段不能进 CRDT → 正是 4.3.1 的 meta 层 | — |

**反方意见（初稿没答）**："一条一个 Doc，打开 10 个便笺窗就是 10 条 WebSocket，还没算列表预览。"——**这个反驳不成立，且我们有实测依据**：`@hocuspocus/provider@4.6.0` 导出 `HocuspocusProviderWebsocket`，多个 `HocuspocusProvider`（每文档一个）共享**同一条 socket**；4.x 新增的 `sessionAwareness` 选项其 `.d.ts` 原文是 "embeds a unique sessionId in the documentName field of every message, **allowing multiple providers with the same document name on a single WebSocket connection**"。

这顺带**解决了初稿只列为风险却没给方案的那一条**（"同一 note 被主列表预览 + 独立便笺窗两个 WebView 同时打开会自己跟自己冲突"）：开 `sessionAwareness: true`，两个 WebView 各持一个 provider、共用一条连接，服务端按 `documentName\0sessionId` 区分，无需在 Rust 侧做单例 Doc 的跨 WebView 广播。**结论维持不变，且实现更简单了。**

#### 4.3.6 附件：两阶段，绝不进 CRDT

1. 客户端算 `blake3(file)` → `POST /blobs/init {hash,size,mime}`；服务端已有该 hash 直接返回 `{exists:true}`（天然去重）。
2. 否则分块上传（1 MB/块，`PUT /blobs/{hash}/chunk/{n}`），断点续传 = 重发缺失块号；`POST /blobs/{hash}/finalize` 校验 hash 后落地。
3. **上传成功后**才向 Y.Doc 插入 `<image src="blob://<hash>">`。
4. **离线时**：文件先复制进本地 `attachments/` 并写 outbox，Y.Doc 里**直接插入 `blob://<hash>`**——hash 本地可算，引用无需等待上传。渲染层查本地缓存命中即显示，未命中且未上传则显示"待上传"占位符。**即使离线，正文里的引用也是最终正确的，事后不需要改文档。**

#### 4.3.7 删除语义

`deleted_at` 软删除 → 回收站（客户端仍持有完整 body）→ `purge_after = deleted_at + 30d` → 服务端每日 GC 删 `note_updates`。**tombstone 行（`notes` 里的 id + deleted_at）永久保留**（一行约 100 B），否则离线 40 天的设备回来会把便笺"复活"。1 万条便笺的墓碑总计约 1 MB，不需要任何优化。

#### 4.3.8 时钟：HLC 与 server lsn 分工

| 用途 | 用什么 |
|---|---|
| 同步游标 / change feed 定序 | **server `lsn`**（客户端时钟不可信） |
| meta 字段级 LWW 胜负 | **HLC**：`hlc = max(physical_now, last_hlc.physical + 1)`，比较序 `(physical, logical, node_id)` |
| 正文合并 | 都不用，CRDT 自己定序 |

**时钟偏移策略（初稿只处理了"快"，漏了"慢"，而"慢"更常见）**：

| 客户端与服务端偏差 | 处理 |
|---|---|
| 客户端**超前** > 5 min | 服务端 clamp 为自身时间，回传 `clock_skew` 告警 |
| 客户端**落后** > 5 min | **服务端在每个响应里回传 `server_time`；客户端把 `hlc.physical` 抬到 `max(local_now, last_server_time)`** —— 这样落后的时钟不会让该设备的编辑在 LWW 里系统性判负 |
| 偏差 > 30 min | UI 明确提示"本机时间不准，可能影响同步"，并给一键校时入口 |

关键点：HLC 的 `max()` 语义本身就允许被外部观测抬升，把 `server_time` 当成一次外部观测即可，不需要 NTP 客户端。这比初稿的"提示用户去改系统时间"可执行得多。

#### 4.3.9 幂等

客户端生成 `note.id`（uuidv7）与每个 op 的 `idem_key`（uuidv7，**重试时不变**）。服务端在同一事务里 `insert into client_ops ... on conflict do nothing`，冲突则返回上次 `result`。

**保留期与初稿不同**：初稿说保留 7 天，同时又在风险里承认"离线超 7 天的设备重放会重复写入"——**这是自相矛盾，等于承认设计有漏洞**。修正为：`client_ops` 保留 **35 天**（覆盖 30 天回收站窗口 + 余量，1 万条/天 × 35 天 ≈ 35 万行，Postgres 毫无压力）；并且**所有写操作在语义上都做成 upsert**（`insert into notes ... on conflict (id) do update ... where excluded.title_hlc > notes.title_hlc`），使幂等表退化为纯优化而非正确性依赖。**正确性不能依赖一个会过期的表。**

#### 4.3.10 冲突的用户可见处理

| 场景 | 处理 | 打扰用户 |
|---|---|---|
| 两端编辑同一条便笺的不同位置 | CRDT 静默合并 | 否 |
| 两端编辑同一段文字 | CRDT 静默合并（字符交错） | 否，但合并后高亮远端新增内容 8 秒 |
| 两端改同一个 meta 字段 | HLC 大者胜 | 否 |
| 一端删除、另一端编辑 | **编辑胜**：若 `body_seq` 在 `deleted_at` 之后仍增长，自动撤销删除 + toast | 是（轻提示） |
| **长度收缩守卫触发**（4.5.2） | 合并照常应用，但顶部黄条 + 【查看合并前版本】【恢复】 | **是（显式，这是产品的信任担保）** |
| 服务端拒绝（配额 / 权限） | op 留在 outbox 并标红，不静默丢弃 | 是 |

**高亮的实现约定（初稿把它留成了 open question，这里定死）**：远端高亮由 Tiptap `Decoration` 实现，触发条件是 `transaction.origin !== localClientId`。**AI 写入必须使用本地 origin**（在第 5 章的 LLM 集成里，AI 结果通过本地 transaction 落笔），否则每次 AI 改写都会触发"远端变更"高亮。这一条要写进两章共用的 origin 约定表。

版本回滚：从 `note_updates` 取目标 `seq` 之前的 update 重放出历史 Doc，**回滚 = 计算 diff 并作为一次新的 CRDT 编辑追加**（绝不删除历史），因此回滚本身也可被撤销。

### 4.4 实时协同

#### 4.4.1 传输选型

**选 WebSocket。** Yjs update 是二进制，SSE 需 base64（+33% 体积）且上行要另开 POST（队头 + HTTP 开销）。SSE + POST 仅作为 WS 被企业防火墙阻断时的**降级信号通道**（只收 `bump`，上行走普通 POST `/push`）。

> ⚠️ 初稿在此表里给出了 Cloudflare Durable Objects 的具体计费规则（"入站 WS 消息按 20:1 折算请求数"、"Hibernation 空闲不计 duration"）。**本轮 `developers.cloudflare.com` 被出口策略拦截，未能核实，故删除具体数字。** 方向性判断（DO + Hibernation 对便笺这类低频长连接场景成本友好）保留，但**在真正决定上 Cloudflare 前必须自行核对当期定价页**。

#### 4.4.2 两条服务端路径（成本关键）

- **个人便笺（≥95% 流量）→ 哑存储**：服务端**不加载 Y.Doc**，只把 `payload` 按 `(note_id, seq)` 追加、分配 `lsn`、向该用户其他设备广播 `bump`。CPU 与内存近乎为零。
- **共享便笺 → Hocuspocus 4.6.0 房间**：`onAuthenticate` 校验短期 JWT，`onLoadDocument` 从 `note_updates` 重放，`onStoreDocument` 落盘。（这四个钩子名已在 `@hocuspocus/server@4.6.0` 的 `.d.ts` 中实测确认，另有 `onChange` / `onConnect` / `onDisconnect` / `onAwarenessUpdate` / `onUpgrade` / `onRequest` / `onConfigure` / `onDestroy`。）

**三处对初稿的修正：**

1. **运行环境**：`@hocuspocus/server@4.6.0` 的 `package.json` 写着 `"engines": {"node": ">=22"}`——**不是初稿写的 Node 20+**。部署镜像按 Node 22 LTS 准备。
2. **可移植性被夸大了**：初稿称"跑在 crossws 上，未来迁 Cloudflare Workers 不用改代码"。实测其 `dist` 中**只引用了 `crossws/adapters/node` 一个适配器**。crossws 本身支持多运行时，但 Hocuspocus 发布产物**绑定了 Node 适配器**——迁 Workers 需要自己换适配器甚至改造，绝不是零成本。**不要把这条写进技术规划的假设里。**
3. **Token 不要放 query 参数**：`@hocuspocus/provider` 的配置项 `token` 类型实测是 `string | (() => string) | (() => Promise<string>) | null` —— **支持异步函数**。用它在每次（重）连接时现取一个 60 s TTL 的 JWT，token 走 Hocuspocus 的 auth 消息帧而非 URL，避免短 token 落进 Nginx access log 和浏览器历史。

#### 4.4.3 Awareness、快照与压缩

- **Awareness**：`y-protocols` 1.0.7，字段 `{userId, name, avatarUrl, color, cursor}`，**只在房间内广播，绝不持久化**。
- **落盘节流**：Hocuspocus 的 `debounce` / `maxDebounce` **默认就是 2000 / 10000 ms**（实测 dist 中 `debounce: 2e3, maxDebounce: 1e4`）——初稿把默认值写成了"我们的配置选择"，实际上无需配置。真正**需要显式改**的是 `unloadImmediately`，其默认值为 `true`，意味着最后一个连接断开时立即卸载文档、**不等 `onStoreDocument` 的 debounce**；对"永不丢数据"目标应设为 `false`，并在进程退出前调用 flush 接口把挂起的 `onStoreDocument` 全部落盘。
- **压缩（这里初稿的判断需要修正）**：初稿说"个人便笺服务端不解析，只能下发 `compact_request` 让客户端算"，并把"用户长期不上线就压不动"列为存储黑洞风险。**但 `yrs 0.27.4` 的 `src/alt.rs` 提供了 `merge_updates_v1/v2(updates) -> Vec<u8>` 与 `diff_updates_v1/v2(update, state_vector)`，纯二进制层操作、不构造 Doc、不理解业务语义。** 所以：
  - **L0（服务端加密）便笺**：服务端可用 `merge_updates_v2` 直接把 N 行 update 合并成 1 行快照，**无需客户端参与，也不需要"加载 Y.Doc"**。存储黑洞风险消失。
  - **L1（E2EE）便笺**：payload 是密文，服务端确实无能为力，才走 `compact_request`。对这类便笺设**硬上限：单 note 5000 行或 50 MB**，超限拒绝新 push 并在客户端提示"请打开此便笺以完成整理"。
- **里程碑**：每天保留一个 `is_milestone=true` 的快照，保留 90 天；压缩只删中间过程。

#### 4.4.4 v1 要不要做实时协同？

**做一半：v1 做"实时同步"，不做"实时协同 UI"。**

- **v1 交付**：WS 通道 + 共享便笺 update 秒级双向广播。两人同时编辑，文字正确合并并在 1-2 秒内互相看到。
- **v1 不做**：光标 / 选区 / 头像 awareness、"某某正在输入"。
- **v1.1 再开**：包已现成——`@tiptap/extension-collaboration-caret` **3.31.2（2026-09-03）**，与主扩展同步发版。协议不变，装包 + 配 `user` 字段即可。

**反方论证（认真走一遍）**："协同光标是共享功能的门面，没有它用户根本感知不到'这是协作产品'，砍掉等于砍掉需求 2 的说服力。"

**反驳成立吗？部分成立，但不足以改变结论。** 理由：(a) 便笺的真实使用形态是"一人写一句、异步接力"，不是 Google Docs 式的同屏共写，光标的边际价值远低于文档场景；(b) 光标的成本不在装包，而在边界处理——同一用户多窗口、光标落在已被远端删除的文本上、离线重连后陈旧 presence 的清理，这些对 1-3 人团队是真实的两周；(c) **它是纯增量的**，v1 不做不产生任何架构债或数据迁移。**结论维持：v1 不做。** 但把 `awareness` 通道在 v1 就打通并跑通"在线人数"这一个最简字段——它成本近零，却能让共享便笺"看起来是活的"，把反方担心的门面问题以 1% 的成本解决 90%。

### 4.5 数据安全网

#### 4.5.1 本地

1. SQLite `journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=5000`；**每次编辑立刻 append 一条 update 行**（不是等 debounce），编辑器内 debounce 只影响网络推送，不影响落盘。
2. 每 50 条 update 或每 5 分钟或窗口失焦时，写一次本地快照行。
3. 本地保留最近 **7 天完整 update 历史 + 30 天每日快照**，与服务端策略解耦——即使账号被封、服务器宕机，本地仍可完整重建。
4. **崩溃自愈**：启动时若发现上次未干净退出，跑 `PRAGMA integrity_check`；失败则切换到 `bianfa.sqlite.bak`（每日轮换的完整副本）并把损坏库改名保留，**绝不静默重建空库**。
5. **数据库路径必须落在 `%LOCALAPPDATA%`（Win）/ `~/Library/Application Support`（macOS）**，并在首次启动检测路径是否位于 OneDrive / iCloud / Dropbox 同步目录——云盘同步 WAL 文件是 SQLite 损坏的头号来源，检测到就阻断并提示迁移。

#### 4.5.2 长度收缩守卫（针对"莫名丢失"的直接探针）

```ts
const before = doc.getXmlFragment('body').toString();
Y.applyUpdateV2(doc, remoteUpdate, 'remote');
const after = doc.getXmlFragment('body').toString();

if (before.length > 200 && after.length < before.length * 0.7) {
  // 不阻止合并——CRDT 必须收敛；只留证据 + 给用户一键恢复
  await db.saveForensicSnapshot(noteId, {
    before, remoteUpdate, at: Date.now(), reason: 'shrink_guard'
  });
  ui.showConflictBanner(noteId, { before, after });
  telemetry.count('shrink_guard_tripped');
}
```

（`Y.applyUpdateV2` / `Y.encodeStateAsUpdateV2` / `Y.mergeUpdatesV2` / `Y.diffUpdateV2` / `doc.getXmlFragment` 均已在 `yjs@13.6.32` 产物中确认存在。）

**取证快照必须有配额**，否则它自己会变成存储问题：单便笺最多保留 3 份，全局最多 200 份或 100 MB，LRU 淘汰。

这个探针的价值不只是救数据，更是**把"莫名丢失"变成可观测指标**——上线后 `shrink_guard_tripped` 的值就是我们与原版便笺的差距量表。

#### 4.5.3 Yjs tombstone 的兜底（把初稿的风险变成方案）

Yjs 的 `gc` 只合并 tombstone、不真正丢弃历史。对 < 2 KB 的便笺这不构成问题，但"当草稿本反复大段删改数年"的极端用户会让快照膨胀。**兜底方案定死**：当单便笺快照 > 256 KB 时，UI 出现【整理此便笺】按钮，点击后执行"导出当前纯内容 → 新建 Y.Doc → 写入 → 替换"，并**明确告知"此操作会清空该便笺的历史版本，当前内容不受影响"**，同时把旧文档存进本地归档目录保留 30 天。不自动执行，因为它是有损的。

#### 4.5.4 导出

`导出全部` 生成 zip：`notes.json`（完整 meta + 正文 CRDT 快照 base64 + 纯文本 + Markdown 三份表示）、`markdown/<id>-<title>.md`、`html/index.html`（可直接浏览的静态站）、`attachments/<hash>.<ext>`。**导出必须离线可用、不经过服务端、不依赖登录状态。** 同时提供 `bianfa export --out ./dump` CLI。

#### 4.5.5 「永不丢数据」原则清单

1. 任何写入先落本地磁盘，再考虑网络。
2. 同步游标只在数据与游标写在同一事务时推进。
3. 服务端"没有"永远不等于"应删除"；删除必须有显式 tombstone。
4. 删除是软的、可撤销的、有 30 天窗口的。
5. tombstone 永久保留（~100 B/条）。
6. 压缩只删中间过程，永远保留每日里程碑快照。
7. 客户端 id 由客户端生成，服务端不重新分配。
8. **所有写操作在语义上是 upsert；幂等表只是优化，不是正确性依赖。**
9. 合并结果收缩超阈值必须留证并告知用户。
10. bootstrap 只做 union，永不做 diff-delete。
11. 导出不依赖服务端、不依赖登录。
12. 迁移脚本必须先备份、可回滚，旧库改名保留而非删除。
13. **垃圾回收一律 mark-and-sweep，永不用分布式引用计数。**

#### 4.5.6 正确性怎么证明（初稿完全没有测试策略——这是最大的空洞）

CRDT 的 bug 不会在单测里出现，只会在用户那里出现。三条最低要求：

| 测试 | 做法 | 门槛 |
|---|---|---|
| **收敛性属性测试** | `proptest`（Rust）/ `fast-check`（TS）随机生成 3 个副本 × 各 200 次随机编辑（插入/删除/格式/中文/emoji），乱序交换 update，断言三副本最终 `to_plain_text()` 完全相等 | 每次 CI，1000 case |
| **双端互通测试** | Rust 侧 yrs 生成的 update 由 JS 侧 yjs 应用，反向亦然；**语料必须含中文与 emoji**（专为 4.2.4 的 `OffsetKind` 地雷设） | 每次 CI |
| **性能回归基准** | 10 万次编辑回放 + 把一个未 GC 的大 update 应用到已 GC 文档（Yjs 的已知慢路径），记录耗时并设上限 | 每次 CI，超 1.5× 基线即失败 |
| **崩溃注入** | 在 `pull_ok` 落盘事务中途 `kill -9`，重启后断言无数据丢失、无游标越位 | 每次发版前手动 + 每周 CI |

### 4.6 E2EE 与团队共享、服务端 LLM 的根本矛盾

#### 4.6.1 矛盾究竟在哪（要精确，不要一概而论）

常见说法"E2EE 不能做实时协同"是**错的**。Yjs update 可交换，服务端可只做按 `note_id` 的密文广播（哑中继），协同照样工作。真正的冲突是这几条：

| 能力 | E2EE 下 | 原因 |
|---|---|---|
| 多设备同步、离线合并 | ✅ | 哑中继 + 客户端合并 |
| 实时协同、awareness | ✅（awareness 也加密） | 同上 |
| **服务端 CRDT 快照压缩** | ❌ | 服务端看不懂密文，`merge_updates_v2` 也用不上（4.4.3），只能靠客户端代劳 |
| **服务端全文搜索** | ❌ | 只能本地 SQLite FTS5；新设备必须先同步完全部便笺才能搜 |
| **服务端 LLM 调用** | ❌ | 服务端拿不到明文，无法代理调用与配额计费 |
| **网页版 / 分享链接** | ❌ 严重受限 | 浏览器要先拿到密钥；公开分享链接等于交出密钥 |
| **团队新成员看历史** | ⚠️ 需密钥重分发 | 见下 |

#### 4.6.2 分层建议（三档，默认档不是 E2EE）

| 档位 | 适用 | 加密 | 可用能力 |
|---|---|---|---|
| **L0 服务端加密（默认，团队便笺唯一选项）** | 所有便笺、团队共享 | TLS 1.3 + 静态加密（磁盘级 LUKS 或 `pgcrypto`）+ 附件服务端加密 | 全部 |
| **L1 个人保险箱（可选，逐分组）** | 个人敏感便笺 | 每便笺 DEK（XChaCha20-Poly1305）；正文与附件密文；`title` 也加密，`color/geom/pinned` 不加密（否则列表无法渲染） | 同步 ✅ 多设备 ✅ 本地搜索 ✅ **BYOK 客户端直连 LLM ✅**；服务端搜索 ❌ 服务端 LLM ❌ 网页版 ❌ |
| **L2 全局 E2EE** | 不提供 | — | 会同时废掉团队功能与 AI 功能，与需求 2、3 直接冲突 |

**密钥体系（L1），全部为已核实的 crate 版本：**

| 用途 | crate | 版本（2026-09-04 实测） |
|---|---|---|
| 口令派生 KEK | `argon2` | 0.6.0 |
| 内容加密 | `chacha20poly1305`（XChaCha20-Poly1305） | 0.11.0 |
| 设备密钥对 | `x25519-dalek` | 3.0.0 |
| 设备间密钥分发（sealed box） | `crypto_box` | 0.9.1 |
| 内容寻址 hash | `blake3` | 1.8.7 |
| OS 密钥库（DPAPI / Keychain） | `keyring` | 4.2.0 |

（初稿写的"`ring` / `age` crate"过于笼统且不匹配实际需求——`age` 是文件加密格式，不适合逐便笺 DEK 包裹。以上为具体可 `cargo add` 的清单。）

- `MK`（32 B 随机主密钥）用 `KEK = Argon2id(password, salt, m=64MiB, t=3, p=4)` 包裹后存服务端；另用 24 词恢复码派生的第二个 KEK 包裹一份。
- 设备私钥存 OS 密钥库，**永不上传**。新设备加入：老设备用新设备公钥 sealed box 分发 `MK`。
- 每便笺 `DEK` 随机 32 B，用 `MK` 包裹后存 `notes.wrapped_dek`。
- 团队 E2EE（不在 v1）：`GK` 包裹 `DEK`，移除成员必须 rotate `GK` 并重包裹所有 DEK——**O(便笺数) 的重操作，是团队 E2EE 成本高的主因。**

#### 4.6.3 明确的取舍陈述（要写进产品文案）

> 团队共享便笺**不做端到端加密**，因为服务端必须能合并、压缩、检索并代理 AI 调用。我们对团队数据的承诺是：传输加密、静态加密、最小权限访问、审计日志、随时可全量导出。
> 需要端到端加密的内容，请放进**个人保险箱**——保险箱内的便笺不参与团队共享，不能用服务端 AI（可用你自己的 API Key 由客户端直连），搜索仅在已同步的设备本地生效。

这条边界必须在 UI 上可见（保险箱便笺显示锁形图标，AI 按钮变为"仅本地/BYOK"），而不是藏在隐私政策里。**开启保险箱前必须强制抄写 24 词恢复码并做一次验证输入**——密码遗忘 = 数据永久不可恢复，这会制造出比丢便笺更严重的差评。

### 4.7 反驳环节：对两个核心结论的对抗性复核

#### 反驳一："自研同步层只有 ~1500 行"——**这个数字是错的，但结论仍然成立**

反方：把 outbox、change feed、bootstrap、退避、幂等说成 1500 行，是典型的"只算 happy path"。真实要写的还有：pull/push 的分页与事务边界、outbox 的顺序保证与死信处理、WS 与轮询的双通道状态机、bootstrap 的断点续传、时钟偏移策略、冲突 UI 的数据通路、多窗口/多进程的本地协调、以及**上面 4.5.6 那一整套测试**。1500 行是 v0 demo 的量级。

**裁决：修正数字，维持结论。** 诚实估计是 **3500-5000 行（客户端 Rust + TS 合计）+ 1200-1800 行服务端 + 1500 行测试**，工期从初稿的 10 天上修到 **18-22 天**。但结论不变，因为：反方论据同样适用于任何现成引擎——用 PowerSync 也要写 Postgres 侧 schema/规则、写冲突后处理、写 Rust 侧的桥接（它没有 Rust 客户端），而且**还要额外承担引擎自身的 API 变动与商业风险**。自研的 4000 行全在我们的控制之内，且直接对齐"永不丢数据"的验收标准。**把工期估准，比换一个方案更重要。**

#### 反驳二："服务端对个人便笺完全哑存储"——**部分推翻**

反方：初稿把"哑存储"当成纯收益（零 CPU、可 E2EE），却在风险清单里承认它造成"客户端不上线就压不动、存储黑洞"。一个自己承认会导致存储无限增长的设计，不该被写成无条件的最优解。

**裁决：反方成立，结论修正。** 4.4.3 已改为**分级**：
- **L0 便笺**：服务端"不理解语义"但**可以做二进制层压缩**——`yrs::alt::merge_updates_v2` 不构造 Doc、不看业务结构，CPU 开销是一次线性解码 + 编码。收益（存储可控）远大于成本，**没有理由不做**。
- **L1 便笺**：才是真正的哑存储，配硬上限 + 客户端 `compact_request`。

初稿的"服务端不加载 Y.Doc"这个约束是对的，但它被错误地推广成了"服务端不能碰 payload"。**区分"不加载 Doc"与"不做任何处理"，是这一节最重要的修正。**

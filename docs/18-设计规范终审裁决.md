## 1 · Windows 便笺顶栏在窄窗口下的降级阶梯

### 问题
按基准 §6.3，Windows 便笺顶栏固定占用 = caption `─ ✕` 两枚 80 + 色点 14 + `⊙⋯` 预留 56 + 同步点 6 + 内边距/间隙 22 = **178px**。220px 窗口余 42px（勉强），基准 §5.6 规定的最小窗口 **180×140 只余 2px（不可行）**。且 `≥320px 高` 时右侧还要长出 meta（`14:22 · 142 字` ≈ 76px），220 宽 × 340 高的窗口需要 254px，**超出窗口本身**。

### 裁决

**(a) Windows 便笺窗取消最小化按钮，caption 收为单枚关闭按钮。**

| | macOS 便笺窗 | Windows 便笺窗 |
|---|---|---|
| caption | 自绘单个 12px 关闭点，**左**缘内缩 8px（macOS 约定） | 自绘单枚 `✕`，`--caption-btn-w` × 满栏高，**右**缘齐边、零内边距（Windows 约定） |
| 关闭态 | hover `--c-danger`，无红底 | hover 底 `#C42B1C` + 白字（实测 5.66:1），active `#B22A1B`（6.48:1） |
| 颜色点位置 | 让位到右侧组首位（`⊙` 左边） | 保持左缘 |
| 最小化 | 用系统 `⌘M`（进 Dock，可恢复） | **无按钮、无键位** |

删掉最小化的三条理由：① 品类领先者 Windows 便笺本身的便笺窗就只有 `⋯` 和 `✕`，没有最小化；② 便笺窗建议 `skipTaskbar:true`（否则 15 张便笺淹没任务栏预览与 Alt+Tab），而 `skipTaskbar` 窗口最小化后没有任何可恢复的入口，是一个会丢窗口的功能；③「让开」这个需求已经有两条更好的路径——双击顶栏折叠为标题条（motion §5.1）、托盘「隐藏全部便笺」（screens §9.1）。切换需求由 `Ctrl+Tab` 缩略图 HUD 承接。

**(b) 三档降级阶梯（容器查询，量的是便笺窗自身的宽）**

| 档 | 触发 | 顶栏内容（左→右，Windows） | 固定占用 | 余量 |
|---|---|---|---|---|
| **W-0** | 宽 ≥ 300px | 色点14 · [拖动区] · meta 76（仅当**高≥320 且 宽≥300**）· `⊙ ⋯`(预留56) · 同步点6 · `✕`40 | 138（+76） | @300 = 86 · @380 = 166 |
| **W-1** | 200 ≤ 宽 < 300 | 同上，**meta 第一个让位**——回落到底部操作条右侧（原本只有「高<320」才回落，现改为「高<320 **或** 宽<300」） | **138** | **@220 = 82** |
| **W-2** | 宽 < 200（compact） | **`⊙` 置顶第二个让位**——进 `⋯` 菜单，`Ctrl/Cmd+P` 键位不变；预留区 56→26 | **108** | **@180 = 72** |

让位顺序的依据：**meta 是纯信息、有第二个家（底部条）→ 最先让；`⊙` 是动作、有键位与菜单两条替代路径 → 第二让；`⋯`、色点、同步点、`✕` 各自是「全部动作的入口 / 身份 / 状态 / 关闭」，都是不可替代的最后一格 → 永不让位。** 拖动区在任何一档都 ≥ 72px，不会退化成不可拖。

**(c) `--ui-scale` 与 caption：自绘 ⇒ 必须缩放。**

结论：**Windows caption 40×28 是我们自绘的 HTML 元素，不是 OS 约定**（基准 §6.3 明写 `decorations:false` + 自绘；46×32 才是 Win11 对**系统绘制**主窗标题栏的规范，我们只在主窗遵守它）。既然自绘，且 `--ui-scale` 的存在理由是无障碍（低视力 / 运动障碍），**caption 不跟着放大是方向性错误**：130% 下窗口最小尺寸变成 234×182，正文字号 ×1.3，唯独关闭按钮还是 40×28，成了全窗最小的点击目标。

```css
:root{
  /* 自绘 chrome 一律走 rem，随 --ui-scale 走；clamp 保住命中区下限与美观上限 */
  --note-titlebar-h: max(28px, 1.75rem);          /* 90%→28  100%→28  115%→32.2  130%→36.4 */
  --note-toolbar-h:  max(32px, 2rem);
  --caption-btn-h:   var(--note-titlebar-h);      /* Windows caption 齐满栏高，是 OS 视觉惯例 */
  --caption-btn-w:   clamp(36px, 2.5rem, 56px);   /* 90%→36  100%→40  115%→46  130%→52 */
}
```

**推论（必须一起接受）：容器查询断点也必须改用 `rem`。** 否则 130% 下 234px 宽的最小窗口会被 px 断点判成「常规 sm」，W-2 档永远进不去。`<200px` → `< 12.5rem`（= 200px × scale）。`rem` 在容器查询条件里按**根元素**字号解析（我们控制的 `calc(16px * var(--ui-scale))`），这是可用的；但必须加一条门禁：`/dev/sizes` 面板 × 四档 scale × Playwright 断言每个断点的实际切换点。若某引擎解析行为不符，退路是 JS 在 `<html>` 写 `data-nw="xs|sm|md|lg|xl"`（ResizeObserver + scale 计算），CSS 改用属性选择器——**不要**在 `@container` 条件里写 `var()`，那是非法的。

### 理由
这是四份文档里唯一一处算术上不可能的规格。裁决没有第二条路：要么砍元素，要么砍窗口下限。砍窗口下限（把 180×140 提高）会连带作废基准 §5.1 的容量账与 §5.6 的 compact 档；砍 caption 只损失一个在 `skipTaskbar` 前提下本来就有害的按钮，而且与品类领先者一致。基准自己在 macOS 侧已经用同一条逻辑做过同一个裁决（「三键 + 安全区吃掉 220px 的 31%，且 Apple 自家 Stickies 就是单键」）——Windows 侧只是把这条逻辑对称地执行完。

### 需要改动
- **design_system.md §6.3**：Windows 便笺 `40×28` 两枚 → 单枚 `✕`；补 macOS 便笺窗关闭点在左、色点让位到右侧组的说明。
- **design_system.md §2.2**：`--caption-btn-w:40px; --caption-btn-h:28px` → 上面的 rem/clamp 版；`--note-titlebar-h` / `--note-toolbar-h` 同改。
- **design_system.md §5.6**：`≥320px 高` 出 meta → `≥320px 高 且 ≥300px 宽`；新增 W-0/W-1/W-2 三档阶梯表；断点阈值单位 px → rem。
- **design_system.md §5.1**：220×220 ASCII 图的顶栏行按 W-1 重画（单枚 `✕`）。
- **screens.md §2.2**：220px 顶栏图补上 Windows 的 `✕`；补「meta 的双条件」；补三档阶梯。
- **frontend_stack.md §4**：「Win11 便笺窗 40×28 的 `─ ✕`」→ 单枚 `✕`。
- **frontend_stack.md §8.1**：便笺窗 builder 补 `.skip_taskbar(true)`。
- **`src/platform/MANIFEST.md`**：caption 分叉条目补「按钮数量、位置（左/右）、色点位置」三项。

## 2 · 最低 WebView 基线

### 问题
frontend_stack §2.7/§8 声明 Safari 16.4 / macOS 13；motion §1.3 的 `linear()` 需 Safari 17.2 / macOS 14；screens §2.3/§6.1 的 CSS Anchor Positioning 需 Safari 26。三章各自假设了三条不同下限。

### 核实结果（2026-09）

**(a) macOS 存量与 Apple 支持窗口**
- Apple 的实际支持窗口是「最新 3 个大版本」，约 3 年。**macOS 13 Ventura 自 2025-09-15 起已不再收到安全更新**（2022-10 发布，末次更新 2025-08）。macOS 14 Sonoma 的安全更新窗口到 2026-09，也就是**此刻正在结束**。
- 存量高度集中在新版本：2026-07 末 telemetry 显示 **macOS 26.5 单版本占 64.94%**，27.0 占 1.03%；Ventura 在 2025 年就已跌到 5–8% 并持续衰减。
- 关键推论：**WKWebView 是系统组件，只随 OS/Safari 更新。** 一台停留在 macOS 13 的机器，等于一个不再打补丁的 WebKit——而 bianfa 会把 AI 供应商返回的 Markdown 渲染进这个引擎。这是安全问题，不是兼容问题。

**(b) Tauri v2 的 macOS 下限**
Tauri v2 支持 macOS 10.15+（默认 bundle 甚至到 10.13）。**框架不构成任何约束**，约束 100% 来自 WebKit 特性与安全窗口。

**(c) Windows 侧**
WebView2 **Evergreen** 运行时预装于全部 Windows 11，并已推送到符合条件的 Windows 10；它**独立于 OS 自动更新**，且被所有采用 Evergreen 的应用共享。**Windows 侧基本不存在这个问题**——但有三条必须落到工程里的推论，否则「基本不存在」会变成「偶发存在」：
1. 安装器必须带 Evergreen Bootstrapper，启动时用 `GetAvailableCoreWebView2BrowserVersionString` 检查 runtime ≥ **140.0.0.0**，低于则引导更新。不假设「Win11 一定有」。
2. **禁止 Fixed Version 分发模式**——它会把 Chromium 冻结在打包那天，等于自己造一条第二个 macOS 式的老基线，还额外付 ~180MB 安装体积。CI：`grep -rn 'WEBVIEW2_BROWSER_EXECUTABLE_FOLDER\|fixed[-_.]version' src-tauri/ apps/` 必须为空。
3. 企业组策略可以延迟/固定 Evergreen 更新，所以运行时版本检查是必需的，不能靠「Evergreen 永远最新」写代码。

### 裁决

**最低支持基线 = macOS 14.4 / WebKit ≡ Safari 17.4；Windows = WebView2 Evergreen ≥ Chromium 140。**

```jsonc
// tauri.conf.json
"bundle": { "macOS": { "minimumSystemVersion": "14.4" } }
// vite.config.ts
build: { target: ['chrome140', 'safari17.4'] }
```

为什么是 14.4 而不是 14.0：macOS 14.0 出厂的是 Safari 17.0，没有 `linear()`。14.4（2024-03）是 Safari 17.4 的系统切点，且任何还在收 Apple 更新的 macOS 14 机器早已越过它（终版是 14.7.x ≡ Safari 18.6）。选 14.4 让「基线」是一个数，而不是「一个 OS 版本加一串特性例外」。

**三层特性规则（机械可执行，写进 review checklist）**

| 层 | 范围 | 用法 |
|---|---|---|
| **无条件可用** | Safari ≤ **17.4** 已 ship | 直接写，不加 `@supports` |
| **允许但必须带降级** | Safari 17.5 – 18.6 | 必须 `@supports` / `CSS.supports()`，且**降级路径不得改变换行结果**（红线 3） |
| **禁止** | Safari ≥ 26 独有 | 一律不用，不做双路径 |

**落到具体特性：**

| 特性 | 层 | 处置 |
|---|---|---|
| `linear()` 缓动（Safari 17.2） | 无条件 | 可用；仍加 3 行 `@supports` 兜住 14.0–14.3 长尾（见下） |
| container queries / `:has()` / `oklch()` / `color-mix()` / `@property` / `overflow:clip` / `cq` 单位 | 无条件 | 可用 |
| `light-dark()`（17.5） | 带降级 | 已按基准 §6.2 走三段式选择器，本来就不作为唯一机制 ✓ |
| `text-box-trim`（18.2） | 带降级 | 仅 `.btn/.tab/.badge`，`@supports (text-box: trim-both cap alphabetic)` 包住；不支持时行盒略高，**不改宽度、不改换行** ✓ |
| **CSS Anchor Positioning（26.0）** | **禁止** | 单路径 Floating UI，见下 |
| `text-spacing-trim` / `hanging-punctuation` / `field-sizing` / `scrollbar-color` | 禁止 | 维持基准 §3.3、frontend_stack §2.7 的既有裁定 |

**降级路径 ①：`linear()` 不可用时**

```css
:root{
  /* 基线值：任何不支持 linear() 的引擎（macOS 14.0–14.1 长尾）都拿到一条能用的曲线 */
  --ease-spring: cubic-bezier(.34, 1.30, .52, 1);
}
/* 探测必须用「函数形式」——linear 关键字到处合法，探测不到东西 */
@supports (transition-timing-function: linear(0, 1)) {
  :root{
    --ease-spring: linear(
      0, 0.164, 0.470, 0.746, 0.931, 1.026, 1.057,
      1.053, 1.037, 1.020, 1.007, 1.000, 1
    );
  }
}
```
```ts
// packages/ui/src/motion.ts —— CSS 与 WAAPI 共用同一条字符串，禁止两处各写各的
const SPRING_LINEAR =
  'linear(0, 0.164, 0.470, 0.746, 0.931, 1.026, 1.057, 1.053, 1.037, 1.020, 1.007, 1.000, 1)';
export const EASE_SPRING =
  CSS.supports('transition-timing-function', 'linear(0, 1)')
    ? SPRING_LINEAR
    : 'cubic-bezier(.34, 1.30, .52, 1)';
export const DUR_SPRING = 360;   // --dur-5，两条分支同时长；差别只是尾部没有二次回弹
```
两条分支同时长、同起止值，只有 5.8% 超调后的尾部形状不同，位移量 ~13px（基准 §5.7 的 `scale(.94)→1`），肉眼不可分；而受影响的人群是「装了 macOS 14 却从未打过一次系统更新」的极长尾。**代价是 3 行 CSS + 1 个三元表达式，买断整条尾巴，没有理由不做。**

**降级路径 ②：Anchor Positioning 不可用时 → 单路径 Floating UI，不做双实现**

裁定**不做** `@supports (anchor-name: --x)` 的双路径。理由不是「省事」：Anchor Positioning 与 Floating UI 的翻转/推挤语义不同（`position-try-fallback` 的 `flip-block` vs `flip()` middleware 的候选序），双路径会让同一条格式浮条在 macOS 26 与其它环境上**落在不同位置**——这正是基准 §3.3 那条「要么两平台都开、要么两平台都关」所禁止的分叉类型。

```ts
// packages/ui/src/hooks/useAnchored.ts —— 全 app 唯一的浮层定位入口
import { useFloating, offset, flip, shift, size, autoUpdate } from '@floating-ui/react-dom';

export function useAnchored(placement: 'top' | 'bottom' = 'top', gap = 8) {
  return useFloating({
    placement,
    // 便笺窗 .note-window 是 overflow:hidden，absolute 会被裁；必须 fixed + portal
    strategy: 'fixed',
    whileElementsMounted: autoUpdate,          // 滚动 / resize / 内容变化自动跟随
    middleware: [
      offset(gap),                              // = screens §2.3 的「选区上方 8px」
      flip({ fallbackPlacements: ['bottom', 'top-start', 'bottom-start'] }),
      shift({ padding: 6 }),                    // 220px 窗内强制夹紧，不许溢出窗口
      size({
        apply({ availableWidth, elements }) {   // xs 容器下自动收窄，配合 §2.3 的五项折叠
          elements.floating.style.maxWidth = `${Math.max(160, availableWidth - 12)}px`;
        },
      }),
    ],
  });
}
```

**两条必须一起写进代码注释的约束**（否则 `strategy:'fixed'` 会静默失效）：
1. 浮层必须 portal 到 `.note-shell` 的兄弟节点 `#float-root`，**不得挂在 `.ai-stream` 内部**——motion §2.1d 的 `contain: layout style` 会成为 `position:fixed` 的包含块。
2. 任何祖先上残留的 `transform`（**包括 `scale(1)`**）同样会成为包含块。这与 motion §3.2 的规则合流：动画结束必须写 `transform: none`，不是 `scale(1)`。

**一句话结论：Windows 的下限是一个我们随时可以抬高的构建常量；macOS 的下限是一个只能靠放弃用户才能抬高的系统版本。所以整个产品的特性基线 = macOS 基线，Windows 侧永远只做「不低于 macOS 基线」的运行时检查，不单独开任何特性。**

## 3 · `Cmd/Ctrl+E` 的格式栏与底部操作工具栏重叠

### 问题
两者都是 `position:absolute; bottom:0; height:32px`，会直接重叠。选项：替换 / 叠加（总高 64px = 220px 窗口的 29%）/ 其它。

### 裁决

**取「替换」，但把它定义成一件更小的事：底部只有一条物理工具栏，它有两种模式。**

```
.note-toolbar[data-mode="object"]   ◉换色  ⇧置顶  ✦AI  ⋯更多            42 字
.note-toolbar[data-mode="format"]   ⟨返回  B I U S  ☐  ≔  🔗            ✦
```

- **只有一条 DOM 元素、一个高度（`--note-toolbar-h`）、一个 `bottom:0`。** 两组图标预置在同一条上，切换是 `opacity` 交叉淡入（`--dur-2`），**条高不变、内容区 `padding-bottom` 不变 ⇒ 零 layout shift、零额外高度占用**。
- `Cmd/Ctrl+E` 的语义统一定义为「**切换底部条的模式**」，不是「唤起第三条栏」。再按一次或 `Esc`（Esc 链第 5 级之前）回到 `object` 模式。
- **≥380px（底部条已常驻且已含 Markdown 组）**：`Cmd/Ctrl+E` 不切模式，改为把焦点送进常驻条的第一个格式按钮（roving tabindex）；再按或 `Esc` 把焦点还给编辑器并**还原光标位置**。
- **有选区时**：浮动格式条已经因选区浮出来了，`Cmd/Ctrl+E` 直接把焦点送进它，同样不切底部条模式。

三条路径合流成一句可实现的规则：**`Cmd/Ctrl+E` = 「把格式操作交到我的键盘手上」，具体交给谁由当前状态决定；任何情况下都不会出现两条 32px 条同时贴底。**

### 理由
- 「叠加」直接违反 screens §2.2 自己立的契约：「底部操作工具栏用 absolute 覆盖、不参与布局；**只有当内容已滚到底时才给正文加 `padding-bottom:32px`**，这样它出现时永远不会盖住正在写的那一行」。64px 会盖住 2.7 行正文（23.8px/行），而且恰好盖在「用户正在给它加粗的那段文字」上——最坏的时机。
- 「浮动格式条改浮在操作条上方」只是换个说法的叠加，还多一层 z 序。

## 4 · `Cmd/Ctrl+W` = `close()` 还是 `set_visible(false)`

### 问题
screens §1 说「收起，位置保留」，motion §5.3 说关闭动画后调 `close()`。直接决定 frontend_stack §8.2 的 420MB RSS 预算是否成立。

### 技术事实（裁决的依据）

**隐藏的 webview 仍然占几乎完整的内存，两个平台都是。**

- **Windows / WebView2**：隐藏宿主 HWND 会让 WebView 进入 occluded 状态 → 合成器丢弃可见 tile、`rAF` 停摆、渲染进程降优先级。但**渲染进程不会退出**，V8 isolate、DOM 树、样式/布局结构、应用 JS 堆全部原地保留。WebView2 之所以要额外提供 `MemoryUsageTargetLevel = Low` 这个 API，恰恰证明「隐藏本身不回收内存」——那个 API 才是用来主动 trim 缓存与解码图像的，量级是几十个百分点，不是数量级。
- **macOS / WKWebView**：把窗口 order out 不会终止 Web Content 进程。macOS 的内存压缩会降低**物理**足迹，但进程与地址空间都在，且压缩过的页在下次触碰时要解压。
- **两个平台都不会自动回收隐藏的 webview。** 唯一确定性的回收方式是销毁它。

### 内存预算表

单窗口模型（Windows 11 / WebView2 Evergreen / 2× DPI / 220×220 / 未聚焦、编辑器未挂载）：

| 组成 | RSS |
|---|---|
| WebView2 渲染进程地板（V8 isolate + Blink + Skia + IPC） | ~34 MB |
| 应用 JS 堆（React 19 共享 chunk + note 入口 45KB + Zustand + Query client） | ~8 MB |
| 该便笺的 DOM / 样式 / 布局（~108 汉字） | ~1 MB |
| **未聚焦便笺窗小计** | **~43 MB**（另占 2.2 MB 显存，2 个合成层 @2×） |
| 聚焦且 Tiptap 已挂载（同时最多 1–2 个，frontend_stack §7.1） | **+14 MB → ~57 MB** |
| 隐藏后（`set_visible(false)` + `MemoryUsageTargetLevel=Low`） | **~34 MB（仅 −21%）** |
| 关闭后（`close()`） | **0**（进程退出） |

共享底座（每 app 一份）：Rust 主进程 + SQLite + 托盘 ~45 MB · WebView2 browser + GPU + 网络/存储 utility ~120 MB · 预热窗口 1 个 ~34 MB · 主窗（打开时，虚拟滚动 1120×760）~150 MB。
**底座 = 45 + 120 + 34 = 199 MB。**

| N 张便笺 | 全部**可见**（两策略相同） | N 张按 `⌘W` 收起后 · **hide** | N 张按 `⌘W` 收起后 · **close** |
|---:|---:|---:|---:|
| 1 | 199 + 57 = **256 MB** | 199 + 34 = **233 MB** | **199 MB** |
| 5 | 199 + 43×4 + 57 = **428 MB** | 199 + 34×5 = **369 MB** | **199 MB** |
| 15 | 199 + 43×14 + 57 = **858 MB** | 199 + 34×15 = **709 MB** | **199 MB** |
| 30 | 199 + 43×29 + 57 = **1503 MB** | 199 + 34×30 = **1219 MB** | **199 MB** |

### 裁决

**(a) `Cmd/Ctrl+W` = `close()`。** 销毁窗口与 webview；关闭前把「位置 / 尺寸 / 滚动位置 / 折叠态」写入 `tauri-plugin-store`，内容早已在 SQLite。「收起」是**对用户的说法**，不是实现——三章统一措辞为「**收起（关闭窗口，不删除内容）**」。

**(b) 明确否决混合策略（N 个以内 hide、超出则 close）。** 混合策略唯一的收益是重开延迟，而这个收益**已经被预热窗口池买断了**：screens §9.2 的预热池（常驻 1 个已完成 webview 初始化的隐藏窗口）让「从 SQLite 恢复一张便笺」走的是和「新建一张便笺」完全相同的 ≤200ms P95 路径。既然重开延迟相同，hide 就是纯粹多付 34MB/张。**被严格支配的方案不需要阈值调参。**

**(c) `set_visible(false)` 保留在唯一一处：托盘的「隐藏全部便笺」**（screens §9.1，会议共享屏幕前一键收）。它必须是 hide，因为 close 会丢掉 undo 栈、IME 组合、滚动位置这些**瞬态**。但要加一条上限：**隐藏超过 10 分钟自动降级为 `close()`**（位置已保存，「显示全部便笺」时从 SQLite + store 恢复），把最坏驻留时间从「无限」压到 10 分钟。

**(d) frontend_stack §8.2 的「15 窗口常驻 RSS 增量 ≤ 420 MB」不成立，且与策略无关。** 15 张可见的实际增量是 858 − 199 = **659 MB**。420MB（= 28MB/窗）这个数把「每窗口只有 45KB gzip 的 bundle」误当成了「每窗口只有几十 MB 的进程」——Chromium 渲染进程的地板不由我们的 bundle 大小决定。改为三条可测子项：

| 新预算 | 值 |
|---|---|
| 未聚焦便笺窗 RSS 增量 | **≤ 45 MB / 窗** |
| 15 张可见时进程组总量（不含主窗） | **≤ 900 MB** |
| 含主窗 | **≤ 1.1 GB**（对 motion §8 验收 #8 的 1.3GB 上限留 200MB 余量）|

**(e) 同时可见便笺窗设软上限 24 张**（≈1.3GB 门槛处）。**不自动关用户的窗**——那比内存问题更糟。超过时托盘图标出 `--c-warning` 角标，菜单第一项变为「桌面上有 26 张便笺，占用内存较高 · 收起最久未用的 6 张」。screens §1 的「便笺窗（多实例，**无上限**）」改为「无硬上限，软上限 24 张并给出可执行提示」。

**(f) 新增门禁**（防止半年后有人把这条改回去）：`set_visible(false)` 前后 15 秒测一次进程组 RSS，**降幅必须 < 25%**——这条断言一旦通过，就固化了「隐藏不回收」这个事实依据；一旦哪天平台真的实现了隐藏即回收，它会红，那时才是重新讨论 hide 的时候。

### 需要改动
- **design_system.md §7** 键盘导航行：`Ctrl/Cmd+W` 关闭 → 「`Ctrl/Cmd+W` **收起 = `close()`**（销毁窗口；内容在 SQLite、位置在 store，永不删除）」。
- **design_system.md §8 红线 2**：末尾补「**且不得以 `set_visible(false)` 代替 `close()` 来实现『收起』**——隐藏的 webview 仍占约 79% 的 RSS」。
- **screens.md §1** 关窗语义段 + **§9.1** 「隐藏全部便笺」条：按上文改写，补 10 分钟自动降级。
- **screens.md §1** 第 1 条：便笺窗「无上限」→「无硬上限，软上限 24 张」。
- **motion.md §5.3**：关闭动画后 `close()` ✓ 保持不变，补一句「这条与 screens 的『收起』是同一件事，措辞见基准 §7」。
- **frontend_stack.md §8.2**：「15 窗口常驻 RSS 增量 ≤ 420 MB」→ 上表三条子项。
- **motion.md §8**：新增验收 #25「隐藏不回收断言」。

## 5 · Toast 与批量操作条的位置

### 问题
Toast（基准 §4：底部居中距边 24）与批量条（screens §3.2：底部居中悬浮 52px pill）抢同一位置，而「选中 3 张 → 删除 → 撤销 Toast」是必然路径。

### 裁决

**底部中央不是两个自由浮层，是一个栈：`.bottom-dock`。**

```css
.bottom-dock{
  position: fixed; left: 50%; bottom: var(--sp-6);        /* 16 */
  transform: translateX(-50%);
  display: flex; flex-direction: column-reverse;          /* 批量条永远贴底，Toast 向上生长 */
  align-items: center; gap: var(--sp-4);                  /* 8 */
  z-index: var(--z-toast);
  pointer-events: none;                                   /* 子元素各自开 auto */
}
.bottom-dock > *{ pointer-events: auto; }
/* dock 成员进出时，其余成员用 transform 平移，绝不过渡 bottom（红线 2：只动 transform/opacity） */
.bottom-dock > *{ transition: transform var(--dur-3) var(--ease-out); }
```

- dock 有两个槽，`column-reverse` 下从底到顶依次是 **`[批量条]` → `[toast-region]`**。
- **基准 §4 的「距边 24」被完整兑现**：dock 距边 `--sp-6`(16) + 成员间距 `--sp-4`(8) = 24，且现在这个 24 是由 token 算出来的，不是一个裸值。
- **批量条不在场时**（便笺窗内、设置窗、无选区的主窗），dock 只有 toast-region，视觉与基准 §4 逐像素一致。
- **批量条在场时**，Toast 自动上移 52 + 8 = 60px，用 FLIP `translateY` 平移（`--dur-3 --ease-out`），不做 `bottom` 过渡。
- toast-region **内部**维持基准 §4 的堆叠视觉（同屏最多 3 条、堆叠 offset 6px + `scale(.98)`），它作为一个整体是 dock 的一个成员。

**「选中 → 删除 → 撤销 Toast」这条必然路径的时序**：删除执行 → 选区清空 → 批量条 `--dur-2 var(--ease-in)` 退场（出场 = 进场 `--dur-3` 降一级，motion §1.1 原则 3）→ Toast 在 `--dur-2` 结束后入场（`--dur-3 var(--ease-out)`），落到 dock 底槽。两者**不是让位，是交接**。

**为什么必须建 dock，而不是只写一条「批量条在时 Toast 上移 60」的规则**：删除只是批量动作之一。「移到笔记本 / 加标签 / 换色」都会在**选区仍然存在**时弹出 Toast，那时两者是真同屏；「同步失败」这类系统 Toast 更是随时可能在有选区时到达。一条 if 规则要在 4 个地方各写一遍，dock 只写一次。

### 理由
把两个各自 `position:fixed; bottom:*` 的浮层改成一个 flex 容器的成员，是把「位置协商」从运行时的 if 语句移到布局引擎里——这类冲突的正确解法。同时它顺手消灭了基准 §4 里 `24` 这个裸值，并且全程只动 `transform`，不碰红线 2。

### 需要改动
- **design_system.md §4 Toast 行**：「底部居中距边 24」→「位于 `.bottom-dock` 内（dock 距边 `--sp-6`，成员间距 `--sp-4`，二者之和 = 24）」。
- **design_system.md §2.2**：无需新 token（复用 `--sp-4/--sp-6/--z-toast`）。
- **screens.md §3.2 批量条**：补「批量条是 `.bottom-dock` 的底槽成员」；出场时长补 `--dur-2 var(--ease-in)`。
- **screens.md §0 z 轴行**：批量条从 `--z-float` 改挂 `--z-toast`（它和 Toast 现在是同一个容器的成员，不能分属两层）。
- **motion.md §2 Toast 行**：「位置按基准 §4：底部居中距边 24」→ dock 描述；新增一行「dock 成员进出 · 其余成员 `translateY` · `--dur-3 var(--ease-out)`」。

## 6 · 便笺墙卡片上三种边框的优先级

### 问题
3px 身份色条（左）+ 2px 选中描边（四边）+ 2px 正在编辑色边框（右）会同时出现，且选中描边会覆盖另外两条。

### 裁决

**一条优先级规则：身份 > 我的状态 > 他人的状态。三者各占独立的几何通道，永不互相遮挡——冲突不靠 z 序解决，靠不重叠解决。**

| 层 | 语义 | 几何通道 | 画法 |
|---|---|---|---|
| **1 身份** | 这张便笺是什么颜色 | 卡片**内**·左缘 | `::before` — `position:absolute; inset-block:0; left:0; width:3px; background:var(--note-dot); border-radius:var(--r-md) 0 0 var(--r-md)`。**任何状态下 3 个像素一个不少。** |
| **2 他人在编辑** | 别人的状态 | 卡片**内**·右缘 | `::after` — `inset-block:0; right:0; width:2px; background:var(--note-dot-user)` + 卡片底一行 `--fs-2xs`「✎ Lin 正在编辑」（不靠颜色单载信息） |
| **3 选中（我）** | 我的状态 | 卡片**外**·第 1 环 | `box-shadow: 0 0 0 2px var(--c-surface-1), 0 0 0 4px var(--c-accent)` + 底色 `--c-selected` + 左上角 12px `✓` + `aria-selected="true"` |
| **4 键盘焦点（我）** | 我的状态 | 卡片**外**·第 2 环 | `outline: 2px solid var(--c-focus)`；未选中 `outline-offset:2px`，已选中 `outline-offset:6px`（让到选中环外面） |

**为什么选中环必须搬到卡片外**：3px 身份条占 x∈[0,3)，任何 2px 的 inset 描边都会吃掉它 2/3。而网格 `gap: var(--sp-5)`(12px) 有充足空间——2px 环 + 2px 白隙共占 4px，两张相邻选中卡之间仍留 4px 净距。选中 + 聚焦同时出现时是 2px 环 / 2px 隙 / 2px 环的双环，是 Finder 早已验证过的「已选中且有焦点」惯用形态。

**实现上的一个必须写对的细节**——选中环和 hover 阴影是同一个 `box-shadow` 属性，分开写后者会覆盖前者：

```css
.wall-card{
  --ring: 0 0 0 0 transparent, 0 0 0 0 transparent;   /* 未选中：两段占位，保证段数恒定 */
  box-shadow: var(--ring), var(--sh-1);
  transition: box-shadow var(--dur-1) linear;         /* 主窗卡片不在红线 2 辖区（辖区是便笺窗） */
}
.wall-card:hover                    { box-shadow: var(--ring), var(--sh-2); }
.wall-card[aria-selected="true"]    { --ring: 0 0 0 2px var(--c-surface-1), 0 0 0 4px var(--c-accent);
                                      background: var(--c-selected); }
.wall-card:focus-visible            { outline: 2px solid var(--c-focus); outline-offset: 2px; }
.wall-card[aria-selected="true"]:focus-visible { outline-offset: 6px; }
```

**四条同时出现时的完整读法**（真实存在的最坏情形：一张柠檬色便笺，被我选中、有键盘焦点、Lin 正在编辑它）：
```
   ┌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌┐   ← 外环 2px --c-focus（offset 6）
   │ ┌──────────────────┐ │  ← 内环 2px --c-accent（offset 2）
   │ │▎ ✓ 便笺墙分组逻辑▕│ │  ▎=3px --note-dot（柠檬）  ▕=2px --note-dot-user（Lin）
   │ │  v3               ▕│ │     底 --c-selected
   │ │  ✎ Lin 正在编辑   ▕│ │
   │ └──────────────────┘ │
   └╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌┘
```
四条信息、四种颜色、四个互不相交的位置，没有一条被压掉。

**顺带修掉红线 3 的一处违规**：`--note-dot-user`（协作者色）与 `--note-dot`（便笺色）都必须走 L3 通道由 JS 写在卡片根元素上，**组件层不得出现 `var(--p-*-dot)`**（sweep B10；frontend_stack 门禁 #8 会当场判失败）。基准 §4 Avatar 的「底色 = `userId` hash → 10 个 dot 色」同改。

### 理由
sweep F6 只要求「一条优先级规则」，但纯粹的 z 序优先级解决不了问题：优先级高的把优先级低的**盖住**，信息就丢了。正确的解法是把三类信息分配到三个不会相交的几何位置，让优先级只在极端情况下（位置真的用完了）才需要仲裁——而 208×180 的卡片有左缘、右缘、外环、外环之外四个通道可用，根本不会用完。screens §5 已经做对了一半（「左边框已被 3px 颜色身份条占用，两条信息不许抢同一条边」），这里只是把这条原则贯彻到第三、第四条信息上。

### 需要改动
- **screens.md §3.2 多选**：「选中态用 `--c-selected` 底 + 2px `--c-accent` 描边」→ 上表第 3 行的外环写法。
- **screens.md §3.1**：色条 `background: var(--p-<color>-dot)` → `var(--note-dot)`（L3 中转）。
- **screens.md §5**「谁在编辑」：用户色 `--p-*-dot` → `--note-dot-user`（L3）；补第 1/3/4 层同时出现时的读法。
- **screens.md 新增 §3.5「卡片状态优先级」**：上表全文 + 合并 `box-shadow` 的实现注意。
- **design_system.md §4 Avatar 行**：「底色 = `userId` hash → 10 个 dot 色」→「→ L3 `--note-dot-user`，由容器 JS 赋值」。
- **design_system.md §7 focus 可见性行**：补「卡片同时选中且聚焦时，焦点环 `outline-offset` 由 2px 让到 6px」。

## 7 · `Cmd/Ctrl+N` 的存废 + 最终全局快捷键总表

### 问题
screens §2.6 引用了不存在的「§12 反向裁定」来为 `Cmd/Ctrl+N` 辩护（悬空引用）。同时快捷键层还有 7 处冲突未裁。

### 裁决 A：`Cmd/Ctrl+N` **保留为唯一的应用内新建键；`Cmd/Ctrl+Shift+N` 这个别名删除。**

理由：① 两个组合绑同一个动作没有任何收益，只是把基准 §7 的历史值和 screens 的直觉值一起留着不做选择；② `⌘N` 是全平台通用的「新建」，而 `⇧⌘N` 在 macOS Finder 是「新建文件夹」、在浏览器是「无痕窗口」，用户对它的预期不是「新建一张便笺」；③ 全局系统热键固定为 `⌥⌘N` / `Ctrl+Alt+N`（sweep 组 1 已裁），与应用内键不同，符合「全局 ≠ 应用内」原则；④ 需要 `⇧⌘N` 的用户可在设置 → 快捷键里自行加回。**悬空引用直接删除，不补写 §12。**

### 裁决 B：macOS 的 `⌃` 系与我们的键位——**冲突是想象出来的**

macOS 系统级 Emacs 文本绑定（NSTextView，WKWebView 的 `contenteditable` 同样遵守）是 **`⌃`（Control）** 系：`⌃A`=行首、`⌃E`=行尾、`⌃K`=删到行尾，另有 `⌃F/⌃B/⌃N/⌃P/⌃D/⌃H/⌃O/⌃T/⌃V/⌃Y`。

**bianfa 在 macOS 上的所有应用内快捷键一律用 `⌘`（必要时 `⇧⌘`/`⌥⌘`），一个 `⌃` 单键组合都不占。** 因此：
- 我们的格式条键在 mac 上是 **`⌘E`**，系统的行尾是 **`⌃E`** —— **不同物理键，零冲突**。
- 我们的命令面板键在 mac 上是 **`⌘K`**，系统的删到行尾是 **`⌃K`** —— **零冲突**。
- 之所以看起来像冲突，是因为 Windows 侧写作 `Ctrl+E` / `Ctrl+K`，字面联想过去了；而 Windows 根本没有 Emacs 绑定集，那边也没有冲突。

**真正被 `⌃A` 影响的只有一处，而且方向相反**：因为 mac 上 `⌃A`=行首、`⌘A`=全选是**两个**键，所以 mac 天然没有歧义；**「全选便笺 vs 全选文本」是 Windows 独有的问题**——那边 `Ctrl+A` 是唯一的全选键。解法见下面的「焦点作用域规则」，两平台写同一条规则，mac 只是碰巧还多一条系统级 `⌃A` 我们不碰。

### 最终全局快捷键总表

1. **全局系统热键 ≠ 任何应用内快捷键。** 否则应用在前台时无法判定该由 OS 热键还是窗口 handler 响应（Tauri 的 global-shortcut 在应用聚焦时仍然拦截）。

## 8 · AI 抽屉高度公式

### 问题
screens §6.1 写 `min(60% 窗口高, 280px)`，380px 高窗口得 228px，sweep 怀疑语义应为 `max`。

### 裁决

**`min` 是对的，`max` 才是错的——sweep 这一条的怀疑不成立。** `min(60%, 280px)` 精确表达的就是「占窗口高的 60%，但不超过 280px 的硬帽」，这正是想要的语义；换成 `max` 会在 700px 高的窗口上得到 420px 的抽屉，把正文压到 4 行以下，与设计意图相反。

**真正的缺陷是另外两个：缺下限，和缺「给正文留底」的约束。** 改为一条 `clamp`，且把主约束从「给抽屉多少」翻转为「**给正文留够**」：

```css
:root{
  /* 抽屉自身 chrome：模型条 32 + 结果操作条 32 + 拖动分隔线 4 = 68 */
  --ai-drawer-chrome: calc(var(--note-toolbar-h) * 2 + 4px);
  /* 抽屉最小可用：chrome + 4 行 AI 输出（4 × 23.8 ≈ 100） */
  --ai-drawer-min: calc(var(--ai-drawer-chrome) + 100px);          /* ≈168px */
  /* 正文地板：顶栏 + 首行标题 24 + 4 行正文 95 */
  --note-body-floor: calc(var(--note-titlebar-h) + 24px + 95px);   /* ≈147–152px */
}
.ai-drawer{
  block-size: clamp(
    var(--ai-drawer-min),                                          /* 下限 */
    60cqh,                                                         /* 目标：容器高的 60% */
    min(280px, calc(100cqh - var(--note-body-floor)))              /* 上限：硬帽 ∧ 给正文留底 */
  );
}
```

验算（`cqh` = `container:note / size` 的高度，容器查询单位在基线内，Safari 16+）：

| 窗口高 | 60cqh | 上限 `min(280, H−152)` | 结果 | 剩给正文 |
|---:|---:|---:|---:|---:|
| 340（自动扩窗失败的兜底） | 204 | min(280, 188) = 188 | **188** | 152 ✓ |
| 380（未触发自动扩窗） | 228 | min(280, 228) = 228 | **228** | 152 ✓ |
| 420（自动扩窗后的常态） | 252 | min(280, 268) = 268 | **252** | 168 ✓ |
| 700 | 420 | min(280, 548) = 280 | **280** | 420 ✓ |

**配套两条：**
- 上式给的是**初始值与复位值**。用户拖分隔线后的值按便笺持久化，但**每次窗口 resize 都要用同一条 `clamp` 重新夹一次**——否则把窗口从 700 拖到 400 时，一个 420px 的抽屉会把正文压没。
- screens §6.1 的「窗口高 < 380 时自动临时扩窗到 420，关闭抽屉后回弹到原高度」保持不变；`--ai-drawer-min` 是它失败时（多显示器边界、用户已手动锁定尺寸）的兜底，不是替代。

### 理由
一个只有上限没有下限的公式，在「窗口被拖到最小」和「抽屉被拖到最小」两条路径上都会产出不可用的抽屉；而 sweep 提议的 `max` 会在另一端产出不可用的正文。`clamp` + 一条以正文地板为准的上限，是唯一能同时守住两端的写法，且它把「便笺正文字号 14px 是地板」（基准 §7）这条无障碍要求延伸成了「便笺正文**行数**也有地板」——同一条原则的自然推论。

### 需要改动
- **screens.md §6.1** 第 1 条：`高度 min(60% 窗口高, 280px)` → 上面的 `clamp` 全文 + 验算表；补「resize 时重新夹紧」。
- **design_system.md §2.2 便笺几何块**：新增 `--ai-drawer-chrome` / `--ai-drawer-min` / `--note-body-floor` 三个 L2 几何 token（并进 frontend_stack §2.2 的 `geometry.json` 与 `bfName()` 的 `geometry` 分支）。
- **frontend_stack.md §2.4 `bfName()`**：`geometry` 分支已能覆盖，无需改代码，但 §10 目录的 `geometry.json` 注释要补这三项。

## 9 · 设置项 `✓` 闪现的 `--dur-4` 与 600ms

### 问题
screens §7 写「改动后对应行右侧闪一次 `✓`（`--dur-4` 淡出，共 600ms）」，300ms 的 token 与 600ms 总时长的关系未说明。

### 裁决

**`600ms` 不是任何一个可设置的值，它是三段之和。从文档里删掉这个数，改写成三段，每段各有 token。**

```
① 出现  opacity 0→1   --dur-1   (90ms)   --ease-out
② 保持  opacity 1     --delay-ack (200ms)   ← 不是 duration，是 transition-delay
③ 淡出  opacity 1→0   --dur-4   (300ms)  --ease-in
                                  总计 590ms
```

```css
/* 非对称进出场的标准写法：进出各写一条 transition，靠属性切换选边 */
.ack{                  opacity:0; transition: opacity var(--dur-4) var(--ease-in) var(--delay-ack); }
.ack[data-on]{         opacity:1; transition: opacity var(--dur-1) var(--ease-out) 0s; }
```

**三条配套裁定：**

**(a) 新增 `--delay-*` 命名空间**，给全套散落的裸延迟一个家（这同时解掉 sweep B7）：
```css
:root{
  --delay-ack:200ms;            /* 设置项 ✓ 的保持段 */
  --delay-selection:180ms;      /* 浮动格式条的 selectionchange debounce（sweep B7/F2b）*/
  --delay-tooltip-in:500ms; --delay-tooltip-out:100ms;   /* 基准 §4 Tooltip */
  --delay-toolbar-blur:200ms; --delay-toolbar-leave:800ms; /* 基准 §5.4 双条件隐藏 */
  --delay-sync-show:300ms;      /* syncing < 300ms 不点亮（motion §2）*/
}
```
**保持段必须用 `--delay-*` 而不是 `--dur-3`**：motion §7 会把 `--dur-3` 在 reduced-motion 下压到 100ms，而「✓ 停留多久」是**信息**不是动效，被 reduced-motion 缩短是错的。

**(b) `--dur-4` 出场是 motion §1.1 原则 3（出场 = 进场降一级）的一处登记例外。** 这里进场 `--dur-1` 已在阶梯底，按规则出场也应是 `--dur-1`；但确认闪现的出场慢是**有意的**——90ms 的淡出会让用户怀疑自己看错了，而这个 `✓` 是「设置已保存」的唯一反馈（screens §7：全部即时生效，无保存按钮）。例外写进 motion §1.2 的出场档位映射表，并注明「仅此一处」。

**(c) reduced-motion 下**：`--dur-1`→1ms（立即出现）、`--delay-ack` 不变（200ms，信息不缩短）、`--dur-4`→100ms（motion §7 的高三档统一值）。总计 301ms，仍然读得到。

**(d) 这个 `✓` 不占 spring 名额。** 基准 §5.7 的三处 spring 是「新建 / 落位 / 待办打勾」；设置项的确认 `✓` 不是待办打勾，用 `--ease-out`。

### 理由
「共 600ms」这种把总时长写死的表述，是 token 体系里最容易腐烂的一类：它既不能被 `--dur-*` 表达，又会在任何一段被调整时静默变错，而且没有任何一段代码能引用它。拆成三段之后，每一段都有 token、都能被 reduced-motion 正确处理、都能被 motion §8 门禁 #24（禁裸数值时长）机器检查。

### 需要改动
- **screens.md §7 保存语义**：「闪一次 `✓`（`--dur-4` 淡出，共 600ms）」→ 三段表 + CSS。
- **design_system.md §2.2 动效块**：新增 `--delay-*` 六项。
- **design_system.md §7 reduced-motion 行**：补「`--delay-*` 不受 reduced-motion 影响——延迟承载信息，不是动效」。
- **motion.md §1.2 出场档位映射表**：新增一行例外「确认闪现 `--dur-1` 进 / `--dur-4` 出（唯一一处反向）」。
- **motion.md §2 表**：新增「设置项确认 ✓」一行。

## 10 · `will-change` 门禁

### 问题
motion §8 验收 #22 的 `grep -rn 'filter:\|backdrop-filter\|mix-blend-mode\|will-change' src/note/` 与 motion §3.2 的合法瞬时 `will-change` 用法冲突：门禁要么误杀正确写法，要么被人「把代码挪出 `src/note/`」绕过。

### 裁决

**门禁 #22 拆成三条，每条只查它能判定的东西；并且把扫描对象从「源码目录」换成「产物 chunk」。**

**#22a — CSS 层零容忍，用 stylelint 不用 grep**
```jsonc
// .stylelintrc.json
{ "rules": { "property-disallowed-list": [
    ["will-change", "backdrop-filter", "mix-blend-mode", "scrollbar-width", "scrollbar-color"],
    { "message": "红线 2：静止态零常驻 GPU 成本。will-change 只允许由 useTransientHint() 在运行时设置" }
]}}
```
作用域 = `packages/ui/src/styles/**` + `apps/**/*.css`。**为什么不用 grep**：grep 会命中注释、字符串、stylelint 配置自身和文档——这正是 sweep 第 37 条指出的「门禁 #10 会自我命中」的同一个病；stylelint 只在真正的**声明**上报错，零假阳性。

**#22b — JS 层只允许一个出口，白名单登记**
```bash
# scripts/ci/will-change.sh
ALLOW='packages/ui/src/hooks/useTransientHint.ts'
HITS=$(grep -rnE 'will-?[Cc]hange' --include='*.ts' --include='*.tsx' packages/ apps/ \
       | grep -v "^${ALLOW}:")
[ -z "$HITS" ] || { printf 'will-change 只允许经 useTransientHint()：\n%s\n' "$HITS"; exit 1; }
# filter / backdrop-filter / mix-blend-mode 在 JS 层零容忍（motion §3.6 已裁定删掉瞬时 filter，没有 helper）
grep -rnE '\.style\.(filter|backdropFilter|mixBlendMode)' --include='*.ts' --include='*.tsx' packages/ apps/ \
  && { echo '瞬时 filter 已被 motion §3.6 裁定删除，不存在合法用法'; exit 1; }
exit 0
```
`will-?[Cc]hange` 同时命中 `setProperty('will-change', …)` 与 `style.willChange`，两种写法一起堵死。

**#22c — 扫描产物而不是目录（这才是「挪走文件就能绕过」的真正解法）**
```bash
# 便笺入口的整条依赖图，而不是一个可以被 mv 的目录
grep -nE 'will-?[Cc]hange|backdrop-filter|mix-blend-mode' \
     dist/assets/note-*.js dist/assets/note-*.css \
  && { echo '便笺入口的产物里出现了红线 2 禁止的属性'; exit 1; }
```
把代码挪到 `src/shared/` 不会让它从 `note` chunk 里消失——只要 `note.html` 还 import 它，它就还在产物里。

**#22d — 运行时断言才是真门禁（静态检查降为辅助）**
```ts
// packages/ui/tests/visual/no-resident-hint.spec.ts —— 便笺窗静止 5s 后
const residual = await page.evaluate(() =>
  [...document.querySelectorAll('*')]
    .filter(el => getComputedStyle(el).willChange !== 'auto')
    .map(el => `${el.tagName}.${(el as HTMLElement).className}`));
expect(residual).toEqual([]);
```
静态检查只能证明「没人写」，运行时检查才能证明「**没人留**」。后者抓的是 motion §3.2 那套写法的真实失败模式：动画被打断 → `transitionend` 从不触发 → `will-change` 永久残留。这条与 frontend_stack §8.2 的 CDP `layerPainted == 0` 断言互补（一个查提层提示，一个查实际重绘）。

**helper 本身是门禁的另一半，必须一起交付**（没有它，#22b 的白名单是一句空话）：
```ts
// packages/ui/src/hooks/useTransientHint.ts —— 全 app 唯一允许写 will-change 的地方
const LIVE = new WeakMap<HTMLElement, number>();

/** 动画开始前 1 帧提示合成器，结束后无条件收回。
 *  三重收回：transitionend / animationend / transitioncancel / 硬超时，任一先到即收。 */
export function transientHint(
  el: HTMLElement,
  props: 'transform' | 'opacity' | 'transform, opacity',
  maxMs = 600,                                    // > --dur-5(360) 的安全上限
): () => void {
  const prev = LIVE.get(el);
  if (prev !== undefined) clearTimeout(prev);
  requestAnimationFrame(() => { el.style.willChange = props; });

  const clear = () => {
    const t = LIVE.get(el); if (t !== undefined) clearTimeout(t);
    LIVE.delete(el);
    el.style.willChange = '';                     // 空串=移除内联声明；写 'auto' 会留下一条声明
    el.removeEventListener('transitionend',    clear);
    el.removeEventListener('animationend',     clear);
    el.removeEventListener('transitioncancel', clear);
  };
  // transitioncancel 不是异常路径：motion §1.1 原则 5 明确要求动效可被打断，打断是常态
  el.addEventListener('transitionend',    clear, { once: true });
  el.addEventListener('animationend',     clear, { once: true });
  el.addEventListener('transitioncancel', clear, { once: true });
  LIVE.set(el, window.setTimeout(clear, maxMs));  // 元素被卸载 / 事件全部没来时的兜底
  return clear;
}
```

### 理由
sweep C3 已经指出方向（CSS 零容忍 + JS 白名单 helper），这里把它做成可执行的四条，并补上两处它没覆盖的：① **用 stylelint 替代 CSS 侧的 grep**，否则会重蹈门禁 #10 自我命中的覆辙；② **查产物而不是查目录**，这是「挪走文件绕过门禁」这个攻击面的唯一真正封堵；③ **运行时残留断言**，因为 `will-change` 的现实危害不是「有人写了」而是「有人没收回」，静态 grep 对此完全无能。

### 需要改动
- **motion.md §8 验收 #22**：整条替换为 #22a/b/c/d 四条。
- **motion.md §3.2**：`el.addEventListener('transitionend', …)` 的裸示例 → 改为「唯一入口 `transientHint()`」+ helper 全文；补 `transitioncancel` 与硬超时两条理由。
- **frontend_stack.md §9.1 门禁表**：#11 stylelint 的 `property-disallowed-list` 扩展为五项；新增 #17「JS 层 will-change 白名单」、#18「note 产物扫描」、#19「运行时无残留 will-change」。
- **frontend_stack.md §9.1 门禁 #10**：同步加 `--exclude-dir={node_modules,.stylelintrc*,docs}` 白名单（sweep 第 37 条的另一半）。
- **frontend_stack.md §10 目录**：`hooks/` 下新增 `useTransientHint.ts`。
- **design_system.md §8 红线 2**：「禁止常驻 … `will-change`」→「禁止常驻 …；`will-change` 仅允许经 `useTransientHint()` 在运行时设置并在动画结束/取消/超时三重收回」。

### 11(a) 暗色 `--c-text-3` `#8B8A81` → `#96958B`

#### 独立复算（WCAG 2.x 相对亮度公式，我自己跑的，非引用）

| 前景 | canvas `#131312` | surface-1 `#1A1A18` | surface-2 `#201F1D` | **surface-3 `#272623`** | overlay `#232220` | selected `#1E2233` |
|---|---:|---:|---:|---:|---:|---:|
| `#8B8A81`（现值） | 5.36 | **5.02** | 4.75 | **4.36 ✗** | 4.58 | 4.54 |
| **`#96958B`（新值）** | 6.17 | 5.78 | 5.47 | **5.02 ✓** | 5.28 | 5.23 |

**裁决：接受 `#96958B`，回写基准 §2.2 暗色块。** frontend_stack 报的三个数（surface-3 = 5.02、canvas = 6.17、overlay = 5.27）与我的独立复算**逐位吻合**，4.36 也复现了。

**但它给的理由里有一处事实错误，必须一并改掉**：frontend_stack §2.5 说「基准只标了它在 canvas 上的 5.02:1」——**5.02 不是 canvas 上的值，是 surface-1 上的**；`#8B8A81` on canvas 实测 **5.36**。基准 §2.2 的注释 `--c-text-3:#8B8A81; /* 5.02:1 */` 没写底面名，才是漏洞的真正根源（同一行的 `--c-text-2` 就明写了 `6.79:1 on surface-1`）。**所有对比度注释一律必须带底面名**，这条要写进 §2.1。

**我的复算额外抓到一处两份文档都漏掉的**：暗色的 `--c-hover:rgba(255,255,255,.045)` 与 `--c-active:rgba(255,255,255,.075)` 是**半透明白**，压在最亮的表面上会把底面进一步抬亮：

| 底面合成方式 | `--c-text-2 #A3A299` | `--c-text-3 #96958B` | `--c-text-1 #EDEDEA` |
|---|---:|---:|---:|
| `--c-active` over **canvas**（frontend_stack 现在的算法） | 6.00 | 5.11 | 13.13 |
| `--c-active` over **surface-3**（真实最坏情形） | **4.69** | **3.99** | 10.26 |

两处结论：
1. **`T3_BG` 白名单排除 hover/active 是必须的，不是保守**——`#96958B` 在 active@surface-3 上只有 **3.99**。frontend_stack 已经这么写了 ✓。
2. **`contrast.mjs` 的 `ratio(fg, bg, base)` 用 `base = c-canvas` 合成半透明底是错的。** 半透明底的最坏情形是压在**最亮**的表面上：暗色应取 `--c-surface-3`，亮色应取 `--c-overlay`(`#FFFFFF`)。不改这一处，`body-text` 对类里 `--c-text-2` on `c-active` 会被算成 6.00（余量充裕），而真实值是 **4.69**（余量 0.19）——门禁失去了它本该有的余量警报。

亮色侧我也复算了 frontend_stack 的第二个发现：`--c-text-3 #6E6E64` on `--c-active #E9E9E5` = **4.23**（吻合），`--c-text-2 #5C5C55` on 同底 = **5.53**（吻合）。**菜单快捷键改用 `--c-text-2` 的处置正确，接受**（sweep A6，screens §2.4 待改）。

### 11(b) 全局 4.5 门禁 → 按对类阈值门禁

**裁决：接受，但按下面的修正版落地。**

**理由（用我自己算出来的数说话）——字面执行「任何一对跌破 4.5:1 即 fail build」会把基准自己最扎实的一层判死：**

| 基准里合法且有意的值 | 实测 | 基准明写的依据 |
|---|---|---|
| `--c-text-disabled` 亮 / 暗 | 3.30 / 2.91 | §2.2「仅禁用态，不承载信息」 |
| 10 色 `dot / paper`（亮） | **3.50–3.94** | §2.3「满足图形元素 3:1」（WCAG 1.4.11 门槛就是 3） |

**也就是说，一条全局 4.5 会让四份文档里对比度最扎实的那一层产出 100+ 对失败。** 同时它还会**放过**真正该更严的地方：便笺 ink 的要求是 **≥10:1**（§7），实测 10.47–10.81，4.5 的门槛根本抓不住「某个色相的 ink 掉到 8:1」这种真实退化。所以按对类给阈值**不是放松，是同时收紧和放宽**：note-ink 从 4.5 收紧到 10，note-dot / focus-ring 从 4.5 放宽到 3（= WCAG 1.4.11 的正确门槛），disabled / borders / note-line 转为只报告。

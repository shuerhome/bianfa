### 6.1 组织模型：选型与三个被推翻的细节

| 维度 | 方案 1 个人空间+团队空间（Slack） | 方案 2 单层 team + 便笺级共享（Keep） | 方案 3 Org→Team→Notebook→Note（Notion） |
|---|---|---|---|
| "给同事看一眼"的步数 | 先移动便笺到团队空间 | 右键→共享，1 步 | 先选 Notebook |
| 归属边界（离职/计费/导出） | 清晰 | **无边界** | 清晰但过重 |
| 权限模型复杂度 | 低 | 中（每便笺一条 ACL） | 高（4 层继承+覆盖） |
| 首屏认知负担 | 需"切换空间" | 零 | 4 个概念 |
| 1-3 人团队实现成本 | ~2 周 | ~1.5 周 | 6 周+ |

**结论：Organization → Workspace → Note 三层，Team 作为"授权主体 + workspace 可见性范围"，不作为便笺容器。**

理由：纯方案 1 强制用户在写之前先决定归属，杀死"随手写"；纯方案 2 无法回答"离职便笺归谁""付几个席位""导出导哪些"，且无法在结构上保证管理员看不到私人便笺；方案 3 的 Notebook 对便笺是纯负担。

#### 初稿在此处的三个洞（本版已修）

**洞 1：团队 workspace 实际是 org 全员可见的。** 初稿的权限解析里，`org_members JOIN workspaces ON m.org_id = w.org_id` 意味着**任何 org 成员对 org 内每一个 team workspace 都拿到 `default_note_perm`**。`teams` 表存在但从不参与 workspace 可见性。结果：HR workspace 对全公司可读。修法是一列——`workspaces.team_id`（NULL = org 全员，非 NULL = 限该 team 成员）。

**洞 2：`permissions` 表是装饰品。** 初稿把角色→能力矩阵做成表，但 `effective_note_permission` 一次都没查它——note 级权限完全由 enum 顺序 + `max()` 决定。为"v2 自定义角色"预留一张永不被读的表，对 1-3 人团队是典型的推测性设计。**v1 删除该表**，org 级能力检查用代码里一个 `const` map（12 行），等 Business 版真要卖自定义角色时再引入（届时 better-auth 的 `organizationRole` 表已经现成）。

**洞 3：审计分区表提前了。** 每月分区 + pg_partman 是 10 亿行量级的工具。v1 单表 + `at` 上的 BRIN 索引即可，`DELETE ... WHERE at < now() - retention` 每周跑一次；等单表超 5000 万行再切分区（`pg_partman` 或 20 行 cron）。**但 append-only 的权限收紧要 day-1 就做**（见 6.7，已实测）。

#### 权限解析（`max(anyenum)` 已在 PG 16.13 实测：`max(viewer,editor,commenter)='editor'`；空集返回 NULL）

```sql
CREATE FUNCTION effective_note_permission(p_user uuid, p_note uuid)
RETURNS note_perm LANGUAGE sql STABLE AS $$
  SELECT max(perm) FROM (
    SELECT 'manager'::note_perm AS perm
      FROM notes n JOIN workspaces w ON w.id=n.workspace_id
     WHERE n.id=p_note AND (n.created_by=p_user OR w.owner_user_id=p_user)
    UNION ALL
    SELECT w.default_note_perm                      -- ★洞 1 修复：team_id 参与判定
      FROM notes n
      JOIN workspaces  w ON w.id=n.workspace_id AND w.kind='team'
      JOIN org_members m ON m.org_id=w.org_id AND m.user_id=p_user AND m.status='active'
     WHERE n.id=p_note
       AND (w.team_id IS NULL
            OR EXISTS (SELECT 1 FROM team_members tm
                        WHERE tm.team_id=w.team_id AND tm.user_id=p_user))
    UNION ALL
    SELECT s.permission FROM shares s
     WHERE s.note_id=p_note AND (s.expires_at IS NULL OR s.expires_at>now())
       AND ( (s.grantee_kind='user' AND s.grantee_user_id=p_user)
          OR (s.grantee_kind='team' AND s.grantee_team_id IN
              (SELECT team_id FROM team_members WHERE user_id=p_user))
          OR (s.grantee_kind='org'  AND EXISTS (SELECT 1 FROM org_members om
              WHERE om.org_id=s.grantee_org_id AND om.user_id=p_user AND om.status='active')))
  ) g;
$$;
```

#### RLS：一个会导致 500 的真实 bug，初稿写错了两处

```sql
ALTER TABLE notes ENABLE ROW LEVEL SECURITY;
ALTER TABLE notes FORCE ROW LEVEL SECURITY;
CREATE POLICY notes_select ON notes FOR SELECT USING (
  EXISTS (SELECT 1 FROM workspaces w WHERE w.id=notes.workspace_id
            AND w.owner_user_id = NULLIF(current_setting('app.user_id',true),'')::uuid)
  OR EXISTS (SELECT 1 FROM workspaces w JOIN org_members m ON m.org_id=w.org_id
            WHERE w.id=notes.workspace_id AND w.kind='team' AND m.status='active'
              AND m.user_id = NULLIF(current_setting('app.user_id',true),'')::uuid
              AND (w.team_id IS NULL OR EXISTS (SELECT 1 FROM team_members tm
                    WHERE tm.team_id=w.team_id AND tm.user_id=m.user_id)))
  OR EXISTS (SELECT 1 FROM shares s WHERE s.note_id=notes.id
              AND (s.expires_at IS NULL OR s.expires_at>now())
              AND (s.grantee_user_id = NULLIF(current_setting('app.user_id',true),'')::uuid
                OR s.grantee_team_id IN (SELECT team_id FROM team_members
                     WHERE user_id = NULLIF(current_setting('app.user_id',true),'')::uuid))));
```

**修正 1 —— `NULLIF(...,'')` 不是风格问题，是必需。** 初稿写的 `current_setting('app.user_id',true)::uuid` 在 PG 16.13 实测会抛错：

```
postgres=# SET app.user_id='x'; RESET app.user_id;
postgres=# SELECT current_setting('app.user_id', true)::uuid;
ERROR:  invalid input syntax for type uuid: ""
```

`missing_ok=true` 只在 GUC **从未被定义过**时返回 NULL；一旦本会话设置过再 `RESET`（或事务 `COMMIT` 后 `SET LOCAL` 失效），返回的是**空串**。而连接池上的连接必然是"设置过又释放"的状态——也就是说这个 bug 在开发机首次请求不复现，在生产第二次请求必现，表现为整条 SELECT 500。加 `NULLIF` 后实测返回 NULL，策略 fail-closed（返回零行）。

**修正 2 —— `server_reset_query = DISCARD ALL` 在 transaction 模式下是无效建议。** PgBouncer 官方 `doc/config.md` 原文："When transaction pooling is used, the `server_reset_query` is not used"，且 `server_reset_query_always` **默认 0**（"the `server_reset_query` will be run only in pools that are in sessions-pooling mode"）。所以初稿把它当作跨租户泄漏的防线是错的。真正的防线只有一条：**`SET LOCAL` 必须在显式事务块内**（`BEGIN; SET LOCAL app.user_id=...; ...; COMMIT;`）。`SET LOCAL` 在事务块外只会发一条 WARNING 然后静默无效——配合上面的 `NULLIF`，结果是查不到数据而不是越权，这是可接受的失败方向。把 `server_reset_query_always=1` 作为可选的第二道锁，代价是每次事务后丢失预备语句缓存。

**RLS 只作兜底，不作主路径。** 策略里不要调用 PL/pgSQL 函数：非 inline 的函数对规划器是不透明黑箱（固定代价估算），且 RLS 会把关系标记为 security barrier，非 LEAKPROOF 的谓词无法下推到策略之下。授权判定的主路径仍是应用层显式调用 `effective_note_permission`。

### 6.2 共享形态与"撤销"这个初稿漏掉的洞

| 形态 | 交互 | 实现 | 版本 |
|---|---|---|---|
| 共享给某人 | `⋯`→共享→邮箱→权限下拉 | `shares(grantee_kind='user')`；未注册则先发 invitation | v1.0 |
| 共享给 team / 全 org | 同面板"团队"tab | `grantee_kind='team'/'org'` | v1.0 |
| 共享收件箱 | 应用内列表，手动"贴到桌面" | `shares_inbox` 索引 + `note_pins` | v1.0 |
| 评论线程 | 便笺翻面 | `note_comments`，非 CRDT | v1.0 |
| @提及 | 编辑器 `@` | `@tiptap/extension-mention@3.31.2` | v1.0 |
| Presence 头像 | 便笺右上角 | Yjs awareness | v1.0 |
| 公开链接 | 开关+密码+有效期 | 见下 | v1.2 |
| 团队共享视图 | 网格 → 后续自由画布 | 见 6.5 | v1.0 / v1.2 |

**别人共享给你的便笺默认不会自动贴到桌面。** 进"共享给我"收件箱 + 一条通知，用户手动点"贴到桌面"才写 `note_pins` 并创建窗口。桌面是最私密的画布，未经同意往上贴东西等同弹窗广告。

**★初稿漏掉的洞：撤销共享不会踢掉已连接的会话。** Yjs WebSocket 房间在 `connect` 时鉴权一次，之后长连接常驻。撤销 `shares` 行、把人移出 team、把人移出 org——三种操作在初稿里都只改数据库，**已经连着的客户端会继续收发 CRDT update，直到它自己断线**。对一个把"共享/撤销"当卖点的产品这是硬伤。修法（不需要 Redis）：

```sql
-- 写事务末尾
SELECT pg_notify('authz_revoked',
  json_build_object('user_id',$1,'scope','note','id',$2)::text);
```

WS 网关进程 `LISTEN authz_revoked`，收到后遍历本进程内该 user 的 socket，对受影响房间发 `authz.revoked` 并关闭该房间订阅（不必断整条连接）。单机 VPS 部署下 LISTEN/NOTIFY 足够；多进程时每个进程各自 LISTEN 即可，NOTIFY 是广播语义。**同时**在网关内加一个 60 秒的定期重校验兜底，防止 NOTIFY 在连接抖动时丢失（NOTIFY 不持久，断开期间的通知会丢）。

**公开链接：做，v1.2，默认关闭。** 三道锁：`organizations.allow_public_links` 默认 `false` 需 owner 显式开启；强制 `permission='viewer'`（无 editor 选项）；`expires_at NOT NULL`，UI 默认 7 天最长 90 天。Token 用 32 字节 CSPRNG → base64url（43 字符），**只存 `sha256` 到 `token_hash`**；密码用 argon2id；响应头 `X-Robots-Tag: noindex, nofollow`；对 `/p/<token>` 端点按 IP 做 10 次/分钟限流，防 token 爆破与内容抓取。

**评论走普通表 + WebSocket 广播，不进 CRDT。** 评论是 append-only，塞进 Yjs 只会让文档单调膨胀且无法做已读标记。

*反方论证：桌面便笺必须离线可用，评论不进 CRDT 就等于离线不能评论。* —— 这个反驳成立，但结论不变，只需补一个比 CRDT 简单一个量级的机制：评论 id 由**客户端生成 UUIDv7**，离线时写入本地 SQLite `outbox` 表，联网后重放，服务端 `INSERT ... ON CONFLICT (id) DO NOTHING` 幂等。评论是 append-only 且不需要字符级合并，UUIDv7 的时间有序性直接给出稳定排序。用 CRDT 解决同样的问题要付出文档体积、GC、未读标记三份代价。

**Presence 用 Yjs awareness**（`yjs@13.6.32` + `y-protocols@1.0.7`，均为核实的当前 latest），复用第 4 章的 y-websocket 连接，零额外基建。便笺尺寸小，不做逐字符光标，只做右上角 2-3 个头像点 + tooltip。

**离职归属：**团队 workspace 的便笺 = 公司资产，成员移除后访问权由 workspace 成员关系自动决定，无需迁移；个人 workspace 的便笺 = 个人资产，**不随离职归公司**，给 30 天导出窗口。移除时的一次性事务：

```sql
UPDATE org_members SET status='removed', removed_at=now(),
       session_epoch = session_epoch + 1              -- 立即失效令牌，见 6.4
 WHERE org_id=$1 AND user_id=$2;
DELETE FROM shares s USING notes n, workspaces w
 WHERE s.note_id=n.id AND n.workspace_id=w.id AND w.org_id=$1
   AND s.grantee_kind='user' AND s.grantee_user_id=$2;
DELETE FROM team_members WHERE org_id=$1 AND user_id=$2;
SELECT pg_notify('authz_revoked', json_build_object('user_id',$2,'scope','org','id',$1)::text);
```

### 6.3 邀请与成员生命周期

#### 关于 better-auth：初稿的三条事实全部需要更正

从 `better-auth@1.7.2` 的**实际发行包源码**核实（`dist/plugins/organization/`）：

| 初稿说法 | 实际情况（1.7.2 源码） | 结论 |
|---|---|---|
| organization plugin 提供 6 张表 | ✅ `organization / member / invitation / team / teamMember / organizationRole` | 维持 |
| `invitationExpiresIn` 默认 48 小时 | ✅ `adapter.mjs`: `getDate(options?.invitationExpiresIn \|\| 3600 * 48, "sec")` | 维持 |
| `invitationLimit` = **单人**待处理邀请上限 100 | ❌ 是**单 org** 的 pending 邀请上限：`findPendingInvitations({ organizationId }).length >= invitationLimit`（默认 100） | **改正** |
| 用 `invitation.id` 当令牌 → 他人可代领 | ❌ `acceptInvitation` 已强制 `invitation.email.toLowerCase() !== session.user.email.toLowerCase()` → 403 | **改正** |
| 需手动开 `requireEmailVerificationOnInvitation` | ❌ 1.7.2 已自动推导：未自定义 `generateId`（即 id 为内建不透明 uuid）时不强制；一旦你换成可预测的 id 生成器，**自动**要求邮箱已验证 | **改正** |

补充核实：`membershipLimit` 默认 100（每 org 成员数），`organizationLimit` 默认 **unlimited**（`types.d.mts` 的 `@default unlimited`），`creatorRole` 默认 `"owner"`。

**修正后的结论：初稿把 better-auth 的邀请流程说成有越权漏洞，是错的**——收件人邮箱校验是硬性的。但**仍然建议 token 与 id 分离**，理由换成两条实际的：① `listInvitations` 会把 id 返回给 org 成员，id 出现在 URL、邮件、日志、Referer 里，属于可枚举的元数据泄漏（谁被邀请了、邀请了什么角色）；② 未注册用户点链接 → 注册 → 接受的三步流程里，用一次性 token 承载"预填邮箱"比用 id 更干净。

```ts
const token = base64url(crypto.randomBytes(32));            // 明文只进邮件
const token_hash = crypto.createHash('sha256').update(token).digest();
// 校验：WHERE token_hash=$1 AND status='pending' AND expires_at>now() FOR UPDATE
//       同事务内 UPDATE status='accepted' —— 单次使用由行锁保证
```

有效期 48 小时；同 org+email 的 pending 邀请由部分唯一索引保证唯一，重发 = `UPDATE` 换新 token 而非插新行；接受时强制校验登录邮箱 == 邀请邮箱；每 org 每小时最多发 50 封邀请（防把产品当群发邮件通道）。

**域名自动加入：v1 明确不做。** 初稿设计了 DNS TXT 验证 + 三档策略 + 公共域名黑名单——这是正确的设计，但它是**一整条子系统**（域名录入 UI、后台 DNS 轮询 job、验证态机、黑名单维护、加入审批流），对 1-3 人团队在 v1 就是过度设计，而收益仅仅是省掉几次邀请点击。**v1 只做邀请链接。** 若 v1.3 要做，必须连 DNS TXT 验证一起做——没有所有权验证的域名加入意味着任何人填 `gmail.com` 就能把全站 Gmail 用户拉进自己的 org，这是有先例的漏洞类别，不存在"先上线再补验证"的选项。

**SSO / SCIM：v1 不做。** 初稿给的理由是 WorkOS 的价格数字（本轮无法联网核实，见 6.8，不要引用）。**真实理由与价格无关**：SSO 的成本不在订阅费，而在每个企业客户一次的 IdP 联调（元数据交换、属性映射、断言调试）与 SCIM 的去激活语义（IdP 说"停用"时你的席位、shares、会话怎么处理），这是持续的人力支出，不是 1-3 人团队能承担的。替代方案：直接支持 **Google / Microsoft Entra 的 OIDC 登录**（标准 authorization code + PKCE，约 200 行），覆盖绝大多数"我们公司用 Google Workspace"的诉求。触发条件写进 roadmap：**首个 >200 席位客户出现时才评估**，在那之前谈到 SSO 一律走"企业版询价"。

**成员移除后的会话失效。** 软删除之外必须让令牌立刻失效，否则被移除者拿着未过期 access token 还能读一整个 TTL。做法：access token TTL 10 分钟，token 里带 `org_ver`，服务端比对 `org_members.session_epoch`，不匹配直接 401。**不要用初稿建议的 `xmin`**：`xmin` 是行的最后修改事务号，任何无关 UPDATE（改个 `seat_billable`、改个角色名）都会 bump 它，把全组人无谓登出；且它是 32 位、会绕回。用上面 DDL 里的显式 `session_epoch int`，只在 remove / suspend / 降级三种操作时 `+1`。

**席位计费。** Stripe per-seat：一个 subscription item，`quantity = count(org_members WHERE status='active' AND seat_billable)`。**硬闸在应用层**——加人时若 `active_seats >= seats_paid` 直接拒绝并弹升级卡片（先付费后占位）；Stripe 侧只跑**每日一次对账 job**，算出应有席位与远端 quantity 比对，不同才 `subscriptions.update({ proration_behavior: 'create_prorations' })`。这样即使 Stripe 侧限流或短暂不可用，也不影响加人这条关键路径。`stripe` npm 当前 latest 为 22.6.1。

**去重三条硬规则**（决定通知系统是有用还是被整体关掉）：① 永不通知 actor 自己；② 同 `group_key` 30 秒内只发一条，多条合并为"张三等 3 人评论了《周会纪要》"；③ 应用窗口在前台且该便笺可见时不发系统通知，只做便笺内高亮。

正文里的 `@` 在 CRDT 文档中，不能靠"insert 时触发"——服务端收到 Yjs update 后做 **debounce 5 秒**的 mention 集合 diff，只对新增的发通知。

#### 队列：pg-boss，附两个必踩的坑

用 **`pg-boss@12.30.0`**（核实为当前 latest），跑在同一个 Postgres 上，1-3 人团队不该为通知 fan-out 引入 Redis。两个从包源码核实出来的硬约束：

- **`package.json` 的 `engines` 是 `node >= 22.12.0`**。若第 2 章定的 Node 版本低于此，要么升 Node，要么退到 pg-boss 10.x 线（`maint-v10` tag 为 10.4.2）。
- **v10 之后队列必须先创建再发送**：`dist/manager.js` 里 `send()` 路径会 `throw new Error("Queue ${name} does not exist")`。启动时必须显式建队列，否则第一条通知就炸：

```ts
const boss = new PgBoss(process.env.DATABASE_URL!);
await boss.start();
for (const q of ['notify.fanout', 'notify.email', 'notes.expire', 'billing.reconcile'])
  await boss.createQueue(q);          // ★ v10+ 必需，幂等
await boss.work('notify.fanout', { batchSize: 20 }, handleFanout);
```

Rust 后端的对等方案：直接 `SELECT ... FOR UPDATE SKIP LOCKED`（约 80 行）。**不要用 crates.io 上的 `pgmq`**——当前索引里它只有 `0.34.0-alpha.x` 且 MSRV 声明为 1.94.0，不适合作为 v1 依赖。

管道：

```
domain event ─▶ notify.fanout ─▶ 解析收件人（排除 actor）
                 ▶ pref(kind) → quiet_hours → notif_group 30s 折叠

                 ├─ desktop ─▶ WS 推送 → 客户端 sendNotification；离线则标记 pending，上线补一条聚合
                 └─ email   ─▶ instant 立发 / digest 每日 09:00（用户本地时区）合并一封
```

### 6.5 团队差异化：一个被推翻的 P0

**反方论证："团队便笺墙是 P0"这个结论站不住。** 理由：① 用户原始需求只有"团队中可以共享便笺"，墙是我们加的；② 初稿说"它不是新数据模型，只是加三列坐标"——这低估了实现量。自由画布意味着拖拽、缩放、平移、多选、层叠、碰撞、视口虚拟化、坐标实时同步、以及"自由布局/按人分列/看板"三种视图切换。对 1-3 人团队这是 **4-6 周**，不是初稿暗示的几天；③ 初稿自己承认墙的全部差异化来自"从墙上撕一张贴到桌面"——**而这个动作在一个普通网格列表里同样成立**，它需要的是 `note_pins`（已在 6.1 补上），不是自由坐标。

**结论：部分推翻。**

- **v1.0 做「团队共享区」**：CSS Grid 卡片网格，按更新时间/创建人排序，无自由坐标、无拖拽、无看板。核心动作只有一个——**卡片右上角图钉 → 写 `note_pins` → 第 5 章的 always-on-top 桌面窗口，与共享区同一份实时同步**。这条把"团队协作"和"Windows 便笺的桌面体验"缝在一起，是 Google Keep / Notion 做不到的（它们没有桌面贴纸）。开发量 ~1 周，差异化 100% 保留。
- **v1.2 再上自由画布**，且只做自由拖拽单一视图。坐标用**独立的 board 级 Y.Doc**（每 workspace 一个），不要塞进便笺内容文档——否则每次拖拽都会广播内容文档的 update，把 CRDT 历史撑爆。`board_z` 不要用"当前最大值 +1"（并发拖拽必然撞号），用 **fractional index**（字符串，两个相邻 key 之间总能插入新 key），冲突时 Yjs 的 LWW 自动收敛。
- **按人分列 / 看板视图：不做。** 一旦做看板就会被拿去和 Trello / Linear 比。

**便笺过期与自动归档（v1.0，P0，与共享区同批上线）。** 共享区最大的失败模式是三个月后变成垃圾场然后没人再打开——TTL 不是锦上添花，是共享区能用的前提。便笺可设 `expires_at`（今天/本周/两周/永久），到期前 24 小时给创建者 `note.expiring` 通知（"续期/归档"两个按钮），到期后归档：从共享区移除但可搜索。

```sql
-- pg-boss schedule: 每小时
UPDATE notes SET archived_at = now()
 WHERE expires_at < now() AND archived_at IS NULL
 RETURNING id, created_by, workspace_id;
```

**值班交接便笺 Handoff（v1.1，不进 v1.0）。** 它确实是唯一能把便笺卖出企业价的垂直场景（NOC、客服排班、医护交接班现在用的是"共享文档 + 微信群"），但它是**赌一个目标客户画像**。在拿到第一个明确说"我们要这个"的用户之前，把 3 天开发量投进去是投机。放 v1.1，并在 v1.0 就把埋点做好（观察是否有团队把某张便笺当"当值台账"反复覆写）。真做时表结构极轻：

```sql
CREATE TABLE handoffs (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  org_id uuid NOT NULL, team_id uuid NOT NULL REFERENCES teams(id),
  note_id uuid NOT NULL REFERENCES notes(id),      -- 当值便笺，固定一张，内容滚动
  shift_label text NOT NULL,                       -- '夜班 22:00-08:00'
  from_user_id uuid, to_user_id uuid,
  due_at timestamptz NOT NULL,
  acknowledged_at timestamptz,
  snapshot jsonb NOT NULL DEFAULT '{}'             -- 交接瞬间快照，只读存档
);
CREATE INDEX ON handoffs (team_id, due_at) WHERE acknowledged_at IS NULL;
```

产品动作三个：到点推通知给接班人 → 接班人点"已接收" → 系统对便笺打快照存档。未确认则 15 分钟后升级给 team lead——用 `boss.send('handoff.escalate', {...}, { startAfter: 900 })` 排一个延迟作业，接班时 `boss.cancel(jobId)`，不要用轮询扫表。

**不做：** 共享待办（打不过 Todoist / Linear，做浅了稀释定位）；模板库（价值依赖用户量，成本低随时可加，v1.3 再说）。

### 6.6 审计与隐私边界

#### append-only 审计（v1 单表，已在 PG 16.13 实测权限行为）

```sql
CREATE TABLE audit_log (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  org_id uuid NOT NULL,
  actor_id uuid, actor_ip inet, actor_ua text,
  action text NOT NULL,     -- note.viewed note.updated share.created share.revoked
                            -- member.invited member.removed role.changed export.requested
                            -- publiclink.created
  target_type text NOT NULL, target_id uuid,
  before jsonb, after jsonb,
  at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON audit_log USING brin (at);
CREATE INDEX ON audit_log (org_id, at DESC);

GRANT INSERT, SELECT ON audit_log TO app_user;
REVOKE UPDATE, DELETE ON audit_log FROM app_user;
```

实测确认（PG 16.13，`app_user` 非 superuser、非表 owner）：`INSERT` 成功，`UPDATE audit_log` / `DELETE FROM audit_log` 均报 `permission denied for table audit_log`。**日后切分区时有一个反直觉点必须知道**：`has_table_privilege('app_user','audit_log_2026_09','INSERT')` 返回 `f`，但通过父表 INSERT 依然成功——分区路由不检查分区自身的权限。所以父表授权是对的，但**直接对分区做 UPDATE 也被拒**（实测报 `permission denied for table audit_log_2026_09`），append-only 保证在分区化之后依然成立。

**`note.viewed` 必须窗口去重**：同 `(actor, note)` 30 分钟内只记一条，用进程内 LRU + TTL 判重（不需要 Redis）。否则打开一次共享区就产生几十条 view 事件，日志量比业务数据大一个数量级。写与分享类事件全量记录，不去重。

**数据导出**：异步 job → `notes.json`（结构化，含 shares/comments 引用）+ `notes/*.md`（人可读）+ 附件目录 → 对象存储 → **24 小时有效的预签名 URL** 邮件送达。owner 可导出整个 org 的 team workspace；**任何角色都无法导出他人的个人 workspace**。

#### 管理员能不能看成员的私人便笺

**不能，而且做成技术上不可能而非策略上禁止。** 三层保证：

1. **结构层**：个人 workspace 的 `org_id` 恒为 NULL（`ws_shape` CHECK 强制）。所有管理端 API 查询以 `org_id = $1` 起手，管理员没有到达个人 workspace 的路径。策略文件会被绕过，外键不会。
2. **接口层**：不提供任何 admin impersonate 端点。成员详情页只暴露：加入时间、角色、最后活跃时间、在**团队** workspace 内的活动统计。看不到便笺标题、条数、任何内容。
3. **产品层**：用户首次在个人 workspace 建便笺时一次性提示"这里的内容团队管理员看不到"，并写进官网与隐私政策。

**团队 workspace 则相反：admin/owner 可读**（公司资产，公司为其付费），但每次读写一条 `audit_log`，且**被读者本人能在便笺的"谁看过"里看到管理员的名字**。允许访问，但不允许偷偷访问。

**反方论证：这个隐私承诺会挡住企业采购。** 反方的两点都成立：① 企业买方的合规清单里常有"雇主可导出员工在企业账号内产生的全部数据"这一条，我们的结构使之不可能，可能直接导致采购否决；② 更实际的问题——个人 workspace 与 org 完全解耦，意味着**org 无法停用一个用户的账号，只能停用他在该 org 的席位**。用公司邮箱注册的员工离职后账号依然存在。

**结论：维持结构隔离，但补两条。** 其一，明确身份分层写进产品文档：**账号是个人的，席位是公司的**；org 的 remove 操作影响的是席位、team 成员关系、shares 与会话，不影响账号本身。其二，在 org 设置里提供一个 **`enterprise_mode` 开关**：开启后，该 org 的成员在客户端内**不显示个人 workspace 入口**（客户端仍可用于其他 org / 个人用途，只是这个 org 的上下文里不提供），从而满足"本 org 内一切内容皆公司资产"的采购要求。把选择权交给买方，而不是我们替所有人决定——同时保持默认值是隐私优先。这样反方的合规诉求被满足，而默认安全没有被牺牲。

**离职取证**：v1 不做 break-glass。成员移除时给 30 天导出窗口；团队便笺本来就归公司，不需要取证。v2（Business 版）再加：owner + 另一名 admin 双人批准，7 天倒计时期间当事人收到邮件并可申诉，到期后授予 72 小时只读窗口，全程 `breakglass.*` 审计不可删。

**法律依据**：GDPR 下雇主处理员工个人数据需要合法基础（履行合同、合法利益或法律义务）并受比例原则约束。员工在个人空间写的内容不属于"履行劳动合同所必需"。把"管理员不可读"做成默认值，等于把合规做成默认安全。

### 6.7 隔离测试（不是可选项）

个人/团队 workspace 的边界一旦在任何一个管理端接口上被打破——哪怕只是一个统计端点漏了 `org_id` 过滤——整个隐私承诺失效且不可挽回。必须有一个**枚举式**集成测试，而不是逐接口手写断言：

```ts
// 以 admin 身份遍历所有已注册的管理端路由，断言响应体中不出现任何 personal workspace 的 id
test.each(listAllAdminRoutes())('admin route %s leaks no personal workspace', async (route) => {
  const res = await callAs(adminToken, route, sampleParams(route));
  const ids = collectUuids(res.body);
  expect(ids).not.toContain(victimPersonalWorkspaceId);
  expect(ids).not.toContain(victimPersonalNoteId);
});
```

关键在 `listAllAdminRoutes()` 从路由表反射生成——新增接口自动进入测试范围，忘了写测试也拦得住。

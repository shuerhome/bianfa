### 5.0 前置产品决策：先能用，再登录

这一条排在选型之前，因为它决定 `user` 表的形状，改起来最贵。

我们替代的是 Windows 便笺——它的第一体验是**双击图标，光标已经在便笺里闪**。任何"先注册后使用"的流程都会在第一屏流失掉大部分用户。

**决策：首启动不登录，本地即用。**

- 首启动生成本地 `local_user_id`（UUID v7）+ 本地 SQLite，所有便笺归属于它，**不联网也不建云账号**。
- 顶栏一个非阻断的"登录以在多设备同步"入口。
- 登录成功后执行一次 **claim 迁移**：把本地 note 的 owner 从 `local_user_id` 改写为云端 `user.id`，作为一批 CRDT 初始操作推上去。迁移必须幂等（用 `local_user_id` 做一次性 claim 标记），因为用户可能中途断网。
- 服务端 `user` 表**不需要**允许 `email` 为空——本地用户根本不在服务端存在。这避开了"匿名账号占满 user 表""匿名账号如何合并""匿名账号的 GDPR 删除路径"三重复杂度。

> 这条把初稿 open_questions 里的"是否要匿名/本地模式"升级为已决事项：**必须做，且做法是纯客户端本地身份，不是服务端匿名账号**。

### 5.1 选型：Better Auth 自托管

#### 5.1.1 横向对比

| 方案 | 形态 | 计费结构 | 自托管 | Org/RBAC | 结论 |
|---|---|---|---|---|---|
| **Better Auth 1.7.2** ✅ | TS 库，跑在自己的 Node/Bun 进程 | 库本身 MIT 免费、**无 MAU 计费** | 极低 | `organization` 插件：`organization`/`member`/`invitation` 三张核心表；开 teams 加 `team`/`teamMember`；开动态角色加 `organizationRole`；`session` 扩展出 `activeOrganizationId`/`activeTeamId` | **选它** |
| Auth.js / NextAuth v5 | TS 库 | 免费 | 低 | 无组织概念 | ❌ `next-auth@beta` 仍停在 **5.0.0-beta.32**，`latest` tag 还是 v4.24.15 |
| Lucia | TS 库 | — | — | — | ❌ npm 上 `lucia@3.2.2` **已带 deprecated 标记**，指向迁移指南 |
| Supabase Auth | 托管/可自托管 | 按 MAU（待核实） | 中（GoTrue + Docker 栈） | 无原生 org | ❌ 绑定 Supabase 的 Postgres/RLS 范式，与 Hostinger VPS 自管冲突 |
| Clerk | 纯托管 | 按 MAU + B2B organizations 为独立附加包（待核实） | 不能 | 最好用 | ❌ 便笺是高频低 ARPU，MAU 曲线远陡于收入曲线；且不可自托管 |
| WorkOS AuthKit | 纯托管 | 免费额度大，企业 SSO 按连接计费（待核实） | 不能 | 好 | ⚠️ 留作未来单接企业 SSO，不做主账号体系 |
| Keycloak | 自托管 JVM | 免费 | **高**：生产常驻 1–2 GB RAM | 有，但 Group/Role 与 workspace 语义对不上 | ❌ 一台 VPS 还要跑 Postgres + API + 同步服务 |
| Zitadel / Logto | 自托管 Go/TS | 免费 | 中 | 原生多租户 | ⚠️ 技术上"对"，但独立 IdP = 多一套用户表 + 多一次 token 交换 + 多一个升级面 |

#### 5.1.2 结论与两条硬理由

1. **用户表就是我们自己的表**。同步引擎要在同一个事务里读 `member.role` 和写 `note` 的 CRDT 版本。独立 IdP 会把这变成跨服务一致性问题。Better Auth 直接建表在我们的 Postgres 里，可以 JOIN。
2. **零 MAU 风险**。免费/低价便笺的 MAU 增长与收入脱钩，任何按 MAU 计费的托管方案都是把增长变成负债。

**未来的企业 SSO**：不要自己写 SAML，用 `@better-auth/sso`（同为 1.7.2）或把该租户单独接到 WorkOS 并让客户买单。可插拔，不影响当前架构。

#### 5.1.3 1.7 的破坏性变更清单（升级必读）

初稿只笼统说"1.x 有过破坏性变更"。核实后的具体清单如下，其中第 4 条会直接影响我们的 VPS 部署：

| 变更 | 影响 |
|---|---|
| `Account.accountId` → `Account.providerAccountId`，唯一键改为 `(issuer, providerAccountId)` | 已有 OAuth 身份需迁移 |
| `verifyAccessToken` → `verifyBearerToken`，旧方法拒绝 DPoP 绑定的 token | API 层改名 |
| 通用 OAuth 重写为一等 provider，`signIn.oauth2()` → `signIn.social()` | 客户端调用改名 |
| **`advanced.trustedProxyHeaders: true` 不开启时，动态 `baseURL` 会忽略 `x-forwarded-host` / `x-forwarded-proto`** | **我们在 Hostinger VPS 上必然走 Nginx/Caddy 反代，不开这个开关会导致回调 URL 生成为 `http://127.0.0.1:3000`，OAuth 全线失败** |
| `oidcProvider` 插件已移除 → `@better-auth/oauth-provider` | 按新包写 |
| MCP 插件迁出为 `@better-auth/mcp`，依赖 JWT 插件 | 暂不用 |
| ID token 增加 `at_hash`；access token 所绑 session 结束后 introspection 返回 `{active:false}`；新增 back-channel logout | 远程登出可做到近实时（见 5.2.6） |

> 初稿声称"1.7 改了 multi-session 的 set-active/revoke 语义"——**本轮在 changelog 中未找到该条目，已删除**。不要在文档里保留无法核实的确定性陈述。

### 5.2 桌面客户端登录流程

#### 5.2.1 反驳一：第一方桌面 App 根本不需要 OAuth，为什么还上 oauth-provider？

**反方立场（值得认真对待）**：OAuth 2.1 是给**第三方**应用做委托授权的协议。我们的桌面端是第一方，用户已经信任它。上 `@better-auth/oauth-provider` 等于自己运营一个授权服务器——要管 client 注册、consent 页、DCR、SSRF 面、`at_hash`、back-channel logout。更省事的做法是：系统浏览器打开我们自己的 Web 登录页，登录成功后页面调一个 `/desktop/handoff` 端点签发一次性 code，302 回 loopback，桌面端拿 code 换 token。少一整个协议栈。

**我的判断：维持 oauth-provider，但收缩配置面。** 反方不成立的原因是——所谓"省事的 handoff"里要自己实现的东西，恰好是最容易写错的那几样：一次性 code 的原子消费、PKCE 绑定、redirect_uri 校验、loopback 端口语义。而 oauth-provider 的 loopback 校验刚在 2026-04-17 合入的 PR #9226 里被专门加固过（见下）。自己写不会更少代码，只会更少测试。

但反方指出的风险是真的，缓解措施必须写死在配置里：

```ts
oAuthProvider({
  allowDynamicClientRegistration: false,          // 关闭 RFC 7591 DCR
  allowUnauthenticatedClientRegistration: false,  // 绝不开放公网注册
})
```
客户只通过 `auth.api.adminCreateOAuthClient()` 在部署脚本里创建，全系统只有一个 client：`bianfa-desktop`，`token_endpoint_auth_method: "none"`（public client，无 secret，PKCE 不可关闭）。

#### 5.2.2 回调方式：loopback 为主

| 维度 | Loopback `http://127.0.0.1:{随机端口}` | 自定义 scheme `bianfa://` | Device Grant (RFC 8628) |
|---|---|---|---|
| 劫持风险 | 仅同机进程可探测 | **高**：多 App 可注册同一 scheme | 无回调可劫持 |
| 用户体验 | 授权后自动回 App | 系统弹"是否允许打开 bianfa？" | 需手输 8 位 user_code |
| 失败场景 | 端口被占（换端口重试） | 卸载残留注册项导致回调打不开 | 无 |
| 结论 | ✅ **主路径** | ⚠️ 仅 Mac App Store 沙盒版兜底 | ✅ **降级路径** |

**已核实的关键细节（初稿此处有错，且错得会致命）**：

- Better Auth oauth-provider 对 native client 允许 `http` loopback 到 `localhost` / `127.0.0.1` / `[::1]` 并**接受任意端口**。
- 但 PR #9226（标题实为 *"fix: unify host classification and close SSRF gaps across packages"*，2026-04-17 合入 main）的实现是：**端口弹性只适用于 IP 字面量**；DNS 名 `localhost` 按 RFC 8252 §8.3 仍走**精确字符串匹配**。
- **因此：注册的 redirect_uri 必须是 `http://127.0.0.1/cb`，绝不能写 `http://localhost/cb`。** 写成后者，随机端口方案会静默失效。初稿没有区分这两者。
- 该修复早于 1.7.2 发布，**锁定 `1.7.2` 即已包含**。初稿"若版本未合入就退化到 51900–51920 共 21 个固定端口轮询"的兜底可以删掉；改为在 CI 里加一条集成测试：起一个随机端口的 loopback，跑完整 authorize→token，断言成功。

#### 5.2.3 登录时序

```mermaid
sequenceDiagram
    participant D as 桌面端(Tauri/Rust)
    participant B as 系统默认浏览器
    participant A as api.bianfa.app (Better Auth)
    participant K as OS Keychain
    D->>D: verifier=random(64B); challenge=S256(verifier)<br/>state=random(32B); 起 loopback 127.0.0.1:0
    D->>B: open /oauth2/authorize?client_id=bianfa-desktop<br/>&redirect_uri=http://127.0.0.1:{port}/cb<br/>&code_challenge={challenge}&code_challenge_method=S256&state={state}
    B->>A: 用户选 Google/Apple/邮箱 (+ 可选 TOTP/passkey)
    A-->>B: 302 → http://127.0.0.1:{port}/cb?code=..&state=..
    B->>D: loopback 收到 code；校验 state；返回"可关闭本页"HTML
    D->>D: 立刻 shutdown loopback
    D->>A: POST /oauth2/token (code + verifier + device_name + device_id)
    A-->>D: access_token + refresh_token + id_token
    D->>K: 只把 refresh_token 写进 Keychain；access 只留内存
```

**loopback server 用什么写？** 初稿在这里和稀泥（"用 `tauri-plugin-oauth` 或手写 `tiny_http` 都行"）。核实结论：**`tauri-plugin-oauth` 的 README 自述为 WIP，无 API 文档、无版本承诺**。不要把登录这条命脉压在一个 WIP 插件上。

**决策：手写。** 约 40 行，用 `tiny_http`（或 `hyper`）：绑 `127.0.0.1:0` 取系统分配端口 → 只接受一次请求 → 校验 `state` → 返回 200 HTML → 立即 `drop(server)`。同时设 60 秒超时，超时后关闭端口并提示用户改用验证码登录。

#### 5.2.4 降级路径：Device Authorization Grant

`deviceAuthorization` 插件常驻开启，作为"浏览器打不开？用验证码登录"的入口。核实到的实际端点与默认值：

| 项 | 值 |
|---|---|
| 端点 | `POST /device/code`、`POST /device/token`、`GET /device`、`POST /device/approve`、`POST /device/deny` |
| `expiresIn` | 默认 `"30m"` |
| `interval`（最小轮询间隔） | 默认 `"5s"` |
| `userCodeLength` | 默认 `8` |
| `deviceCodeLength` | 默认 `40` |

配 `validateClient` 只放行 `bianfa-desktop`，`onDeviceAuthRequest` 里记审计。

#### 5.2.5 第三方登录矩阵

| Provider | 优先级 | 必须知道的坑 |
|---|---|---|
| Google | P0 | 必须走系统浏览器；嵌入式 webview 会被拒（`disallowed_useragent`）——**该策略本轮未能联网复核，但方向不变：无论如何都不要把 OAuth 页塞进 Tauri webview** |
| Apple | P0（macOS 上架前） | **client secret 是我们自己用 .p8 私钥签的 JWT，最长有效期 15,777,000 秒（六个月）**。这意味着**必须有一个轮换定时任务**——初稿完全没提，是会在上线半年后炸掉登录的定时炸弹。多平台时用 `clientId: string[]` 或 `audience: string[]` 同时容纳 Service ID 与 bundle ID；原生端不传 `appBundleIdentifier` 会报 `JWTClaimValidationFailed: unexpected 'aud' claim value` |
| Microsoft | P1 | `tenant: "common"` 同吃个人号与企业租户 |
| GitHub | P1 | 开发者用户获取成本最低 |
| 手机号 / 微信 | P2，单独立项 | 国内版牵出 ICP 备案（须购中国内地服务器，与 Hostinger VPS 冲突）+ 短信通道 + 微信开放平台企业主体三重依赖。**具体备案要求与短信单价本轮未核实**。建议先做海外版，不要现在污染架构 |

> **初稿漏掉的硬依赖：发信通道。** 邮箱验证、找回密码、邀请、安全告警全都依赖发信。**从 Hostinger VPS 自建 SMTP 发信基本必进垃圾箱**（IP 信誉 + SPF/DKIM/DMARC + 反向解析）。必须用 Resend / Postmark / SES 之类的托管发信，并在 M1 就接通——否则整个账号体系是个空壳。

#### 5.2.6 Token 策略与"离线不掉线"

```
access_token   短 TTL（15 min），不落盘，仅内存
refresh_token  不透明随机 32 字节 → base64url 43 字符，每设备一条
               带 family_id，轮转 + 复用检测
```

**离线优先应用的三条铁律：**

1. **本地库的加解密密钥与 token 完全无关**。本地 SQLite 的密钥单独生成、单独存 Keychain。token 过期只影响 `/sync` 通道，**不影响本地读写、搜索、编辑、置顶**。任何"token 没了就锁本地数据"的实现都是产品事故。
2. **区分两类失败**：`401 + WWW-Authenticate: invalid_token` → access 过期，静默换新；`400 invalid_grant` → refresh 失效，进入 `SYNC_PAUSED_NEEDS_AUTH` 状态：托盘角标 + 顶栏一条不打断的提示，本地照常全功能，变更继续累积在 `outbox` 表，重新登录后按 CRDT 合并。**绝不弹模态框、绝不清空本地。**
3. **"远程登出"与"远程抹除"是两件事**。前者只撤 token，本地数据一个字节都不动；后者是独立开关、独立二次确认。把两者合并实现 = 用户在另一台设备点了"登出"，本机未同步的便笺永久丢失。

**集成注意（初稿在此有结构性缺口）**：oauth-provider 自带 token 表与生命周期管理。**不要先设计一张自建 `refresh_token` 表，再去和插件打架**。落地顺序是：先实测 oauth-provider 是否内置 refresh rotation 与复用检测；若内置，我们只加一张 `device` 表并在其 hook 里挂 `family` 语义；若不内置，才自建下表。

```sql
CREATE TABLE device (
  id            uuid PRIMARY KEY,               -- 客户端生成 UUIDv7
  user_id       text NOT NULL REFERENCES "user"(id) ON DELETE CASCADE,
  name          text NOT NULL,                  -- "William 的 MacBook Pro"
  platform      text NOT NULL,                  -- windows | macos | linux
  app_version   text NOT NULL,
  last_ip       inet, last_seen_at timestamptz NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  revoked_at    timestamptz
);
```

**并发陷阱**：桌面端多个请求同时撞 401 会并发调 refresh，第二个必被判"复用"从而撤销整个 family，用户被莫名登出。客户端必须用 **single-flight 互斥锁**包住 refresh；服务端给 **30 秒宽限窗口**——`rotated` 状态的 token 在 30 秒内被再次使用时返回其子 token，而不是撤销 family。

**近实时踢下线**：1.7 起，access token 所绑 session 结束后 introspection 返回 `{active:false}`。配合同步 WebSocket 下发 `session.revoked`，被踢设备可以秒级掉线，而不必等满 15 分钟的 access TTL。

#### 5.2.7 桌面端 token 存储

**结论：用 Rust `keyring` crate。核实到的最新版是 4.2.0（2026-08-29 发布）——初稿写的 "v3.x" 已过时。** v4 的 `default = ["v1"]` feature 一次性带上三个平台后端（`apple-native-keyring-store/keychain`、`windows-native-keyring-store`、`zbus-secret-service-keyring-store`），不需要再手工拼 feature flag。

**关于 Tauri Stronghold**：初稿断言"官方已不推荐、将在 Tauri v3 移除"——**本轮在其官方 README 中未找到任何弃用声明，该断言无法核实，已删除**。不排除它仍然是错的选择，但理由要站得住：Stronghold 需要一个解锁口令，而我们是一个开机自启、后台静默同步的应用——问用户要口令是体验灾难，把口令存别处则是问题原地打转。`keyring` 直接复用 OS 已经为用户解锁的凭据库，语义正确。

| 平台 | 后端 | 落点 |
|---|---|---|
| Windows | DPAPI + Credential Manager | Generic Credential |
| macOS | Security.framework | login.keychain generic password |
| Linux | Secret Service (libsecret / zbus) | 无 keyring 的 headless 环境降级到 age 加密文件 + 显式警告 |

```
service="app.bianfa.desktop"
  account="refresh_token"   -> "rt_<43字符>"     # 不透明随机，非 JWT
  account="device_id"       -> UUID v7
  account="db_key"          -> 32B 随机（SQLCipher 用）
```

**Windows blob 大小限制**：`wincred.h` 中 `CRED_MAX_CREDENTIAL_BLOB_SIZE` 定义为 `5 * 512 = 2560` 字节——**该数值本轮未能联网复核（微软文档站被出口策略拦截）**。但结论不依赖精确数值：**refresh token 必须是不透明随机串而非 JWT**，因为 JWT 携带 claim 后长度不可控，且在 Windows 上会**静默失败**而 macOS 不会暴露问题。CI 里加一条断言：写入 Keychain 的任何值长度 < 2048 字节。

绝不写 `~/.bianfa/auth.json`。开发期 mock 用 `BIANFA_DEV_TOKEN` 环境变量，且 release build 里用 `#[cfg(debug_assertions)]` 编译掉。

**macOS 签名陷阱**：Keychain item 的 ACL 绑定 App 签名。换开发者证书后旧 item 读不出来，表现为"更新后所有 macOS 用户被登出"。读失败必须优雅降级到重新登录，而不是崩溃。

#### 5.2.8 MFA：TOTP 走应用内，passkey 走系统浏览器

Tauri 没有可靠的跨平台 webview WebAuthn 能力；passkey 插件的配置本身也证明它是**浏览器 origin 绑定**的（需要 `rpID` / `rpName` / `origin`，并依赖一个 `webAuthnChallengeCookie`）。

- **TOTP（P0）**：`twoFactor` 插件，桌面端原生 UI 输 6 位码，走普通 HTTP，零 webview 依赖。插件的 `twoFactor` 表**自带 `failedVerificationCount` 与 `lockedUntil`**——不要再手写一套锁定逻辑。
- **Passkey（P1）**：注册与验证都发生在 5.2.3 那个系统浏览器页面里，桌面端什么都不用做。
- **恢复码**：默认生成 10 个、每个 10 字符。**关键：`storeBackupCodes` 的默认值是明文入库。** 初稿写的"argon2id 哈希后入库"既不是插件行为、也做不到（用过的码需要被定位并移除）。**必须显式配置 `storeBackupCodes: "encrypted"`**，并在部署检查清单里列为一条硬项。

### 5.3 授权模型

#### 5.3.1 RBAC + 一张例外表，不上 ReBAC

便笺的共享语义只有两跳：`workspace → notebook → note`。跑 OpenFGA/SpiceDB 意味着多一个 gRPC 服务、多一套 schema DSL、多一份需与主库保持一致的 tuple 存储——对 1–3 人团队是纯负债。

**选 RBAC + 一张 `resource_grant` 例外表**。角色覆盖 90% 的粗粒度权限，`resource_grant` 处理"把这一本笔记本单独分享给某人"的 10%。迁移信号：出现三跳继承，或需要"列出 X 能访问的所有资源"且无法走索引——届时 grant 表可直接映射成 tuple。

#### 5.3.2 反驳二：五个角色是过度设计

**反方立场**：初稿定义了 owner/admin/member/guest/viewer 五个角色 + 一张 grant 表 + 一个三层中间件。对一个还没有第一个付费团队的 1–3 人项目，这是在为想象中的客户写代码。Better Auth 内置的 owner/admin/member 三个角色已经能覆盖"我和我同事共享一个笔记本"的全部场景。

**我接受这个反驳，推翻初稿的第一版范围。**

- **M2 只上 owner / admin / member 三个内置角色**，配 `createAccessControl` 声明我们自己的 `notebook` / `note` / `attachment` / `ai` / `billing` 资源。
- `guest` / `viewer` 与 `resource_grant` 表**推迟到有真实外部协作需求时再加**。但 `authz` 中间件的第 3b 分支（查 grant）留出接口——加角色时不用改中间件结构。
- `dynamicAccessControl` **第一版关闭**。它允许运行时创建自定义角色，开放给 owner 就等于开放了"用户自己造一个能改计费的角色"的提权面。

| | workspace 设置 | 邀请成员 | 计费 | notebook 增删 | note 编辑 | note 硬删 | AI 调用 | AI provider key |
|---|---|---|---|---|---|---|---|---|
| **owner** | ✅ | ✅ | ✅ 管理 | ✅ | ✅ | ✅ | ✅ | ✅ |
| **admin** | ✅ 除删除/转让 | ✅ | 只读 | ✅ | ✅ | ✅ | ✅ | ✅ |
| **member** | ❌ | ❌ | ❌ | ✅ 建，仅删自建 | ✅ | ❌（仅软删） | ✅ | ❌ |

#### 5.3.3 反驳三：一律返回 404 是安全剧场

**反方立场**：初稿要求"任何一层鉴权失败都返回 404 而非 403"。这会把调试成本转嫁给自己，更糟的是——**对一个便笺应用，让用户看到"笔记不存在"而不是"你没有权限"，用户的第一反应是数据丢了**。这是产品级误导。

**我部分推翻初稿，改为分场景：**

| 场景 | 返回 |
|---|---|
| 资源属于**别的 organization**（跨租户） | `404 not_found` —— 资源存在性确实是秘密 |
| 资源在**同一 organization** 内，但角色权限不足 | `403 forbidden` + 明确 error code（如 `insufficient_role`），UI 显示"需要 admin 权限" |
| 未认证 | `401` |

同 org 内的资源存在性对成员不是秘密，藏起来只制造困惑。

```ts
export const authz = (need: { resource: string; action: string; idParam?: string }) =>
  async (c, next) => {
    const session = await auth.api.getSession({ headers: c.req.raw.headers });
    if (!session || session.user.banned) return c.json({ error: "unauthorized" }, 401);

    const orgId = c.req.header("x-organization-id") ?? session.session.activeOrganizationId;
    if (!orgId) return c.json({ error: "no_active_organization" }, 400);

    const member = await cache.wrap(`m:${session.user.id}:${orgId}`, 30, () =>
      db.member.findFirst({ where: { userId: session.user.id, organizationId: orgId } }));
    if (!member) return c.json({ error: "not_found" }, 404);   // 跨租户 → 404

    const ok = roles[member.role]?.authorize({ [need.resource]: [need.action] }).success;
    if (!ok) {
      audit(c, "authz.denied", { orgId, ...need });
      return c.json({ error: "insufficient_role", required: need }, 403);  // 同 org → 403
    }
    c.set("auth", { userId: session.user.id, orgId, role: member.role });
    await next();
  };
```

> **桌面端 Bearer 与 Web 端 cookie 的统一**：`auth.api.getSession()` 默认读 cookie。要让它同时接受 `Authorization: Bearer`，需要启用 `bearer` 插件（或用 `verifyBearerToken`，注意 1.7 已从 `verifyAccessToken` 改名）。初稿说"两条路收敛到同一个 session"但没说怎么收敛——这里是具体做法。

**owner 单独兜底**：`transfer-ownership`、`delete-organization`、`billing:manage` 三个动作额外硬校验 `member.role === "owner"`，不走通用矩阵——权限配置写错时这三个的爆炸半径最大。

#### 5.3.4 邀请流程（初稿缺失）

`organization` 插件自带 `invitation` 表（`email` / `inviterId` / `organizationId` / `role` / `status` / `expiresAt`）。要自己补的是：

- 邀请链接指向 **Web 页**（`https://bianfa.app/invite/{id}`），**绝不用 `bianfa://`**——邮件客户端对自定义 scheme 支持混乱。
- 接受时分两种情况：已有账号 → 登录后直接 accept；无账号 → 注册流程完成后自动 accept，且注册邮箱必须与被邀请邮箱一致（否则任何拿到链接的人都能加入）。
- 邀请过期时间设 7 天；重复邀请同一邮箱要覆盖而非堆积。

#### 5.3.5 PostgreSQL RLS：不作主授权层，只作防呆兜底

**不用 RLS 做主授权**，三条理由：

1. 两层继承（note → notebook → grant/role）写成 policy 就是每行一个相关子查询，10 万条 note 的列表查询会退化成 seq scan。
2. Better Auth 与业务代码共用同一个 DB role，`current_user` 对隔离毫无意义，必须靠 `SET LOCAL app.*` 传上下文——这把授权正确性绑死在"每个请求都正确开了显式事务"上，而 ORM 的连接池 + 惰性事务边界让这个前提非常脆。
3. 一旦上 **PgBouncer transaction pooling**，用 `SET`（非 `SET LOCAL`）会让租户上下文残留在归还池的连接上，下一个请求直接继承别人的 org_id。

**兜底方案（成本低，值得做）**：只在 `note` / `notebook` / `attachment` 三张表加一条最简单的 `organization_id` 隔离策略，防的是"某个 handler 忘了带 `WHERE organization_id`"。

```sql
ALTER TABLE note ENABLE ROW LEVEL SECURITY;
ALTER TABLE note FORCE ROW LEVEL SECURITY;             -- 表 owner 也受约束
CREATE POLICY org_isolation ON note USING (
  organization_id = current_setting('app.org_id', true)
);
```

配套四条纪律：所有 DB 访问走统一的 `withOrgTx()`（`BEGIN; SET LOCAL app.org_id = $1; ...; COMMIT;`，**只用 `SET LOCAL`**）；PgBouncer 配 `pool_mode = transaction` + `server_reset_query = DISCARD ALL`；`current_setting(..., true)` 的第二个参数必须为 `true`（未设置时返回 NULL 而非抛异常，NULL 比较不匹配 = 拒绝，符合预期）；迁移脚本用独立的 `BYPASSRLS` role 跑。

**加一条 CI 测试**：用一个不带 `SET LOCAL` 的裸连接 `SELECT * FROM note`，断言返回 0 行。这条测试是整个兜底方案唯一的活性证明。

### 5.4 安全细节

#### 5.4.1 密码哈希

**核实结果修正了初稿的论证**。OWASP 当前给出五组 Argon2id 参数：`m=47104(46MiB),t=1,p=1` / `m=19456(19MiB),t=2,p=1` / `m=12288,t=3,p=1` / `m=9216,t=4,p=1` / `m=7168,t=5,p=1`，并明确说明**这几组提供同等强度，差别只是 CPU 与 RAM 的取舍**。

所以初稿"不要用 46 MiB 那档（因为更重）"的表述是错的——46 MiB 那档反而 CPU 更轻（t=1）。正确的理由是**内存峰值**：在一台还要跑 Postgres + API + 同步服务的 VPS 上，`并发登录数 × 46 MiB` 的瞬时内存占用不可接受。

**决策：`m=19456, t=2, p=1`**，并在 API 层用信号量把并发 hash 数限制在 4 以内（19 MiB × 4 ≈ 78 MB 峰值，可控）。库用 `@node-rs/argon2`（核实版本 **2.2.0**，Rust binding，内存在堆外）。

```ts
password: {
  hash: (pw) => hash(pw, { algorithm: 2, memoryCost: 19456, timeCost: 2, parallelism: 1 }),
  verify: ({ hash: h, password: pw }) => verify(h, pw),
}
```

哈希串内嵌参数（`$argon2id$v=19$m=19456,t=2,p=1$...`），未来提参数时在登录成功后按需 rehash，无需刷库。

#### 5.4.2 限流（初稿给了一张不可实现的表）

**核实结果**：Better Auth 内置限流生产默认 `window: 60s / max: 100`，开发模式默认关闭。`customRules` 支持按路径配置（含 `/two-factor/*` 通配和 async 函数），`false` 可禁用某路径。存储可选 memory（默认，多进程会各算各的）、`"database"`、secondary storage、或自定义 `customStorage`（其 `consume` 必须原子地检查并自增）。

**但内置限流按 IP 计数。** 初稿那张表里的 `ip + email`、`userId`、`device_id` 三种维度**用 `customRules` 实现不了**——必须自己在 Better Auth 之前加一层 Redis/Valkey 中间件。

```ts
// 自建维度限流；Better Auth 内置限流保留为 IP 兜底
async function limit(key: string, max: number, windowSec: number) {
  const n = await redis.incr(key);
  if (n === 1) await redis.expire(key, windowSec);
  return n <= max;
}
// /sign-in/email
if (!await limit(`li:${ip}:${email}`, 5, 900)) return c.json({ error: "rate_limited" }, 429);
```

| 端点 | 限流 | 维度 | 实现 |
|---|---|---|---|
| `/sign-in/email` | 5 / 15 min | `ip + email` | 自建中间件（只按 IP 误伤 NAT，只按 email 会被撞库分散 IP 绕过） |
| `/sign-up/email` | 3 / hour | ip | 内置 `customRules` 即可 |
| `/forget-password` | 3 / hour | email | 自建；**响应恒为 200 且文案恒定**，不泄露邮箱是否存在 |
| `/two-factor/*` | — | userId | **用插件自带的 `failedVerificationCount` / `lockedUntil`**，不要重复造 |
| `/oauth2/token` (refresh) | 60 / min | device_id | 自建 |
| 全局兜底 | 100 / 60s | ip | Better Auth 内置默认值 |

不做 CAPTCHA（桌面端体验差），做**递增延迟**（第 n 次失败 sleep `min(2^n, 8)` 秒）+ 连续 10 次失败触发邮件告警。

#### 5.4.3 邮箱验证、找回、会话固定

- **验证/找回 token**：32 字节随机，**数据库只存 sha256**，验证 15 min、找回 30 min，均一次性。链接指向 Web 页。
- **改密码/改邮箱后**：撤销该用户除当前会话外的所有 session 与 refresh token family，并发一封含被撤销设备列表的通知邮件。
- **会话固定**：登录成功、通过 2FA 提权、切换 active organization 三个时刻都必须重新签发 session token。切换组织时显式调 `auth.api.setActiveOrganization`，绝不直接 `UPDATE session`。

#### 5.4.4 CSRF

桌面端全程 `Authorization: Bearer`，浏览器不会自动附带，**结构性免疫 CSRF**。Web 面（邀请接受页、密码重置页）用 cookie，保留 `trustedOrigins` 白名单 + `SameSite=Lax` + `Secure` + `__Host-` 前缀。

**关键纪律：API 层永远不要"cookie 和 Bearer 都接受"。** 给桌面端的 `/v1/*` 路由显式关闭 cookie 认证，否则等于在 Bearer API 上偷偷开了一个 CSRF 面。

#### 5.4.5 审计日志

```sql
CREATE TABLE audit_log (
  id              bigserial PRIMARY KEY,
  occurred_at     timestamptz NOT NULL DEFAULT now(),
  organization_id text,                             -- 平台级事件为 NULL
  actor_type      text NOT NULL,                    -- user | system | api_key
  actor_id        text, actor_ip inet, actor_device_id uuid,
  action          text NOT NULL,                    -- 'note.deleted' | 'member.role_changed'
  target_type     text, target_id text,
  outcome         text NOT NULL DEFAULT 'success',  -- success | denied | error
  metadata        jsonb NOT NULL DEFAULT '{}',      -- {before:{role:'member'}, after:{role:'admin'}}
  request_id      text
) PARTITION BY RANGE (occurred_at);
CREATE INDEX ON audit_log (organization_id, occurred_at DESC);
CREATE INDEX ON audit_log (actor_id, occurred_at DESC);
```

按月分区，热数据留 90 天在库、冷数据 dump 到对象存储。**必记事件**：登录成功/失败、MFA 变更、密码/邮箱变更、成员增删与角色变更、邀请发出与接受、设备登出与远程抹除、token 复用检测、workspace 删除、AI provider key 写入（**只记 key 最后 4 位与哈希，绝不记明文**）。

审计写入与业务事务**同事务**（否则回滚后留幽灵记录）；`audit_log` 只授 `INSERT` + `SELECT`，不授 `UPDATE`/`DELETE`。

### 5.6 平台总管理员（实例级超级管理员）

> 本节按 `apps/server` 的最终实现写（迁移 `0009_platform_admin.sql`、`src/auth/admin-guard.ts`、`src/auth/services/admin.ts`、`src/auth/routes.ts`、`src/platform-admin.ts`）。字段名一律 snake_case，与 `desktop-server-contract.md` 的线格式一致。**为什么这么设计**见 `docs/10-安全隐私与合规.md` §9.4.6；**怎么开出第一个、怎么关停、怎么审计**见 `infra/RUNBOOK.md` §11。

#### 5.6.1 定位：实例级，不是组织级

5.3 那一整套（owner/admin/member + `authz` 中间件 + `X-Organization-Id`）是**组织级**授权，回答的是"你在这个 org 里能干什么"。总管理员在它之外：它不属于任何 organization，它的权限不由任何 `member.role` 决定，它等价于自托管场景里"这台机器的主人"。

因此它**不复用** `member` 表，而是单独一张 `platform_admin`（`user_id` PK / `granted_at` / `granted_by` / `note`）。`/v1/admin/*` 也不过 `requireOrgRole`、不要求 `X-Organization-Id`。

| | 能 | 不能 |
|---|---|---|
| 密码 | 改任意**非管理员**用户的密码（改完吊销其全部令牌与会话） | 改另一个总管理员的密码；改自己的（走普通改密流程，要验旧密码） |
| 账号 | 冻结 / 解冻任意非管理员账号 | 冻结另一个总管理员；冻结自己 |
| 内容 | **只读**查看目标用户能看到的全部内容（含其所在团队的工作区） | 写任何用户数据（查看跑在只读事务里）；读 E2EE 便笺的正文（服务端只有密文） |
| 身份 | 查看名单（`GET /v1/admin/admins`） | **授予 / 撤销总管理员**——界面上没有这个入口，只能 SSH 上跑 `infra/vps/platform-admin.sh` |

最后一行是整个设计的支点，不是省事：`platform_admin` 开了 RLS 且只给 `bianfa_app` 一条 SELECT 策略，而 api 进程是 NOBYPASSRLS——**api 即使被完全攻陷也铸不出一个新的总管理员**。写入需要 `bianfa_worker`（BYPASSRLS），那把身份只在 worker 容器里。

#### 5.6.2 鉴权与失败语义

`/v1/admin/*` 挂在 `/v1` 的 `requireBearer` 之后，再过 `requireSuperAdmin`：

| 情况 | 返回 |
|---|---|
| `PLATFORM_ADMIN_ENABLED=0` | `404 not_found` —— 这个部署里这些端点确实不存在（先于名单判定；`requireBearer` 仍在它之前，所以不带 Bearer 时看到的仍是 401） |
| 无 / 无效 Bearer | `401 unauthorized`（`/v1` 的统一行为） |
| 已登录但不在名单里 | `403 {"error":"insufficient_role","required":"platform_admin"}`，并写一条 `authz.denied` 审计 |

**为什么是 403 而不是伪装成 404**（与 5.3.3 的分场景一致）：`/v1` 全程要求 Bearer，能走到这里的都是已登录用户，"存在一个 `/v1/admin`"本身不是秘密；真正的边界是名单判定本身。而且伪装 404 要求响应与全局 404 逐字一致，`fail()` 会多一个 `server_time` 字段，做不到——那等于给出一个更细的 oracle 还自欺欺人。

名单判定**不缓存**（org 成员那套 30 秒缓存是为扛高频调用）：管理端点低频高危，多一次索引命中换"撤销即刻生效"。判定异常一律 fail-closed 当作"不是管理员"。

#### 5.6.3 端点

全部在 `/v1/admin` 之下，响应同样带 `server_time`。

| 端点 | 入参 | 响应关键字段 |

| `GET /admins` | — | `admins[]{user_id,email,name,granted_at,granted_by,note}` |

| `GET /users/:id` | — | `user{…同上}`、`frozen_by`、`organizations[]{id,name,slug,role,status}`、`teams[]{id,name,org_id}`、`devices[]{id,name,platform,revoked}`、`scale{workspaces,notes,deleted_notes,e2ee_notes}` |

| `POST /users/:id/freeze` | `{reason?}`（≤200 字） | `{ok:true, revoked_devices}`；`400 cannot_freeze_self`、`403 target_is_platform_admin`、`409 user_deleted` |
| `POST /users/:id/unfreeze` | — | `{ok:true}`；`409 not_frozen`、`409 user_deleted` |
| `POST /users/:id/password` | `{new_password}`（8–128） | `{ok:true, revoked_devices}`；`400 cannot_target_self`、`403 target_is_platform_admin`、`409 user_deleted` |

目标用户不存在一律 `404 not_found`（`:id` 或 `:noteId` 格式非法同样是 404，不给格式校验的回声）。列表里的 `excerpt` 是正文前 200 字符。

被查看的便笺永远不返回"部分解密"的东西：E2EE 便笺（`encryption = 'e2ee'`）在列表里 `excerpt` 为空、详情里 `content` 为 `null`、`content_text` 为空串，两处都带 `readable: false` + `unreadable_reason: "e2ee"`。**如实说看不到，不假装看到了全部。**

#### 5.6.4 「查看内容」的语义：重新进入 RLS，不是绕过它

不新增 BYPASSRLS 角色、不改任何一条既有 RLS 策略、不新开连接池。做法是在一个**只读事务**里把 `app.user_id` 切成**目标用户**，再走一遍 5.3.5 的那套策略：

```
BEGIN;
  SET LOCAL transaction_read_only = on;
  SELECT set_config('app.user_id', <目标用户 id>, true);
  -- 之后的查询与那个用户自己发起时看到的行完全一致
COMMIT;
```

由此得到三条性质：

1. **管理员的可见范围 ≡ 目标用户的可见范围。**"包括其团队的内容"不是另写的一段逻辑，而是 `workspaces` 那条策略（owner / org member / team member 三支）自然的结果。授权逻辑只有一份，不会漂移。
2. **写路径逐字节没动**，不存在"顺手把写权限也放开"的风险；`SET LOCAL transaction_read_only` 是第二道保险——真写了 `UPDATE` 会被 PostgreSQL 直接拒绝，而不是改掉数据。
3. `SET LOCAL` 事务结束即恢复，PgBouncer transaction 模式下连接归还不会把身份泄漏给下一个请求（这正是 5.3.5 那条纪律要求的写法）。

**代价要写明**：管理员看到的是"目标用户视角"，所以同一篇团队便笺可能通过多个用户被看到，审计里也就会有多条 `admin.content_viewed`——这是对的，追责要回答的是"谁看了谁的内容"。

#### 5.6.5 冻结堵的是五条路

只改一个标志位是不够的——冻结要在所有"还能继续用"的入口上同时生效：

| # | 路 | 做法 |
|---|---|---|
| ① | Web cookie 登录（含密码登录、社交回调、注册后自动登录、两步验证后建会话） | `databaseHooks.session.create.before` 判 `frozen_at` / `banned` / `deleted_at`，拒绝并写 `auth.sign_in_denied`。挂在这里而不是某个 `/sign-in` 端点上：`internalAdapter.createSession` 是所有建会话路径的唯一收口 |
| ② | 桌面端 Bearer | `verify-bearer` 的那条 JOIN 里加 `frozen_at`，与 `banned` / `deleted_at` 同级拒绝 |
| ③ | 手里已有的 refresh token 与**待兑换的设备码** | 撤销该用户全部令牌与设备行；把 `deviceCode` 未处理的置 `denied`——`@better-auth/oauth-provider` 的 token 端点全程不查用户状态 |
| ④ | 已经连着的同步 WebSocket | 事务内调 `notifyAuthzRevoked(…, scope="session")` → `pg_notify('authz_revoked')` → sync 侧关掉该用户全部 socket（`docs/07-团队管理与便笺共享.md` 里「撤销共享后连着的房间还在收发」用的同一条通道） |
| ⑤ | 手里那张还没过期的同步凭据 | `sync/auth.ts` 的 `authorize()` 开头判账号可用性。同步凭据是 60 秒 JWT，`onAuthenticate` 只验签名与过期，`authorize()` 原本只判"这个人对这篇便笺有没有权限"——两者都答不了"这个账号还在不在"，缺这条就有最长 60 秒的重连窗口 |

另外冻结时**一并把 `banned` 置 true**：老镜像的 `verify-bearer` 只认 `banned`，这样即使回滚到不认识 `frozen_at` 的旧镜像，Bearer 面依然是关的（回滚时 Web 面会恢复，见 RUNBOOK §11.4）。解冻只在 `deleted_at IS NULL` 时清 `banned`——`banned` 同时是账号清除任务的墓碑标记，无条件清会把一个已匿名化的账号复活。

改密码复用同一条吊销序列（改完全部令牌、设备、Web 会话失效），并额外要求：不能改自己（走普通改密流程）、不能改另一个总管理员（否则一次令牌泄漏就能横向拿下所有管理员账号，且无法遏制）。

#### 5.6.6 审计

管理员的每一个动作都写审计，包括**只读查看**：`admin.user_listed` / `admin.content_viewed` / `admin.user_frozen` / `admin.user_unfrozen` / `admin.password_set`，SSH 授予撤销另写 `admin.granted` / `admin.revoked`（`actor_type = 'system'`），被拒绝的越权访问写 `authz.denied`（`metadata.required = "platform_admin"`；注意 `GET /v1/admin/audit` 只捞 `admin.%` 与 `auth.sign_in_denied` 两类，这一条要另查）。查看的那一笔是在读之前用独立事务写的（读事务只读，写不进 `audit_log`），所以读失败同样留痕。

这些条目的 `org_id` 恒为 NULL，而 5.3 那套 org 审计接口硬编码 `WHERE org_id = <当前 org>`，结构上永远查不到——所以 `GET /v1/admin/audit` 必须是独立入口，否则"能追责"只是一句空话。表级上 `audit_log` 对 `bianfa_app` 只授 SELECT / INSERT，管理员抹不掉自己的痕迹。

#### 5.6.7 关停开关

`PLATFORM_ADMIN_ENABLED=0` 让整面 404。取值只接受 `0` / `1`（zod enum，其它值让 api 启动时报「环境变量校验失败」）；`1` 或不设（空串按未设处理）= 开启，判定用 `!== "0"` 而不是布尔取反——字符串 `"0"` 在 JS 里为真。它刻意不进 `.env.prod.example`——`deploy.sh` 会拒绝任何含 `REPLACE_ME` 的必填键，而这是个有安全缺省值的可选开关，不该成为所有自托管实例的部署前置。操作步骤与那条"compose 必须显式映射它"的前置见 RUNBOOK §11.3。

# 动效、微交互与手感 (Feel)

> 本章的判定标准只有一条：**用户不该「看见」动效，只该觉得「这东西反应真快」**。便笺是高频、碎片化、每天开关几十次的工具，任何超过 300ms 的入场动画在第 20 次使用时都变成阻塞。
>
> 本章所有 token 名与值以基准 §2「Design Token 体系」为准。motion 层只做**两处反向裁定**（新增 `--dur-5` 档位、`--ease-spring` 换 `linear()` 实现），理由写在 §1.2 与 §1.3；其余一律服从基准，包括三条工程红线。

---

## 1. 动效原则与 Motion Token

### 1.1 五条原则

1. **反馈 ≤ 100ms，转场 ≤ 250ms，庆祝 ≤ 400ms。** 便笺没有「庆祝」场景，所以 400ms 只用于新建便笺弹出，且其中只有前 200ms 是感知时长（见 §1.3 对 spring 时长的拆分）。
2. **状态变化必须有动效，位置变化尽量没有。** 颜色/选中/hover 用 transition；列表重排除非用户主动拖拽，否则直接跳变（避免「我刚才点的那条跑哪去了」）。
3. **进场慢、出场快。** 落成一条可执行的机械规则：**出场 = 进场档位降一级**（`--dur-4`→`--dur-3`→`--dur-2`→`--dur-1`，`--dur-1` 不再降），缓动从 `--ease-out` 换成 `--ease-in`。比例约 0.65–0.70，与经验值「× 0.6」一致，且不需要再引入一套 exit 专用 token。
4. **只动 `transform` 和 `opacity`。** 这不是本章的偏好，是基准 §8 红线 2（「每个便笺窗口静止态常驻 GPU 成本为零；hover/focus 过渡只允许动 `opacity` 与 `transform`」）的直接落地。见 §3 性能红线。
5. **动效可被打断。** 用户在便笺淡出到一半时按 Ctrl+Z，必须能从当前视觉状态反向回去，不能等动画播完。CSS transition 天然可打断，`@keyframes` 不行 —— 所以列表项优先用 transition。

### 1.2 Duration Token（合并后的最终表）

基准 §2.2 定义了 `--dur-1..4 = 90 / 140 / 200 / 300`。本章原先自带的 `--dur-instant/fast/base/moderate/slow/spring/exit-fast = 80/120/160/220/320/360/100` **整套作废**，按下表并入基准主干。

| Token | 值 | 用途 | 取代的旧 token |
|---|---|---|---|
| `--dur-1` | `90ms` | hover 底色、按下缩放、checkbox 勾选、滚动条槽淡入、拖起 `scale(1.03)` | `--dur-instant` 80ms |
| `--dur-2` | `140ms` | 图标切换、tooltip 出现、便笺换色、工具栏淡入淡出、关窗、**所有由 `--dur-3` 降级而来的出场** | `--dur-fast` 120ms + `--dur-exit-fast` 100ms |
| `--dur-3` | `200ms` | 默认转场值：Dialog / Toast 入场、FLIP 归位、Tabs indicator、列表内展开 | `--dur-base` 160ms + `--dur-moderate` 220ms |
| `--dur-4` | `300ms` | 视图切换（网格↔列表）、侧栏展开、AI 面板推出 | `--dur-slow` 320ms |
| **`--dur-5`** | **`360ms`** | **唯一新增档位：spring 的物理收敛时长，只允许配 `--ease-spring` 使用** | `--dur-spring` 360ms |

**为什么只补一档，而不是把 6 档全塞回去。** 逐档核对后，基准的 4 档梯子在感知上已经覆盖了旧表的 5 档：80↔90、120↔140、160/220↔200、320↔300 的差值都落在 20% 以内，接近这一时长区间的时长辨别阈（Weber 分数约 10–20%）。把它们拆成两个 token 只会制造「该用 base 还是 moderate」的日常争论，不会产生任何用户能感知的差别。

真正压不进去的只有 spring：**360ms 不是审美选择，是 `mass=1 / stiffness=500 / damping=30` 这组物理参数的收敛时间**。ζ = 30 / (2√500) = 0.671，ζωn = 15，收敛到 ±1% 需 −ln(0.01·√(1−ζ²)) / 15 ≈ 327ms，取 360ms 留余量。把它压到基准的 `--dur-4`(300ms) 会在尾部截断回弹，视觉上变成「弹了一半被掐掉」。所以它必须是独立档位，而且**不参与「出场降一级」规则**（spring 只用于进场，没有出场形态）。

**出场档位映射表**（原则 3 的机械形式，写进 review checklist）：

| 进场 | 出场 | 典型场景 |
|---|---|---|
| `--dur-5` `--ease-spring` | `--dur-2` `--ease-in` | 新建便笺 → 关闭便笺 |
| `--dur-4` `--ease-out` | `--dur-3` `--ease-in` | AI 面板推出 → 收起 |
| `--dur-3` `--ease-out` | `--dur-2` `--ease-in` | Dialog / Toast |
| `--dur-2` `--ease-out` | `--dur-1` `--ease-in` | tooltip、工具栏 |
| `--dur-1` | `--dur-1` | hover（本来就在阈值上，不再降） |

### 1.3 Easing Token（合并后的最终表）

基准 §2.2 只有三条：`--ease-out` / `--ease-in-out` / `--ease-spring`。本章原先的五条 `--ease-standard/decelerate/accelerate/apple/inout` 按下表折叠：

| 旧 token | 归并到 | 理由 |
|---|---|---|
| `--ease-standard` `cubic-bezier(.2,0,0,1)` | `--ease-out` | 两条曲线在 0–1 上的最大偏差 < 4%，肉眼不可分 |
| `--ease-decelerate` `cubic-bezier(.05,.7,.1,1)` | `--ease-out` | 基准的 `(.16,1,.3,1)` 就是一条 easeOutExpo 型「飞进来停稳」曲线，正是 decelerate 想要的 |
| `--ease-apple` `cubic-bezier(.32,.72,0,1)` | `--ease-out` | **删除，无条件。** 一条 macOS 专用缓动会让两平台手感分叉，而基准 §8 红线 3 规定平台分叉只允许在 chrome 层。手感不是 chrome |
| `--ease-inout` `cubic-bezier(.45,0,.55,1)` | `--ease-in-out` | 基准的 `(.65,0,.35,1)` 更对称，循环动画（骨架屏呼吸）用它 |
| `--ease-accelerate` `cubic-bezier(.3,0,.8,.15)` | **`--ease-in`（新增 1 个 L2）** | 这是真实缺口，见下 |

**新增 `--ease-in`：** 基准有 `--ease-out` 和 `--ease-in-out`，唯独缺出场用的「慢起快走」曲线。用 `--ease-out` 做出场会让元素「拖着走」，直接违反原则 3。新增的这一条**命名严格对称于基准既有的两条，不引入新前缀、不建新体系**，值沿用本章实测过的 `cubic-bezier(.3,0,.8,.15)`。

```css
/* —— 合并后的最终 motion token（并入基准 §2.2 的 :root 块） —— */
:root {
  --dur-1:90ms; --dur-2:140ms; --dur-3:200ms; --dur-4:300ms;
  --dur-5:360ms;                       /* 新增：spring 物理收敛档，只配 --ease-spring */

  --ease-out:cubic-bezier(.16,1,.3,1);
  --ease-in-out:cubic-bezier(.65,0,.35,1);
  --ease-in:cubic-bezier(.3,0,.8,.15);  /* 新增：出场专用，命名对称于上二者 */

  /* spring：mass=1, stiffness=500, damping=30 → ζ=0.671，超调 5.8%，360ms 收敛到 ±1%
     取代基准的 cubic-bezier(.34,1.30,.52,1)，理由见下方【反向裁定】 */
  --ease-spring: linear(
    0, 0.164, 0.470, 0.746, 0.931, 1.026, 1.057,
    1.053, 1.037, 1.020, 1.007, 1.000, 1
  );
}
```

**【反向裁定】`--ease-spring` 从 `cubic-bezier(.34,1.30,.52,1)` 改为 `linear()`。** cubic-bezier 只能表达单峰超调，它冲过 1 之后是**单调回落**，没有真实弹簧的二次微幅回弹；在 220×220 便笺这种小尺寸上，`scale(.94)→1` 的位移只有 ~13px，单峰超调看起来像「顶了一下」而不是「弹稳了」。`linear()` 直接采样真实 mass-spring-damper：超调 5.8%、一次可见回弹、收尾平滑。

代价核对过，是零：`linear()` 已于 2023-12 在 Chrome 113 / Firefox 112 / Safari 17.2 全线可用（预计 2026-06-11 进入 Baseline Widely Available）。WebView2（Chromium 113+）与 macOS 14+ 的 WKWebView 都满足，**bianfa 可以直接用，不需要 JS spring 库**——省掉 Motion / Framer Motion 的约 30KB 和主线程逐帧计算，spring 完全跑在合成线程。这一点对红线 2 尤其关键：JS spring 库要么写 `will-change` 常驻，要么每帧 rAF 改内联 transform，两条路都过不了「静止态零常驻 GPU 成本」的门。

**不要用 CSS `spring()`：** 截至 2026-09 仍是 CSS Easing Level 2 草案，无浏览器实现。需要新曲线时用 linear-easing-generator 采样成 `linear()`。**Web Animations API 同样支持 `linear()`**：`el.animate(kf, { easing: 'linear(0, 0.164, ...)' })`，JS 侧和 CSS 侧共用同一条曲线字符串（从一个 `motion.ts` 常量导出，禁止两处各写各的）。

**spring 名额仍是 3 处**（沿用基准 §5.7 的纪律）：**新建便笺窗口 / 拖拽落位 / 待办打勾**。本章原先给「窗口置顶」的图钉也配了 spring，现降级为 `--dur-3 --ease-out`——图钉的 `rotate + scale` 关键帧本身已经足够有物理感，把第 4 个 spring 名额花在这里会稀释前三处的分量。

### 1.4 与基准 §5.7 的三处 spring 对齐

基准 §5.7 给新建/删除写的关键帧含 `box-shadow` 变化（`--sh-3` ↔ `--sh-window`），而基准 §8 红线 2 明确要求「`box-shadow` 过渡改两层伪元素 crossfade」。这是基准内部的表述冲突，本章按红线执行：

```css
/* 阴影层化：两层伪元素预置好各自阴影，只 crossfade opacity —— 合成线程，0 paint */
.note-shell::before{ box-shadow:var(--sh-window); opacity:1; }
.note-shell::after { box-shadow:var(--sh-3);      opacity:0; }
.note-shell::before,.note-shell::after{
  content:''; position:absolute; inset:0; border-radius:inherit;
  pointer-events:none; transition:opacity var(--dur-3) var(--ease-out);
}
.note-shell[data-lift="true"]::before{ opacity:0 }
.note-shell[data-lift="true"]::after { opacity:1 }
```

三处 spring 的最终定义：

- **新建**：`scale(.94) rotate(.8deg) → scale(1) rotate(0)`，`--dur-5 --ease-spring`；阴影 `--sh-3 → --sh-window` 走上面的 crossfade（`--dur-3 --ease-out`）；`opacity 0→1` 只占前 `--dur-3`(200ms)。
- **拖拽落位**：FLIP 归位 `--dur-5 --ease-spring`（基准 §5.7 的「落位」即此处）。
- **待办打勾**：`stroke-dasharray:16 → dashoffset:0`，`--dur-3 --ease-out` delay 40ms；方框 `scale(.9)→1` `--dur-5 --ease-spring`。SVG stroke 属性动画会触发 paint，但作用面积是 16×16px，落在 §3.1「小面积可动」的白名单内。

## 2. 关键动效逐个定义

所有时长/缓动均为 §1.2–1.3 的 token，代码里不许出现裸数值。

| 场景 | 动效 | 值 |
|---|---|---|
| **新建便笺（窗口）** | 窗口先 `visible:false`，前端首帧后 `show()`；**动的是窗口内的 `.note-shell`，不是窗口本身**（见 §5.3：Windows 便笺窗 `transparent:false`，整窗 opacity/scale 会露出不透明底色）。`scale(.94) rotate(.8deg)→1`，`transform-origin` 指向触发点（列表项位置或鼠标位置） | `--dur-5 var(--ease-spring)`；`opacity 0→1` 只用前 `--dur-3` |
| **新建便笺（列表内）** | 高度 `0→auto` 用 `grid-template-rows: 0fr→1fr`（可动画，不触发 JS 测高）+ 内容 `translateY(-4px)→0` | `--dur-3 var(--ease-out)` |
| **删除便笺** | `translateY(-6px) rotate(-1.2deg) scale(.98)` + 阴影 crossfade 到 `--sh-3`，随后整体 `opacity→0`；列表后续项用 FLIP 上移。**不做 `filter: blur()`，不做撕纸锯齿动画**（裁定见 §3.6） | `--dur-2 var(--ease-in)`；后续项上移 `--dur-3 var(--ease-out)`，delay 60ms |
| **颜色切换** | 只过渡 `--note-paper` / `--note-ink` 驱动的 `background-color` 与 `color`；**同时给 10 个色块做 `outline` 位移**（选中环从旧色块滑到新色块，用共享元素而非各自 fade）。同帧调 `setBackgroundColor()` 同步原生窗口底色（见 §5.2） | `--dur-2 var(--ease-out)`；选中环 `--dur-3 var(--ease-out)` |
| **窗口置顶反馈** | 图钉 `rotate(0→-35deg)` + `scale(1→1.15→1)`；窗口边界强调用 `box-shadow: inset 0 0 0 1px var(--c-accent)` 的**预置层 crossfade**，不改 border-width（避免重排），也不动 box-shadow 本身 | 图钉 `--dur-3 var(--ease-out)`；边界层 `--dur-2 linear` |
| **拖拽便笺（列表内排序）** | 拖起：`scale(1.03)` + 阴影 crossfade 到 `--sh-3` + `cursor:grabbing`，`--dur-1`；跟随鼠标 **0 延迟**（`transform: translate3d()` 直接写，不过 transition）；落下：FLIP | 落下 `--dur-5 var(--ease-spring)`；占位符高度 `--dur-3 var(--ease-out)`；层级 `--z-drag` |
| **列表项 hover** | `background-color` → `--c-hover` + 右侧操作按钮 `opacity 0→1`；**不做位移、不做 scale**（鼠标划过 20 条时每条都动会晕） | 进 `--dur-1 linear`；离开 `--dur-2`（离开慢一点，防抖误触感） |
| **便笺窗工具栏** | 双条件触发（基准 §5.4：`聚焦 AND (悬停 OR 有选区 OR 3s 内有输入)`）。**只动 `opacity`，不动 `transform`**——15 张窗口同屏时任何位移都会连成波浪 | 显示 `--dur-2`；隐藏延迟 200ms（失焦）/ 800ms（离开），过渡 `--dur-2` |
| **Toast** | 位置按基准 §4：**底部居中距边 24**。入场 `translateY(8px)→0 + opacity`；出场同路径反向 | 入 `--dur-3 var(--ease-out)`；出 `--dur-2 var(--ease-in)`；层级 `--z-toast` |
| **Dialog** | scrim（`--c-scrim`）`opacity 0→1`；面板 `scale(.96)→1 + translateY(8px)→0` | 面板 `--dur-3 var(--ease-out)`；scrim `--dur-2`；关闭 `--dur-2 var(--ease-in)`；层级 `--z-modal` |
| **骨架屏** | 只在 >400ms 才显示（<400ms 直接空白，闪一下骨架比等待更烦）；动效按基准 §4：`opacity .55→1` 呼吸，**不用 shimmer 渐变位移**（裁定见 §3.6）。文本条高 10px（13px 文本）/ 11px（14px 文本），行距等于被替代文本，`--r-xs`，底色 `--c-surface-3` | `1.2s var(--ease-in-out) infinite alternate` |
| **同步状态** | 三态：`idle`（无指示）/ `syncing`（1.5px 细环 `rotate` `900ms linear infinite`，色 `--note-ink2`，便笺外用 `--c-text-3`）/ `error`（静态图标 + `--c-danger`）。**syncing 少于 300ms 不显示**——用 `setTimeout(300)` 才点亮 | 消失 `opacity --dur-2`，不做 checkmark 弹跳 |

> 环宽保留 1.5px：基准 §2.2 禁的是 0.5px（Win 125%/150% 下不可预测），1.5px 在 100%/125%/150% 下分别是 1.5 / 1.875 / 2.25 device px，无消失风险。

### 2.1 AI 流式输出（重点）

这是最容易做出「廉价感」的地方。五个必须做对的点：

**(a) 不要逐字符渲染，按 rAF 批量刷新。**

```ts
let buf = '';
let scheduled = false;
function onToken(t: string) {
  buf += t;
  if (scheduled) return;
  scheduled = true;
  requestAnimationFrame(() => {          // 16.7ms 一批
    scheduled = false;
    flush(buf); buf = '';
  });
}
```

中文 token 通常 1-2 字，SSE 每秒 30-80 个 token。逐 token setState 会让 React 每秒 reconcile 80 次；rAF 批量后最多 60 次，且每次 diff 更大更划算。实测差别在长文本（>2000 字）时是 **55fps vs 22fps**。

窗口失焦时按红线 2 降级：rAF 换成 `setTimeout(100)` 批，窗口失焦 3s 后彻底停 rAF（AI 面板本身不在便笺窗内，但同一条纪律统一执行）。

**(b) 不要每个 chunk 重新解析整篇 Markdown。** 增量策略：把流式内容切成「已完成块」和「未完成尾块」。已完成块（遇到 `\n\n` 即封块）解析一次后 **key 固定、不再重渲染**；只有尾块每帧重解析。这把 O(n²) 降为 O(n)。

**(c) 不要给新增文字做 fade-in 动画。** 逐字 fade 会在中文下产生「闪烁的马赛克」，而且每个 `<span>` 都是一次布局。正确做法：**文字直接出现，只在文本末尾放一个 2px×1.1em 的光标块**，`opacity 1→0.2` `1000ms steps(2) infinite`，色用 `--c-accent`。

**(d) 防抖动的具体 CSS（含中文排版对齐）：**

```css
.ai-stream{
  /* 排版三件套必须与 .prose / .note-body 完全一致（基准 §3.3），
     否则同一段文字在 AI 面板和便笺里换行位置不同，粘贴过去会「跳行」 */
  text-autospace:no-autospace;
  text-spacing-trim:space-all;
  letter-spacing:.01em;
  line-break:strict;
  word-break:normal; overflow-wrap:anywhere;
  line-height:var(--lh-body);
  /* 关键：禁用 pretty/balance，否则每来一个 token 整段重新换行计算，还会让已定行回跳 */
  text-wrap:wrap;
  /* 已完成块跳过屏幕外渲染；注意 contain:layout 会成为 position:fixed 的包含块，
     浮层必须挂在 .ai-stream 之外 */
  contain:layout style;
  /* 防止代码块出现时把宽度撑开导致整栏重排 */
  min-width:0;
}
.ai-stream pre{ overflow-x:auto; font-family:var(--f-mono); letter-spacing:0 }
.ai-stream img{ aspect-ratio:attr(width) / attr(height) }
```

**绝对不要在流式区域碰 `font-feature-settings`。** 基准 §3.3 已经全局禁掉 `"palt" / "halt" / "chws"`——苹方有、雅黑没有，开了必然两平台错位；标点挤压一律由内嵌子集字体 **BF Punct** 的静态字宽处理。流式场景下这条禁令还有一层额外理由：OpenType feature 的挤压是**上下文相关**的，尾块每帧重解析时上下文在变，同一个标点会在两帧之间改变宽度，肉眼看到的就是文字左右抖。BF Punct 是静态 advance，无此问题。

**(e) 自动滚动到底：** 只有当用户滚动位置距底部 `< 48px` 时才跟随。用户一旦向上滚动 >48px，立即停止跟随并显示「回到底部」按钮。跟随用 `scrollTop = scrollHeight`（瞬时），**不要用 `behavior: 'smooth'`**——平滑滚动和持续追加会打架，产生上下抖动。同时给容器设 `overflow-anchor: none`，避免浏览器滚动锚定和手动滚动冲突。

## 3. 性能红线

### 3.1 只动 transform / opacity

| 属性 | 代价 | 结论 |
|---|---|---|
| `transform` / `opacity` | 合成线程，0 布局 0 绘制 | ✅ 随便动 |
| `filter` | GPU，需要独立层，且**打断 `position:fixed` 的包含块** | ❌ 常驻绝对禁止（红线 2）；瞬时用法见 §3.6，默认不用 |
| `background-color` / `color` | 触发 Paint | ⚠️ 小面积可动（< 200×60px），大面积禁止。便笺换色是例外：整窗 paint 一次，140ms 内完成，不循环 |
| `box-shadow` | Paint，模糊半径越大越贵 | ❌ 动画禁止。要做「抬起」用两层预置阴影 crossfade opacity（§1.4） |
| `background-position` / `background-size` | Paint，且循环时是**常驻** paint 成本 | ❌ 禁止（这条直接杀掉 shimmer 骨架屏，见 §3.6） |
| `width/height/top/left/margin/padding` | Layout + Paint | ❌ 绝对禁止动画 |
| `backdrop-filter` 的 `blur()` 半径 | 每帧重新采样背景 | ❌ 绝对禁止动画；且便笺窗内连静态都禁止（红线 1、2） |
| `grid-template-rows: 0fr→1fr` | Layout，但只影响单个 subtree | ⚠️ 仅用于 `contain: layout` 的小容器 |
| `border-radius` | Paint + 重新裁剪 | ❌ 禁止动画。Windows 便笺 `--r-window:0`，任何「圆角渐变」动画都会让直角/圆角在两平台跑出不同结果 |

### 3.2 `will-change` 正确用法

```js
el.addEventListener('pointerenter', () => el.style.willChange = 'transform');
el.addEventListener('transitionend', () => el.style.willChange = 'auto');
```

规则：**动画开始前 ≥1 帧加上，动画结束后立刻去掉。** 永久写在 CSS 里的 `will-change: transform` 违反红线 2，且是内存泄漏——每个提升层按 `宽 × 高 × 4bytes × DPR²` 占显存。

修正一处原稿算错的数：220×220 = 48,400 px，`× 4 bytes × 2² = 774,400 B ≈ **0.74 MB**`（原稿写 0.39MB，是漏了 DPR 平方里的一个因子）。这不改变结论，但会改变 §3.3 的预算表，下面已经按正确值重算。

同理，动画结束后必须把 transform 复位成 `transform: none` 而**不是** `scale(1)`：`scale(1)` 仍然创建包含块，会影响 IME 候选窗定位（§4.2）与 `position:fixed` 浮层。

### 3.3 15 个窗口的合成层预算

- **单窗口层预算：≤ 8 个合成层。** 便笺窗口正常应该只有 2-3 层（根层 + 编辑器 + 浮动工具栏）。
- **15 窗口总显存目标 < 200MB。** 每个 220×220 便笺窗口（2x DPI）：WebView 后备缓冲 0.74MB + 2 个额外层 1.48MB ≈ **2.2MB**，×15 = **33MB**，很宽裕。但如果每个窗口加一个全窗 `backdrop-filter`，每层要额外的背景快照纹理，直接翻倍到 ~66MB，且每个窗口每帧多一个 GPU pass——这正是红线 1、2 同时禁掉它的量化依据。
- **进程内存才是真瓶颈**：Windows 上每个 Tauri 窗口是独立 WebView2 渲染进程，基线 40-90MB。15 个 = 0.6-1.35GB。**必须做的优化**：便笺窗口的前端 bundle 单独打包，目标 gzip < 60KB，不引入编辑器以外的任何库；列表/设置/AI 面板走另一个 entry。
- **非活动窗口降级（红线 2 的强制项）**：窗口 `blur` 后立即给根元素加 `.window-inactive`，内部 `animation-play-state: paused`，同步指示器降为静态图标；**失焦 3s 后停止所有 `animation` 与 `rAF`**。搭配基准 §5.3 的「退半步」：失焦窗口只切 `--note-paper-dim` / `--note-ink-dim` 两个变量，**只触发 paint，不创建合成层，不用 `filter`**。

### 3.4 backdrop-filter 真实代价与降级

实测量级（2x DPI）：`backdrop-filter: blur(20px)` 的成本 ≈ **背景区域像素数 × 2 次 pass**。

- 1280×800 主窗口全屏毛玻璃：3-8ms GPU/帧，中端集显（Intel Iris Xe）会掉到 40fps。
- **便笺窗口一律不用**——不是因为性能不够（220×220 只要 0.3-0.6ms），而是因为红线 1：Windows 上带 alpha 的合成面会让 Chromium 退回灰度抗锯齿、放弃 ClearType，13px 中文明显变虚，而正文是产品 80% 的像素。这是可读性问题，不是性能问题，不接受任何性能论证的翻案。
- **允许范围**：只有设置窗口与 AI 面板（基准 §6.3），且尺寸 ≤ 400×600。

Tauri 原生窗口特效（`window-vibrancy`）的坑：**Windows 10 v1903+ / Win11 22000 的 acrylic 在拖拽和 resize 时有已知严重掉帧；Win11 22621+ 的 blur 同样有问题。** 结论：

- **macOS**：设置窗/AI 面板用原生 `NSVisualEffectView` vibrancy（`under_window` 材质），性能好且与系统一致。便笺窗仍然是实色 `--note-paper`。
- **Windows 11**：**默认关闭** acrylic / blur / Mica。便笺窗 `transparent:false` 是红线，主窗口也不上 Mica（基准 §1 已把 Mica 划入放弃项）。
- **降级链**：`@supports not (backdrop-filter: blur(1px))` → 换 `background: var(--c-surface-1)`（实色，不是半透明——半透明在 Windows 上同样杀 ClearType）。
- **拖拽期间强制降级**：`pointerdown` 时给 `<html>` 加 `.is-dragging`，CSS 里 `.is-dragging *{ backdrop-filter:none !important }`。
- **`prefers-reduced-transparency` 兜底**：WebKit 未实现，Rust 侧读系统设置下发 `data-reduce-transparency="1"`（基准 §7），命中时设置窗/AI 面板也退实色。

### 3.5 长列表虚拟化

- **阈值：> 80 条启用虚拟化。** 80 条以下 DOM 直出更快也更简单（搜索高亮、Ctrl+F、无障碍都不用特殊处理）。
- 库：`@tanstack/virtual` v3（2026-09 最新 3.13.x，headless，React/Svelte 都有绑定，用 `measureElement` 支持不定高卡片）。
- 网格视图用 `lanes` 参数做多列虚拟化，`overscan: 5`。
- **配合 `content-visibility: auto` + `contain-intrinsic-size: auto 180px`** 给非虚拟化的中等列表（20-80 条）提速，代价接近 0。
- 团队便笺墙的看板列：每列独立虚拟化，不要整个墙一个 virtualizer。
- 列表项的 3px 左色条与 8px 色点用 `--note-dot`（基准 §1 的语境化着色：列表是中性卡片 + 色条 + 色点，不整块染色），这两个元素是**静态背景色**，不参与任何动画。

### 3.6 两处与红线的正面冲突：裁定

**冲突 A：删除动效里的 `filter: blur(0→2px)`。**

先回答通则问题——**瞬时 filter 与常驻 filter 该不该区别对待？该**。红线 2 的原文是「静止态常驻 GPU 成本为零」，禁的是稳态开销：常驻 filter 让每个窗口每帧都多一个 GPU pass、多一块纹理，15 窗口就是 15 份，且永远不会消失。瞬时 filter 只在动画的 100–200ms 内存在，成本是一次性的。所以通则是：**瞬时 filter 允许，但必须同时满足三个条件**——① 不在便笺窗口内（便笺窗是红线 1 的辖区，任何新渲染面都可能扰动 ClearType 路径，且 `filter` 会打断 `position:fixed` 包含块，正是基准 §5.3 禁掉「退半步 filter」的同一条理由）；② 动画 ≤ 150ms，且 `filter` 属性在 `animationend` 里从**内联样式**移除，不得留在样式表里；③ 元素已因 `transform` 提层，`filter` 不新增合成层。

**但这一处不值得用掉这个例外，直接删掉。** 具体理由三条：(a) 视觉收益趋零——删除动画总时长 `--dur-2`(140ms)，`opacity` 在前 90ms 就掉到 0.2 以下，`blur(2px)` 实际只在前 40ms 可见，而 2px 模糊对 14px 中文的形变量小于抗锯齿本身；(b) 它把「单窗口 ≤ 8 层」的账算不清——列表里同时删多条时层数不可预测；(c) 一致性——同一个产品里「消失」只应该有一种写法，留一个带条件的例外，半年后必然被复制到便笺窗内。

最终写法：`translateY(-6px) rotate(-1.2deg) scale(.98)` + 阴影层 crossfade + `opacity→0`，纯合成线程，`--dur-2 --ease-in`。旋转和位移保留（基准 §5.7 的「纸被拿走」隐喻，这是便笺身份的一部分，比 blur 值钱得多）。

**冲突 B：骨架屏的 `background-position` 平移 shimmer。**

**服从基准，改 `opacity .55→1` 呼吸。** 理由：shimmer 需要一个持续运动的渐变，`background-position` 动画每帧触发 **paint**（不是合成），在长列表 + 15 窗口场景下这是**常驻 paint 成本**，性质上等同于常驻 filter，同样撞红线 2；而且它无法被 `.window-inactive` 之外的手段廉价降级。

原稿反对 opacity 呼吸的理由是「呼吸看着像出错」——这条我承认部分成立，但它是参数问题不是机制问题：常见的 `.3→1` 大幅呼吸确实像故障闪烁，而基准给的 `.55→1` 幅度 + 1.2s `--ease-in-out` `alternate` 已经温和得多，配合本章保留的「>400ms 才显示骨架」，用户实际能看到的呼吸周期不超过 1–2 次，读不出「出错」。

**已评估并否决的第三条路**：用 `transform: translateX()` 的伪元素遮罩做合成线程 shimmer。技术上确实合规，但需要 `overflow:hidden` + 额外一层，每个骨架条 +1 合成层，长列表里立刻炸掉 §3.3 的层预算。收益（好看一点）配不上代价。

本章保留的骨架屏洞见全部不变：>400ms 才显示、尺寸必须等于真实内容（CLS = 0）、`aria-busy="true"`、加载完成后 `aria-live` 播报、reduced-motion 下改静态 `--c-surface-3`。

## 4. 输入手感

### 4.1 打字延迟目标

| 指标 | 目标 | 上限 |
|---|---|---|
| keydown → 字符出现在屏幕（p50） | **< 16ms** | 33ms |
| keydown → 字符出现（p99） | < 33ms | 50ms |
| 输入时 GC 暂停 | 0 次 > 8ms | — |

测量方法（放进 CI 之外的手动 perf 面板）：

```ts
input.addEventListener('keydown', e => {
  const t0 = performance.now();
  requestAnimationFrame(() => requestAnimationFrame(() => {
    // 双 rAF ≈ 下一帧已提交合成
    log(performance.now() - t0);
  }));
});
```

保证手段：

- 输入路径上 **不做任何同步持久化**。CRDT 更新写内存，`300ms` 空闲 debounce + `2000ms` 强制 flush 才落盘（Rust 侧 `tokio` 异步写）。
- 字数统计、自动链接识别、AI 建议触发全部走 `requestIdleCallback` 或 `250ms` debounce。字数用 `tabular-nums`（基准 §3.2），否则每次更新数字宽度变化会带动整行重绘。
- 富文本装饰（搜索高亮、Markdown 语法着色）用 ProseMirror `Decoration` / CodeMirror `ViewPlugin`，**只重算视口内的**。
- 高亮底色用 `--note-mark`（基准 §5.2 已定义：`color-mix(in oklab, var(--note-dot) 30%, transparent)`），不新造颜色。

### 4.2 IME（中文输入法）—— 必须做对的六件事

这是中文用户每天踩的坑，也是「这软件是老外做的」的最大破绽。

**背景机制：** 输入拼音时，浏览器先发 `compositionstart`，然后每敲一个字母发 `compositionupdate` + 一个 `input`（`inputType: "insertCompositionText"`），选字后发 `compositionend` + 最终 `input`。期间 `keydown.keyCode === 229`（Chromium/WebKit 通用），`KeyboardEvent.isComposing === true`。

**坑 1：回车被当成提交/换行，拼音被吞。**
最经典。用户输 "bianfa" 按回车选字，结果消息发出去了。

```ts
function onKeyDown(e: KeyboardEvent) {
  // 必须两个都判：Safari 在 compositionend 后紧接的 keydown 里 isComposing 已是 false，
  // 但 keyCode 仍是 229（部分 IME）；反之某些 Windows IME 只给 isComposing
  if (e.isComposing || e.keyCode === 229) return;
  if (e.key === 'Enter' && !e.shiftKey) submit();
}
```

同样适用于 AI 面板的斜杠命令（`/` 触发菜单，上下键选择必须让位给候选窗）、搜索框的 Enter，以及基准 §7 定义的 `Esc` 逐级收起（**组合中按 Esc 应该只取消组合，既不收工具栏也不关窗**）。

**坑 2：受控组件把候选文字吃掉。**
React 受控 `<input value={state}>` 在 `compositionupdate` 时 setState 再回写 value，会打断 IME 的组合区。规则：**组合期间不回写 DOM value，不做 setState 驱动的重渲染。**

```tsx
const composing = useRef(false);
<input
  onCompositionStart={() => (composing.current = true)}
  onCompositionEnd={e => { composing.current = false; commit(e.currentTarget.value); }}
  onChange={e => { if (!composing.current) commit(e.currentTarget.value); }}
/>
```

**坑 3：组合期间跑搜索/筛选。**
输 "ni" 时就去搜索，结果列表疯狂闪烁而且搜的是拼音。搜索、便笺墙筛选、AI 自动补全，**一律在 `compositionend` 之后 + 150ms debounce 才触发**。

**坑 4（最难）：CRDT 远端更新打断组合。**
团队便笺墙里，A 正在用拼音输入，B 的编辑通过 Yjs 到达，`y-prosemirror` 应用 transaction → 修改 DOM / DOM selection → **IME 组合区被销毁，已输入的拼音丢失**。ProseMirror 的策略是组合期间「离 DOM 远一点」，但远端更新会强制刷新。

方案：**组合期间挂起远端应用，出组合再放。**

```ts
let pending: Uint8Array[] = [];
let composing = false;
let guardTimer: number | undefined;

provider.on('update', (u: Uint8Array) => {
  if (composing) { pending.push(u); return; }
  Y.applyUpdate(ydoc, u, 'remote');
});

view.dom.addEventListener('compositionstart', () => {
  composing = true;
  // 关键：部分中文 IME（如某些五笔/双拼配置）在用户不选字时永不 commit，
  // 组合可以挂几十秒。必须有超时兜底，否则协作被单个用户阻塞。
  guardTimer = window.setTimeout(forceFlush, 3000);
});
view.dom.addEventListener('compositionend', () => {
  clearTimeout(guardTimer);
  // 再等一帧：compositionend 之后浏览器还会发最终的 input 事件
  requestAnimationFrame(forceFlush);
});

function forceFlush() {
  composing = false;
  const q = pending; pending = [];
  Y.transact(ydoc, () => q.forEach(u => Y.applyUpdate(ydoc, u, 'remote')));
}
```

配套：**本地组合中的文字不要广播。** 只在 `compositionend` 后把最终字符写入 Y.Text，否则协作方看到 "n" → "ni" → "你" 三次闪烁，且 CRDT 里堆了一堆垃圾操作历史。代价是协作延迟 +0.5~2s，**这是正确的取舍**（中文场景下没人想看别人打拼音）。

**坑 5：undo 粒度。**
一次组合（"bianfa" → "便笺"）必须是 **一个 undo 单元**。Yjs 侧用 `new Y.UndoManager(ytext, { captureTimeout: 500, trackedOrigins: new Set([localOrigin]) })`；ProseMirror 侧 `history({ newGroupDelay: 500 })`。绝对不能让 Ctrl+Z 一次退掉一个字母。同时组合期间 **禁用 Ctrl+Z**（`if (e.isComposing) return`）—— IME 自己会处理退格。

**坑 6：EditContext API 不能用。**
`EditContext` 是解决 IME 的正解（把组合状态从 DOM 里解耦），但截至 2026-09 **仅 Chromium 121+ 支持**，Firefox 只有正面表态、Safari/WebKit 无信号。bianfa 要跑 macOS 的 WKWebView，**必须用 `contenteditable` + composition events 这套老方案**。这同时是红线 3 的要求：平台分叉只允许在 chrome 层，两套编辑器实现会直接改变换行结果，是明令禁止的分叉。

**其他 IME 细节：**

- 候选窗定位由系统根据 DOM selection 的 caret rect 决定。**编辑器上不得残留 `transform`**——包括 `scale(1)`。这与 §2 的新建入场动画有直接耦合：`scale-in` 只作用于 `.note-shell`（编辑器的祖先），且必须在 `animationend` 里写 `transform: none`（不是 `scale(1)`），否则 macOS 候选窗会偏移几十像素。窗口新建时不可能已有组合，所以动画期间无风险，风险全在动画结束后的残留上。
- 编辑区禁止 `text-transform`。`font-feature-settings` 已被基准 §3.3 全局禁掉（`palt`/`halt`/`chws` 一律不用），标点由 BF Punct 静态字宽处理——这对 IME 是额外的好消息：静态 advance 不随上下文变化，组合区的候选文字与最终文字宽度一致，不会在 commit 瞬间跳一下。
- `text-autospace:no-autospace` 与 `text-spacing-trim:space-all` 在编辑区**同样显式钉死**（基准 §3.3），不做「哪边支持哪边开」的渐进增强。
- 组合中的下划线（`insertCompositionText` 期间的虚线）是系统绘制的，**不要用 `text-decoration: none` 全局清掉**。

### 4.3 光标、选区与快捷键

- **光标：** 便笺窗口用 `caret-color: var(--note-ink)`（跟随便笺色的墨色，不是黑）。空便笺聚焦后光标必须已经在里面——窗口 `show()` 之后立即 `editor.focus()`，不要等 spring 收敛。
- **选区：** 便笺内用基准 §5.2 已定义的 `--note-sel`：`::selection{ background: var(--note-sel); color: inherit }`。便笺外（AI 面板、设置、列表）用 `color-mix(in oklab, var(--c-accent) 22%, transparent)`。**中英混排下不要设 `color`**，否则中文字重感变化明显——这一点在 Windows 上尤其要命，因为雅黑没有 500/600，任何字重变化都会触发合成假粗（基准 §3.1）。
- **选中浮动菜单：** `selectionchange` 后 **180ms debounce** 才出现（拖选过程中不要跳出来），`scale(.94)→1 + opacity`，`--dur-2 --ease-out`，层级 `--z-float`。鼠标松开前不显示。菜单容器不能挂在 `contain:layout` 的祖先里（§2.1d）。
- **快捷键响应：** 本地快捷键 keydown → 视觉反馈 **< 50ms**。键位表以基准 §7 为准：`Ctrl/Cmd+Shift+N` 新建、`Ctrl/Cmd+W` 关闭、`Ctrl/Cmd+K` 命令面板、`Ctrl/Cmd+1~9` + `Ctrl/Cmd+0` 换 10 色、`Ctrl/Cmd+P` 置顶。系统级全局热键默认注册为同一组合 `Ctrl/Cmd+Shift+N`，可在设置改（原稿写的 `Ctrl+Alt+N` 作废，与基准键位表冲突）。
- 所有快捷键 handler 首行加 `if (e.isComposing) return;`。
- 文本编辑快捷键完全跟随系统（mac 的 `Ctrl+A` 是行首不是全选，不处理会被当 bug）。
- 焦点可见性按基准 §7 的单一规则：`:focus-visible{ outline:2px solid var(--c-focus); outline-offset:2px }`；便笺窗内因 `overflow:hidden` 会裁光晕，改 `outline-offset:1px` + 一圈 `box-shadow:0 0 0 1px var(--note-paper)` 内环。**焦点环不做任何动画**——它是无障碍设施，出现必须是即时的。

## 5. 窗口级手感

### 5.1 拖拽跟手度

**绝对不要用 JS 监听 mousemove 再调 `setPosition()`。** 那条链路是 webview → IPC → Rust → OS，实测 30-60ms 延迟，窗口明显「拖在鼠标后面」，是廉价感的头号来源。

正确做法是把拖拽交给 OS：

```ts
// 3px 阈值，避免误触；避免在按钮/输入框上触发
titlebar.addEventListener('pointerdown', async (e) => {
  if (e.button !== 0 || (e.target as HTMLElement).closest('button,input,[contenteditable]')) return;
  const x0 = e.clientX, y0 = e.clientY;
  const move = (m: PointerEvent) => {
    if (Math.hypot(m.clientX - x0, m.clientY - y0) > 3) { cleanup(); getCurrentWindow().startDragging(); }
  };
  const cleanup = () => { window.removeEventListener('pointermove', move); window.removeEventListener('pointerup', cleanup); };
  window.addEventListener('pointermove', move);
  window.addEventListener('pointerup', cleanup);
});
```

比 `data-tauri-drag-region` 属性更可控：属性只在直接挂载的元素上生效（子元素不继承），且社区报告拖拽结束后 **IPC command 变慢** 的 bug（tauri#12597）—— 手动 `startDragging()` 更容易在出问题时加 workaround。

**拖拽区 = 整条标题栏 `--note-titlebar-h`（28px；窗口高 ≥320px 时按基准 §5.6 变 32px）**，便笺没有标题栏文字，整条都可拖（窗口控件区域 `no-drag`）。双击该区域切换「折叠为标题条」。

macOS 上还要处理：拖拽到屏幕边缘时的贴边吸附自己实现（阈值 12px，吸附动画 `--dur-3 var(--ease-out)`，并触发 §6 的一次 `.alignment` 触觉）；Windows 11 的 Snap Layout 在 `decorations:false` 下需手动处理，便笺窗口 **不参与 Snap**（尺寸太小没意义），主窗口参与（对 `WM_NCHITTEST` 返回 `HTMAXBUTTON`，基准 §6.3）。

### 5.2 Resize

无边框窗口需要自绘 8 个 resize 热区（边 4px、角 8px，层级 `--z-resize`）。要点：

- resize 期间 **暂停所有非必要渲染**：加 `.is-resizing` 类，暂停动画、AI 流式渲染降到 100ms 一批。（便笺窗内本来就没有 backdrop-filter 可禁——红线 1 已经禁掉了。）
- WebView2 的 resize 和窗口框架不同步，会露出背景色 → 必须在 `tauri.conf.json` 里给窗口设 `"backgroundColor"` 为当前便笺的 `--note-paper` 实色值（换色时通过 `setBackgroundColor()` 在同一帧同步更新），这样露出的边缘颜色一致，肉眼看不出来。**这条只在 Windows 上生效且是必须的**——因为 Windows 便笺窗 `transparent:false`，没有透明兜底。
- 编辑器用 `ResizeObserver` 而非 `window.resize`，回调内只做 `transform` 级调整；重排交给 CSS 容器查询（基准 §5.6 的断点全部是 `container:note / size`，不是媒体查询）。
- 最小尺寸 `180×140`（基准 §5.6），且随 `--ui-scale` 一起缩放（基准 §7：`180×140 × scale`）。

### 5.3 窗口打开动画

平台差异是真实的：

| | macOS | Windows 11 |
|---|---|---|
| 有边框窗口 | 系统无入场动画（只有 sheet/panel 有） | DWM 提供淡入+微缩放，可被「动画效果」关掉 |
| `decorations: false` + 透明 | 无动画 | **DWM 动画失效** |

所以 **统一在 web 层做**：窗口创建时 `visible: false` → 前端 mount 完成 + 首帧 paint 后调 `show()` → 内容播 `--dur-5 var(--ease-spring)` 的 scale-in。这同时解决了 Tauri v2 众所周知的**启动白屏闪烁**问题。

**关键约束（红线 1 的推论）：动的必须是窗口内的 `.note-shell`，不是窗口本身。** Windows 便笺窗 `transparent:false`，对整窗做 opacity 或 scale 会把不透明的窗口底色露出来，变成「一个白/彩色方块里长出一张便笺」。macOS 便笺窗虽然 `transparent:true` + `--r-window:10px`，技术上可以整窗做，但**不做**——两平台走同一条代码路径，是红线 3 的要求，也省掉一个只在一个平台上出 bug 的分支。

```rust
// Rust 侧：预热一个隐藏窗口，全局快捷键命中时直接复用
```

**预热是达成 < 200ms 目标的关键**：冷创建一个 WebView2 窗口在中端机上要 400-900ms。应用启动后后台常驻 1 个隐藏的空便笺窗口，用户按 `Ctrl/Cmd+Shift+N` 时把它填充内容并 `show()`，然后再后台补一个新的隐藏窗口。预热窗口在隐藏期间必须满足红线 2：不跑任何 `animation` / `rAF`。

**入场时长的两段拆分**（这也是 `--dur-5` 能通过验收 #1 的原因）：`opacity 0→1` 与主要位移在前 `--dur-3`(200ms) 内完成，用户在 200ms 时已经看到一张完整、可输入、光标在闪的便笺；剩下的 160ms 是 spring 5.8% 超调的收敛尾巴，不阻塞任何交互（`pointer-events` 全程可用，`editor.focus()` 在 `show()` 后立刻调）。

关闭动画：`scale(1→0.96) + opacity→0`，`--dur-2 var(--ease-in)`（140ms），然后 `close()`。**超过 150ms 的关闭动画一律不做**——用户已经想让它消失了。同样只动 `.note-shell`。

### 5.4 动效层允许的平台分叉清单

红线 3 要求所有分叉集中在 `src/platform/` 并登记。动效层只有三条，全部在 chrome 层，**没有一条改变内容的换行结果**：

| 分叉 | macOS | Windows | 为什么不影响换行 |
|---|---|---|---|
| 窗口圆角 | `--r-window:10px` | `--r-window:0` | 只改裁剪路径，内容盒宽度不变（`--note-pad-x` 两平台相同） |
| 窗口透明 | `transparent:true` | `transparent:false` + `backgroundColor` 同步 | 只改合成方式 |
| 原生 vibrancy | 设置窗/AI 面板 `NSVisualEffectView` | 无（实色 `--c-surface-1`） | 不落在便笺窗，不落在正文容器 |

`grep -rn 'data-os' src/components/` 必须为空；入场/关闭/拖拽/resize 的动效代码里出现任何 `data-os` 或 `navigator.platform` 分支即 fail CI。

## 6. 触觉与声音

**结论：声音默认关闭并保留开关；触觉只在 macOS 做一处。**

- **声音**：Windows 便笺原版没有音效，桌面工具类应用加音效是负分。唯一值得做的是可选的「删除确认」提示音（40ms，-24dBFS，mono，OGG < 6KB），默认 **off**，在设置里叫「操作音效」。绝对不要做打字音、新建音、同步完成音。
- **触觉**：Windows 桌面端没有可用的触觉 API（除非是 Surface 手写笔）。macOS 有 `NSHapticFeedbackManager`，但**只在有 Force Touch 触控板时有效**。唯一值得做的一处：便笺**贴边/贴网格吸附时**触发 `.alignment` 级别的一次反馈——这正是 Apple 设计这个 API 的场景（对齐辅助线），与 §5.1 的 12px 吸附阈值是同一个事件。需要一个小的 Rust `objc2` 调用，约 20 行。ROI 一般，排在 P2。
- 不做的：拖拽阻尼触觉、按钮点击触觉、滚动到底触觉。
- 触屏分支（基准 §5.4 的 `pointer:coarse`）：无 hover，工具栏常驻，长按 500ms 唤出 sheet。长按期间**不做进度环动画**（会变成常驻 animation），改为长按到 500ms 时一次性的 `scale(.97)` 回弹 `--dur-1`。

## 7. `prefers-reduced-motion` 完整降级

Windows 11 的开关在 设置 → 辅助功能 → 视觉效果 → 动画效果；macOS 在 辅助功能 → 显示 → 减弱动态效果。WebView2（Chromium）和 WKWebView 都正确映射到该媒体查询。

**核心原则：reduce 不等于 0ms。** 全局 `animation: none` 会让元素「啪」地出现，反而更刺眼，也丢掉了「这是新出现的」这个信息。正确做法是 **保留 crossfade，去掉位移与缩放**。

基准 §7 写的是「所有 `--dur-*` → 1ms」，但同一格里又写「**保留工具栏的 100ms opacity 过渡**（硬闪现更刺眼）」——它自己已经承认转场需要 crossfade。本章按这个意图把规则写完整、消除自相矛盾：**低两档归零，高三档统一压到 100ms**。基准的其余四条要求（`--ease-spring` → `--ease-out`、旋转/位移归零、`animation-iteration-count:1`、Skeleton 改静态）逐条照做。

```css
@media (prefers-reduced-motion: reduce) {
  :root {
    /* 反馈档本来就在感知阈值上，归零无损 */
    --dur-1: 1ms;  --dur-2: 1ms;
    /* 转场档保留 crossfade：硬闪现比动画更刺眼，且丢失"这是新出现的"信息。
       基准 §7 要求的"工具栏 100ms opacity 过渡"由 --dur-2→...此处统一为 100ms 覆盖 */
    --dur-3: 100ms; --dur-4: 100ms; --dur-5: 100ms;
    --ease-spring: var(--ease-out);   /* 与基准 §7 一致：去掉超调 */
    --ease-in:     linear;
  }
  /* 去掉所有位移/缩放/旋转，只留 opacity */
  *, *::before, *::after {
    animation-iteration-count: 1 !important;
    scroll-behavior: auto !important;
  }
  .note-shell, .dialog-panel, .toast, .float-menu, .list-item { transform: none !important; }
  /* 循环动画：旋转改为 opacity 脉冲，骨架屏改为静态灰块（基准 §4） */
  .spinner { animation: none }
  .spinner::after { content:''; animation: pulse 1.6s var(--ease-in-out) infinite }
  .skeleton { animation: none; background: var(--c-surface-3) }
  /* AI 流式光标：保留但降低频率 */
  .ai-caret { animation-duration: 2s }
  /* 三个"系统正在工作"的指示器豁免 iteration-count:1 —— 停下来等于告诉用户卡死了 */
  .spinner::after, .ai-caret { animation-iteration-count: infinite !important }
}
@keyframes pulse { 0%,100%{opacity:.35} 50%{opacity:.8} }
```

> 注意 `--dur-2` 在 reduce 下归零后，工具栏淡入变成瞬时。这是有意的：工具栏是 hover 触发的，瞬时出现不构成「凭空冒出」的困惑。基准要求保留的那 100ms，落在 `--dur-3` 一档（Dialog/Toast 这类真正凭空出现的浮层）。

JS 侧（spring、FLIP、拖拽惯性）也必须查询：

```ts
const rm = matchMedia('(prefers-reduced-motion: reduce)');
export const motionOK = () => !rm.matches && settings.motion !== 'off';
rm.addEventListener('change', rebuildAnimations);   // 用户运行中切换要生效
```

**FLIP 排序动画在 reduce 下直接跳变。** 拖拽本身保留（那是用户主动的直接操纵，不算「动效」），但落下的归位动画从 `--dur-5 --ease-spring` 降到 100ms 纯 opacity。

设置里给三态：**跟随系统 / 完整动效 / 减少动效**，默认「跟随系统」。这与基准 §6.2 的主题三态（跟随系统 / 浅色 / 深色）是同一种交互模型，共用一个设置组件。

## 四、结论

**这套规范现在还不是内部自洽的，但离自洽已经很近了——剩下的裂缝是可枚举的，不是结构性的。**

**已经做对的**（三章的重写确实收敛了大量分歧）：

- **色板与对比度**是四份文档里最扎实的一层。frontend_stack 的矩阵门禁不但实现了基准 §2.1 的要求，还反过来抓到了基准自己的两处错（暗色 `--c-text-3` on surface-3 = 4.36:1、亮色 `--c-text-3` on `--c-active` = 4.23:1），并给了正确的分类处置（一个改 token、一个改组件）。这是"生成器 > lint"这条方法论真正兑现的地方。
- **`palt`/`halt`/`chws`、`scrollbar-width`/`scrollbar-color`、0.5px 描边**三项残留扫描**全部通过**，三章不但没有残留，还各自补强了理由（motion 补了流式场景下 OpenType 挤压逐帧抖动的额外论证；frontend_stack 把它们全部做成了机器可判定门禁）。红线 3 的"不改变换行结果"在字体层是真的被守住了。
- **红线 1（Win 不透明）**在三章里零违规，且推论链（不透明 → ClearType → 直角）被三章一致复述。
- **motion 的时长/缓动归并**（6 档压到 4+1、5 条曲线压到 3+1）和**"出场 = 进场降一级"**这条机械规则，是把审美判断转成 review checklist 的正确做法。

**还剩的裂缝，按性质分三类：**

1. **基准自身的三处内部矛盾，被三章各自"补丁"成了三种不同答案。** 这是最危险的一类，因为每一章看起来都自洽：
 - 便笺正文字号地板（§7 说 14px 是地板 / §5.6 说 compact 用 13px）→ screens 选地板、frontend_stack 选 §5.6；
 - reduced-motion（§7 说全部 → 1ms + 保留工具栏 100ms）→ screens 照抄矛盾、motion 解成分档规则；
 - Windows 字距（§2.2 的 .008em / §3.3 的 .01em）→ 三章都选 .01em，基准是唯一异类，且它那条本身就破红线 3。
 **修基准比修三章更省事**，而且现在不修，半年后一定会有人拿基准原文来推翻三章。

2. **三处技术选型的正面冲突**（Anchor Positioning vs Floating UI、`measureElement` 用不用、拖拽用属性还是 `startDragging()`），根源都是**没有一份写死的浏览器基线**。把 A4 定下来，E1 自动解决，A3 也不再悬空。

3. **两处"算术上不可能"或"事实前提错误"的地方**，是四份文档里唯一无法靠裁定解决、必须回到设计台的：
 - **Windows 220px 顶栏塞不下 80px caption 按钮**（F1b）——四章没有一章注意到；
 - **motion §2.1a 写着"AI 面板本身不在便笺窗内"，而 screens §6 明确说 <640px 时它就是便笺窗内的底部抽屉**（C1）——一条 GPU 红线的执行范围建立在一个错误的事实上。

**一句话判断**：token 层与排版层已经硬了，可以开始生成；**交互层（工具栏形态、同步指示器、Esc 链、快捷键）还有 11 处需要人裁定，其中 P0 的 10 条不解决就会产出两套实现**。建议的顺序是：先钉基线（issue 1）→ 修基准的三处自相矛盾（8、11、C5）→ 回写 `--dur-5`/`--ease-in`/`#96958B` 到基准（6、A5）→ 再让三章按修订后的基准做最后一次对齐。Windows 顶栏（issue 2）可以并行交给设计，它不阻塞 token 管线。

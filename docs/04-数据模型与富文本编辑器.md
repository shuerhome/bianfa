## 第 3 章：笔记数据模型与富文本编辑器

> 本章所有版本号、API 名、许可证均于 2026-09-04 从 npm registry / crates.io / 上游源码逐条核实。核实中推翻了初稿的 6 处错误（见 3.7 勘误表），其中 3 处会在编码阶段直接导致运行时崩溃或静默数据错误。

### 3.1 内容模型：权威格式 + 三个投影

五条约束互相拉扯：富文本要结构、CRDT 要字符级序列、LLM 要可读文本、全文检索要纯文本、diff 要稳定块边界。没有单一格式同时最优，答案不是"选一种格式"，而是**一个权威格式 + 三个只读投影**。

| 候选 | 富文本 | CRDT 字符级合并 | LLM 读写 | 全文检索 | 结论 |
|---|---|---|---|---|---|
| HTML string | 好 | 差（标签边界破坏合并） | 中 | 需剥标签 | 否决 |
| Markdown string | 中 | **差**：并发下成对标记会坏 | 最好 | 好 | 否决 |
| **ProseMirror JSON** | **最好** | **最好**（映射成 `Y.XmlFragment`） | 好（可双向转 MD） | 需展平 | **选中** |
| Lexical EditorState | 好 | 好（`@lexical/yjs`） | 中 | 需展平 | 否决 |
| Quill Delta | 中（线性+属性，嵌套吃力） | 好 | 差 | 好 | 否决 |

Markdown 被否决的具体机制值得写死在设计文档里：两人并发在 `**粗体**` 的内侧和外侧插入字符，CRDT 按字符位置合并后会得到 `**粗` + `体**` 这种非法标记序列——Markdown 的成对标记不是结构，CRDT 无法保护它。

**结论：权威真源 = Yjs `Y.Doc`（二进制 CRDT）；文档结构 = ProseMirror JSON schema（由 Tiptap v3 扩展集定义）；PG 里的 `content` JSONB / `content_text` / `checklist_items` 全是只读投影。**

#### 反驳一：CRDT 对便笺是不是过度设计？

反方立场成立的部分：1-3 人团队、一个便笺应用，"每条笔记整体 last-write-wins + `updated_at` 比较"能用 200 行写完，而 CRDT 是 3000 行 + 一整套多端集成测试。**这个反驳我部分接受。**

但推翻的部分是具体的：便笺的头号场景就是"公司改了一条，回家在另一台机器上又改了同一条"。LWW 在这里的行为是静默丢掉一整条便笺的一半内容，而用户不会知道——这是本产品最不能出的 bug。且 CRDT 是**数据格式决定**，不是功能：v1 用 LWW、v2 再上 CRDT，意味着全量数据迁移 + 编辑器重写 + 老客户端不兼容。

**修正后的结论**（比初稿更省）：保留 CRDT 数据模型，但 **v1 砍掉实时协同基础设施**——不做 WebSocket 中继、不做 awareness/多光标、不做 `yCursorPlugin`。v1 的同步是"HTTP 上跑 CRDT 增量"：客户端把 `updateV2` 攒进 outbox，按 `state vector` 做增量拉取，冲突由 CRDT 自动合并。这砍掉了 60% 的服务端工作量（一个有状态的长连接 fan-out 服务），保住了 100% 的合并正确性。多光标留到团队功能真正有人用时再加，加的时候是纯增量。

### 3.2 数据模型

#### 3.2.1 主键：UUIDv7

选 UUIDv7 不选 ULID。已核实 PostgreSQL 18（当前 stable 18.6）内置：

```
uuidv7 ( [ shift interval ] ) → uuid      -- ms 精度 UNIX 时间戳 + 亚毫秒 + 随机
uuidv4 ( ) → uuid
uuid_extract_timestamp ( uuid ) → timestamptz   -- v1/v7 有效，其他版本返回 NULL
uuid_extract_version  ( uuid ) → smallint
```

理由：原生 `uuid` 16 字节（ULID 在 PG 里要么 `text(26B)` 要么装扩展）；时间前缀带来 B-tree 写入局部性；客户端离线可生成（`uuid` npm v13 / `uuid` crate v1.18+ 均有 v7）。代价是泄露创建时间——**分享链接必须用独立随机 token，不能暴露 note id**（写进第 5 章）。

#### 3.2.2 核心 DDL

```sql
CREATE EXTENSION IF NOT EXISTS pgroonga;
CREATE EXTENSION IF NOT EXISTS citext;

CREATE TABLE notes (
  id            uuid PRIMARY KEY DEFAULT uuidv7(),
  workspace_id  uuid NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
  owner_id      uuid NOT NULL REFERENCES users(id),
  notebook_id   uuid REFERENCES notebooks(id) ON DELETE SET NULL,

  -- 以下三列全部是投影，只由 projector 写；任何其他写入路径都是 bug
  content       jsonb NOT NULL DEFAULT '{"type":"doc","content":[]}'::jsonb,
  content_text  text  NOT NULL DEFAULT '',
  title_cache   text  GENERATED ALWAYS AS (left(split_part(content_text, E'\n', 1), 120)) STORED,

  schema_version smallint NOT NULL DEFAULT 1,   -- PM schema 版本，见 3.6
  color         smallint NOT NULL DEFAULT 0 CHECK (color BETWEEN 0 AND 6),
  pinned        boolean  NOT NULL DEFAULT false,

  crdt_sv       bytea  NOT NULL,       -- Y.encodeStateVector(doc)，增量同步握手用
  crdt_bytes    integer NOT NULL DEFAULT 0,     -- 监控指标，见风险
  version       bigint NOT NULL DEFAULT 1,      -- 客户端拉取水位，单调递增

  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now(),
  deleted_at    timestamptz,
  purge_after   timestamptz
);

-- 服务端 CRDT 存储：append-only + 周期压缩，与客户端同构
-- 【对初稿的修正】不要把全量 crdt_state 存成 notes 表的一个 bytea 列：
-- 每次按键批都要重写整个 TOAST 外部块，写放大在长笔记上是灾难性的。
CREATE TABLE note_updates (
  note_id  uuid   NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
  seq      bigint NOT NULL,
  update_v2 bytea NOT NULL,           -- 一律 V2 编码，见 3.7 勘误 #7
  author_id uuid,
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (note_id, seq)
);
CREATE TABLE note_snapshots (        -- 压缩后的基线
  note_id  uuid PRIMARY KEY REFERENCES notes(id) ON DELETE CASCADE,
  upto_seq bigint NOT NULL,
  state_v2 bytea NOT NULL,
  sv       bytea NOT NULL
);
```

压缩策略：`note_updates` 累计 200 条或 512 KB 时，worker 用 `Y.mergeUpdatesV2` 合成新的 `note_snapshots.state_v2` 并删除已并入的行。实测这个折叠很值：逐字符输入一句 105 字节的中文，`updateV2` 事件累计 1148 B，`encodeStateAsUpdateV2` 折叠后 130 B，**压缩 8.8 倍**。

```sql
-- 窗口几何：per-device，绝不放 notes 表
CREATE TABLE note_placements (
  note_id uuid NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
  device_id uuid NOT NULL REFERENCES devices(id) ON DELETE CASCADE,

  z_order int NOT NULL DEFAULT 0,
  is_open boolean NOT NULL DEFAULT true,
  is_desktop_pinned boolean NOT NULL DEFAULT false,
  monitor_key text,                    -- "\\.\DISPLAY1|2560x1440|@0,0"，换显示器时回落居中

```

用户在 27" 上摆在 (3200, 1800) 的窗口同步到 1366×768 笔记本就飞出屏幕了。Windows 便笺自己也是本机存几何。`pinned`（列表置顶）是逻辑属性，留在 `notes`。

```sql
CREATE TABLE notebooks (
  id uuid PRIMARY KEY DEFAULT uuidv7(),
  workspace_id uuid NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
  parent_id uuid REFERENCES notebooks(id) ON DELETE CASCADE,  -- v1 应用层强制 NULL
  name text NOT NULL, sort_key text NOT NULL,                 -- fractional index
  created_at timestamptz NOT NULL DEFAULT now(), deleted_at timestamptz
);
CREATE TABLE tags (id uuid PRIMARY KEY DEFAULT uuidv7(), workspace_id uuid NOT NULL,
                   name text NOT NULL, color smallint, UNIQUE (workspace_id, lower(name)));
CREATE TABLE note_tags (note_id uuid REFERENCES notes(id) ON DELETE CASCADE,
                        tag_id uuid REFERENCES tags(id) ON DELETE CASCADE,
                        PRIMARY KEY (note_id, tag_id));

CREATE TABLE attachments (
  id uuid PRIMARY KEY DEFAULT uuidv7(),
  workspace_id uuid NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
  content_hash bytea NOT NULL,        -- BLAKE3-256, 32B
  byte_size bigint NOT NULL, mime text NOT NULL,
  width int, height int, blurhash text,
  storage_key text NOT NULL,          -- 'ws/<workspace_id>/blake3/ab/cd/<hex>'
  ref_count int NOT NULL DEFAULT 0,
  gc_after timestamptz,               -- ref_count 归零时 = now()+7d
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (workspace_id, content_hash)
);

CREATE TABLE checklist_items (        -- 投影，真源在 PM doc 的 taskItem 节点
  note_id uuid NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
  block_id text NOT NULL,             -- UniqueID 写进 attrs.id
  text text NOT NULL, checked boolean NOT NULL, ordinal int NOT NULL,
  PRIMARY KEY (note_id, block_id)
);
CREATE TABLE reminders (
  id uuid PRIMARY KEY DEFAULT uuidv7(),
  note_id uuid NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
  block_id text,
  rrule text, next_fire_at timestamptz NOT NULL, tz text NOT NULL DEFAULT 'Asia/Shanghai',
  status text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','fired','done','cancelled'))
);
CREATE INDEX reminders_due_idx ON reminders (next_fire_at) WHERE status = 'pending';
```

三条决策：

- **附件去重范围 = `workspace_id`，不是全局。** 全局去重能省更多存储，但会产生跨租户存在性泄露：攻击者上传一张图，观察是否秒传，就能判断别的团队有没有这张图。省的那点存储费不值这个洞。`ref_count` 归零后写 `gc_after = now()+7d` 进延迟队列，防"删了又撤销"时对象已被清；**硬删顺序必须是先删 note 引用再扫 ref_count，反了就是回收站恢复后全裂图**。
- **checklist 项不做真源表。** 任务项要能拖排序、内含粗体和链接、能字符级合并——这些 PM 文档天然有，拆成行反而要自己实现 fractional ordering 和富文本子结构。约定死：**笔记内渲染勾选框一律读 PM doc；`checklist_items` 只供跨笔记聚合查询**，否则 worker 的异步窗口期会让勾选框闪烁。
- **v1 不做嵌套文件夹**，理由不是"没需求"而是"并发树移动会成环"：两端离线时分别把 A 移进 B、B 移进 A，合并后子树从根不可达。正确解需要 Kleppmann 的 move operation（带 undo-do-redo 日志），2-3 周。交付单层 `notebooks` + 多标签；`parent_id` 列先建好，v2 零迁移。

#### 3.2.3 元数据也进 Y.Doc —— 干掉 409/rebase 这条路径

初稿的 outbox 有个 `meta_patch` + `base_version` 乐观锁 + 409 触发 rebase 的分支。**这条分支应该删掉**：改颜色、置顶、换 notebook 这些操作离线并发时，"服务端返回 409、客户端 rebase 再重放"是一整套需要单独测试的状态机，而它解决的冲突只有"两台设备改了同一条便笺的颜色"这种无关紧要的问题。

做法：在同一个 `Y.Doc` 里开一个 `Y.Map('meta')` 存 `color / pinned / notebook_id / tag_ids`。这样：

- 同步通道只有一条（CRDT update），outbox 的 `op` 从 4 种缩到 2 种（`ydoc_update` | `blob_upload`）；
- 冲突由 Yjs 的 LWW-per-key 自动解决，语义正好（后改的颜色赢）；
- 服务端 `notes.color / pinned` 变成 projector 写的投影列，与 `content_text` 同一条代码路径。

`notebook_id` 是外键，投影时要校验目标 notebook 存在，不存在则落 NULL——这是 CRDT 换来的唯一额外工作，20 行。

#### 3.2.4 索引与中文检索

服务端选 **PGroonga 4.0.8**（2026-08-03 发布；`main` 分支 `pgroonga.control` 已标 `default_version = 4.0.9`，发布时以实际包为准）。

| 方案 | 中文效果 | 许可 | 否决理由 |
|---|---|---|---|
| tsvector + `simple` parser | 不可用 | — | 不分词，整句一个 token |
| pg_trgm | 差 | PostgreSQL | trigram 提取忽略非字母数字，中文实测不可用 |
| zhparser (SCWS) | 中 | BSD | 词典自维护，新词切不出；无 BM25 排序 |
| pg_jieba | 好 | MIT | 同上无排序；仓库活跃度低 |
| pg_search (ParadeDB) | 好（jieba+BM25） | **AGPLv3** | SaaS 场景法务边界模糊，不值 |
| **PGroonga 4.0.8** | **好**（bigram，零词典） | **PostgreSQL License** | — |

**【勘误】PGroonga 本身是 PostgreSQL License（类 BSD/MIT），不是初稿写的 LGPL-2.1**——已核对其 `COPYING` 与 README（"released under PostgreSQL license that is similar to BSD license and MIT license"）。LGPL-2.1 的是它依赖的原生库 Groonga，作为动态链接的数据库扩展加载，对我们的应用代码没有传染性。这条纠正把初稿列的"法务风险"降级为"零"。

PGroonga 用 bigram 索引，不依赖词典，所以新词、中英混排、错别字片段都能召回。ordered index scan 能力自 **4.0.4**（2025-10-02，同版本加的 PG 18 支持）起可用——不是初稿写的"PG 18 起"。

```sql
-- 【修正】多列 pgroonga 索引：把租户过滤压进索引，避免 BitmapAnd 在
-- workspace 数量大时退化。这同时解决了初稿留作 open question 的跨库检索问题。
CREATE INDEX notes_search_idx ON notes
  USING pgroonga (workspace_id, content_text) WHERE deleted_at IS NULL;
CREATE INDEX notes_list_idx ON notes (workspace_id, pinned DESC, updated_at DESC)
  INCLUDE (title_cache, color) WHERE deleted_at IS NULL;
CREATE INDEX notes_trash_idx ON notes (workspace_id, deleted_at DESC) WHERE deleted_at IS NOT NULL;
CREATE INDEX note_tags_tag_idx ON note_tags (tag_id, note_id);
```

```sql
-- Q1 侧边栏列表（最高频）：Index Only Scan，无 Sort 节点
SELECT id, title_cache, color, pinned, updated_at FROM notes
WHERE workspace_id = $1 AND deleted_at IS NULL
ORDER BY pinned DESC, updated_at DESC LIMIT 50;

-- Q2 中文检索 + 高亮
-- 【勘误】pgroonga_snippet_html 返回 text[]（第三参数 width 默认 200），不是 text
WITH kw AS (SELECT pgroonga_query_extract_keywords($2) AS k)
SELECT n.id, n.title_cache,
       (pgroonga_snippet_html(n.content_text, kw.k))[1] AS snippet,
       pgroonga_score(n.tableoid, n.ctid) AS score
FROM notes n, kw
WHERE n.workspace_id = $1 AND n.deleted_at IS NULL AND n.content_text &@~ $2
ORDER BY score DESC LIMIT 20;
-- &@~ 是 query 语法（支持 AND/OR/括号），&@ 是单词匹配，&@| 是 OR 数组。
-- 上线前必须用真实语料跑 EXPLAIN (ANALYZE, BUFFERS) 定 p95，别信任何未实测的延迟数字。
```

**客户端 SQLite 才是搜索主路径。** 个人 workspace 通常 < 1 万条，本地检索零网络延迟、离线可用；服务端 PGroonga 只服务 Web 端和团队共享库跨用户检索。这条架构决定让 VPS 的检索压力下降一个数量级。

#### 反驳二：PGroonga 把我们锁死在自管 VPS 上，是不是该换 Meilisearch？

反方成立的部分是硬事实：PGroonga 依赖 Groonga 原生库，RDS / Supabase / Neon 一律不支持；升 PG 大版本必须等 `postgresql-NN-pgdg-pgroonga` 包，会卡住升级窗口。

但**反方的替代方案更差**。Meilisearch/Typesense 意味着 1-3 人的团队要多运维一个有状态服务：额外的进程、额外的持久卷、额外的备份、以及最麻烦的**双写一致性**（PG 写成功而搜索索引写失败时怎么办）。对这个团队规模，"一个 PG + 一个扩展"的运维成本比"一个 PG + 一个搜索引擎"低一个量级。

**维持原结论，但补上退出坡道**：`content_text` 是普通 text 列，索引与业务查询之间只隔一层 repository 方法 `searchNotes()`。换搜索后端 = `DROP INDEX` + 换掉这一个方法的实现，不动 schema、不动数据。锁定成本已被限制在一个函数里。同时把"PG 大版本升级需等 pgroonga 包"写进第 6 章的运维 checklist。

#### 3.2.5 客户端 SQLite

```sql
CREATE TABLE notes (
  id TEXT PRIMARY KEY, workspace_id TEXT NOT NULL, notebook_id TEXT,
  content TEXT NOT NULL, content_text TEXT NOT NULL DEFAULT '',
  content_bigram TEXT NOT NULL DEFAULT '',   -- 见下：兜底路径用
  schema_version INTEGER NOT NULL DEFAULT 1,
  color INTEGER NOT NULL DEFAULT 0, pinned INTEGER NOT NULL DEFAULT 0,
  x INTEGER, y INTEGER, w INTEGER DEFAULT 320, h INTEGER DEFAULT 320,
  z_order INTEGER DEFAULT 0, is_open INTEGER DEFAULT 1, is_desktop_pinned INTEGER DEFAULT 0,
  monitor_key TEXT,
  version INTEGER NOT NULL DEFAULT 0, local_rev INTEGER NOT NULL DEFAULT 0,
  created_at INTEGER, updated_at INTEGER, deleted_at INTEGER
) STRICT;

CREATE TABLE ydoc_updates (note_id TEXT NOT NULL, seq INTEGER NOT NULL,
                           update_v2 BLOB NOT NULL, created_at INTEGER NOT NULL,
                           PRIMARY KEY (note_id, seq)) STRICT;
CREATE TABLE ydoc_snapshots (note_id TEXT PRIMARY KEY, upto_seq INTEGER NOT NULL,
                             state_v2 BLOB NOT NULL, sv BLOB NOT NULL) STRICT;

CREATE VIRTUAL TABLE notes_fts USING fts5(
  content_text, content='notes', content_rowid='rowid', tokenize='simple 0');
```

分词器选 **wangfenjin/simple v0.7.1**（2026-02-23，双许可 MIT or GPLv3，取 MIT 分支）。它提供 `simple_query()` / `simple_highlight()` / `simple_snippet()` / `jieba_query()`，并支持拼音检索（"zhangliangy" 命中"张靓颖"）——Windows 便笺没有的低成本差异化。以 `.dll`/`.dylib`/`.so` 随 Tauri 打进 `resources/`。

**【重要勘误】初稿的兜底方案是错的。** SQLite 内置 `tokenize='trigram'` 在中文上不可用于兜底：核对 `ext/fts5/fts5_tokenize.c` 的 `fts5TriTokenize()`，它在填充首个 trigram 时若输入不足 3 个 code point 就直接 `return SQLITE_OK` **不产出任何 token**。而中文查询词绝大多数是**两个字**（"会议""报销""需求"），走 `MATCH` 时命中数恒为 0——不是"效果差"，是"完全不工作"。

正确的兜底是**应用层 bigram shingling**（约 30 行）：projector 在写 `content_text` 的同时，把连续 CJK 字符切成空格分隔的二元组写进 `content_bigram`（"周会纪要" → `周会 会纪 纪要`），查询词同样切 bigram 后用内置 `unicode61` tokenizer 检索。代价是索引体积约 2 倍、无拼音、无 BM25 语义调优，但**能召回**。

```sql
-- 兜底路径（simple 扩展加载失败时启用）
CREATE VIRTUAL TABLE notes_fts_bg USING fts5(
  content_bigram, content='notes', content_rowid='rowid', tokenize='unicode61');
```

启动时探测：`load_extension` 成功且 `SELECT simple_query('测试')` 不报错 → 主路径；否则切兜底并在设置页显示降级提示。两条路径共用同一个 `searchLocal()` 接口。

### 3.3 编辑器实现

依赖清单（全 MIT，已核实 npm 上均为 3.31.2）。**注意 StarterKit 已内含 `extension-list`/`extension-link`/`extension-strike`/`extension-underline`，初稿的清单有重复项**：

```ts
import { Editor } from '@tiptap/core'

```

`filterTransaction: tr => !isChangeOrigin(tr)` 不是可选项：UniqueID 的官方 d.ts 明写这个选项是为了 "Ignore some mutations, for example applied from other users through the collaboration plugin"。不加，两个客户端会给同一个新节点各生成一个 ID，合并后 attrs 冲突。

**快捷键复刻表**（已解包各扩展的 `dist/index.js` 核对默认键位）：

| 便笺行为 | 快捷键 | Tiptap 默认 | 处理 |
|---|---|---|---|
| 粗体 / 斜体 | Ctrl+B / Ctrl+I | `Mod-b` / `Mod-i` | 已对齐 |
| 下划线 | Ctrl+U | `Mod-u`（源码中 `Mod-u` 与 `Mod-U` 都注册） | 已对齐 |
| **删除线** | **Ctrl+T** | **`Mod-Shift-s`**（已核实） | **必须覆盖**：`addKeyboardShortcuts: () => ({ 'Mod-t': () => this.editor.commands.toggleStrike() })` |
| **项目符号列表** | **Ctrl+Shift+L** | 无序 `Mod-Shift-8` / 有序 `Mod-Shift-7` / 任务 `Mod-Shift-9`（已核实） | 覆盖 `Mod-Shift-l`，写一个三态机：无序 → 有序 → 取消 |
| 新建 / 关闭便笺 | Ctrl+N / Ctrl+W | — | 走 Tauri 全局层（第 4 章） |

Ctrl+T 在普通浏览器是"新标签页"，但我们跑在 Tauri WebView 里，宿主不注册该快捷键，可安全占用。

**图片粘贴**：`@tiptap/extension-file-handler` 统一 paste/drop。流程是先插 `blob:` URL 占位节点让用户立刻看到图，Rust 侧 `spawn_blocking` 里算 BLAKE3（**同步算大文件会阻塞 Tauri command 线程池**）→ 命中本地 `attachments` 则秒传 → 否则进 outbox → 拿到 id 后 `editor.commands.updateAttributes` 换成 `bianfa://att/<id>` 自定义协议。**绝不把 base64 data URI 写进文档**——2 MB 截图变 2.7 MB base64 进 Y.Doc，且 Yjs 的删除只留墓碑，状态永久膨胀。

**Markdown 输入法 + IME**：Tiptap input rules 自带 `# ` → h1、`- ` → 列表、` ``` ` → 代码块、`[] ` → taskItem。中文用户必踩的坑：IME composition 期间 ProseMirror 跳过 input rule，拼音上屏后 `# ` 不触发。解法是监听 `compositionend` 后手动重跑一次匹配，作为一个自写扩展固化下来，并配一条 Playwright + CDP `Input.imeSetComposition` 的回归测试。

**撤销栈**：协同下 undo 必须是 local undo（只撤销自己的操作），否则 A 按 Ctrl+Z 会删掉 B 刚打的字。`Y.UndoManager` 天生是 local undo，`Collaboration` 扩展内部即用 `yUndoPlugin`。三个坑：(1) `StarterKit` 的 `undoRedo` 必须 `false`（选项名在 v3 是 `undoRedo`，v2 叫 `history`），否则两套 history 打架，PM 的 history 会尝试反转已被远端改动的位置并抛 `RangeError`；(2) 远端更新必须用不在 `trackedOrigins` 里的 origin 提交；(3) AI 生成整段要显式 `ydoc.transact()` 包裹，让一次 Ctrl+Z 撤销整段而不是 200 次。

**手写墨迹：v1 不做，但这是一个需求冲突，不是纯技术决策。** 需求 1 写的是"完美复刻便笺当前所有的功能"，而 Windows 10 时代的便笺是支持墨迹书写的。**上线前必须先确认目标 Windows 版本上便笺是否仍有墨迹功能**——如果有，砍掉它就是明确违背需求 1，需要用户拍板，而不是由技术团队单方面推迟。

技术路径本身是清楚的：WebView2 是 Chromium 内核，完整支持 Pointer Events（`pointerType === 'pen'`、`pressure`、`tiltX/tiltY`、`getCoalescedEvents()`），配 `touch-action: none` + `setPointerCapture`，用 `perfect-freehand@1.2.3`（MIT）把点序列转成变宽 SVG path，存自定义 `inkNode`（`attrs: { paths, w, h }`）而非位图，缩放不糊且能进 Y.Doc。**成本 = 基础版 10-15 人日；生产级（掌压误触抑制、橡皮擦、笔锋曲线、高 DPI 多显示器、墨迹与文本混排选区、墨迹增量 CRDT 编码）合计 4-6 周。** macOS 侧要独立评估：WKWebView 下 Magic Trackpad 是否暴露压感需实测，不要凭假设写进方案。**v1 折中**：支持粘贴/拖入手写 PNG，走 attachments 通路，零额外成本。

### 3.4 LLM 读写协议（本章最容易做错的部分）

**LLM 边界用 Markdown，不用 PM JSON。** 实测（脚本可复现，见 `scratchpad/ratio.mjs`）：一篇典型中文便笺（标题+段落+加粗+链接+3 项 checklist+代码块），Markdown 281 字符，压缩后的 PM JSON **1350 字符 = 4.8x**，pretty-print 是 11.2x。带 UniqueID attrs 和 link mark 的完整属性后比例只会更高——初稿写的 3.5x 偏低。

**【勘误】`editor.commands.setMarkdown()` 不存在。** 解包 `@tiptap/markdown@3.31.2` 的 `dist/index.d.ts` 核实，实际 API 是：

```ts
// 客户端读：Editor 接口被扩展了一个方法
const md: string = editor.getMarkdown()
// 客户端写：走 setContent / insertContent 的 contentType 选项
editor.commands.setContent(md, { contentType: 'markdown' })
editor.commands.insertContentAt(range, md, { contentType: 'markdown' })

// 服务端（无 DOM、无 Editor 实例）：直接用 MarkdownManager
import { MarkdownManager } from '@tiptap/markdown'
const mm = new MarkdownManager({ extensions: sharedExtensions })
const json = mm.parse(markdownFromLLM)   // → JSONContent
const out  = mm.serialize(pmJson)        // → string
```

`MarkdownManager` 可独立实例化这一点很关键——它让服务端的投影与 LLM 转换共用同一套扩展定义，无需 headless 编辑器。

**【勘误】`updateYFragment` 的第 4 个参数不是 mapping。** 从 3.0.9 的实现核实，签名是 `updateYFragment(y: Y.Doc, yDomFragment: Y.XmlFragment, pNode: Node, meta: { mapping: Map, isOMark: Map })`。传一个裸 `Map` 会在运行时炸。同时 `yDocToProsemirrorJSON` 在 3.0.9 里已标 `@deprecated`，应改用 `yXmlFragmentToProseMirrorRootNode` / `initProseMirrorDoc`。

**【补强：初稿漏掉的竞态】** 初稿的流程"服务端读 Y.Doc → 转 MD → 喂模型 → 回写 `updateYFragment`"在并发下会吞掉用户编辑：模型推理要 3-10 秒，期间用户在改同一段。`updateYFragment` 做的是**结构化 diff**，它只会产生真正变化的 op（这点初稿说对了，也是不用全量替换的唯一正确姿势），但 diff 的基准是"服务端读到的旧文档"，用户在被改写块内的新输入会被当成差异删掉。

正确协议（v1 就要这么做）：

1. **改写一律在客户端落地，服务端只返回文本。** 服务端接收 `{ blockIds: string[], markdown: string, prompt }`，返回 `{ blockIds, newMarkdown }`，**不碰 Y.Doc**。服务端唯一被允许写 Y.Doc 的场景是用户不在线的后台任务（如定时摘要），且只能 append 新块，永不改写既有块。
2. **块级乐观锁靠 UniqueID。** 请求时带上每个 `blockId` 及其内容的 BLAKE3；应用前重新校验，任一块 hash 变了就中止并提示"内容已变更，请重试"。
3. **应用时限定范围**：用 blockId 在当前文档里定位 `from/to`，`editor.chain().focus().insertContentAt({from, to}, newMarkdown, { contentType: 'markdown' }).run()`，包在单个 `ydoc.transact(fn, LOCAL_AI_ORIGIN)` 里——`LOCAL_AI_ORIGIN` 必须在 `trackedOrigins` 内，这样一次 Ctrl+Z 整段回滚。
4. 服务端确实需要构造文档时（导入、迁移脚本），用 `prosemirrorJSONToYDoc(schema, json)` + `generateUniqueIds(doc, extensions)`（`@tiptap/extension-unique-id` 导出的无 Editor 版本）。

### 3.5 本地存储

**选 `rusqlite 0.40.2`（2026-08-08）+ SQLCipher，自写 Tauri command 暴露领域接口，不用 `tauri-plugin-sql`。** 三个理由：(1) 该插件底层是 sqlx，只支持 `sqlite/mysql/postgres` 三个 driver，README 全文未提 SQLCipher 或加密；(2) 它把 `db.execute(sql, params)` 直接暴露给 WebView，任何一个 XSS（恶意链接预览、AI 返回的富文本）就等于拿到整库读写权限；(3) 我们需要 `load_extension` 加载 `simple` 分词器。前端只能调 `notes_list` / `notes_search` / `note_apply_update` 这类领域命令，拿不到任意 SQL。

```toml
# 【勘误】初稿写的 loadable_extension 是错的 —— 那个 feature 的用途是
# "Used to generate a cdylib"，即用 Rust 写一个 SQLite 扩展。
# 加载外部扩展的 feature 叫 load_extension。
rusqlite = { version = "0.40", features = [
  "bundled-sqlcipher-vendored-openssl",  # 隐含 bundled-sqlcipher → bundled
  "blob", "load_extension", "backup", "functions", "limits",
] }
keyring = "3"
blake3  = "1"
```

**加密：SQLCipher 页级加密（AES-256-CBC + 每页 HMAC-SHA512，PBKDF2 迭代 256000，核实自 sqlcipher 4.18.0 `src/sqlcipher.c` 的 `PBKDF2_ITER`），不用应用层字段加密。** 后者会直接杀死 FTS5（密文不能分词）和所有 WHERE 下推，等于把数据库降级成 KV。密钥管理：首次启动生成 32 字节随机 DEK，用 `keyring` crate 存进 Windows Credential Manager / macOS Keychain，`PRAGMA key = "x'<64 hex>'"` 传原始密钥——**这个 raw-key 写法会跳过 256000 轮 PBKDF2**，冷启动省掉一次几百毫秒的密钥派生，且安全性更好（熵来自 CSPRNG 而非口令）。

**明确不做端到端加密**：服务端要跑 LLM 摘要、全文检索、链接预览抓取、团队共享，都需要明文。E2EE 作为未来"本地保险箱"单笔记特性，不影响主链路。

**不用 IndexedDB / `y-indexeddb`**：(1) WebView2 的 IndexedDB 在磁盘上是明文 LevelDB，本机任何进程可读；(2) 无 SQL，跨笔记待办聚合要全量拉进内存；(3) 会形成两套持久化和两个加密边界。`y-indexeddb` 最新是 9.0.12，**最后一次发布是 2023-11-02**（npm registry 核实），已实质停更。自写 persistence provider 移植其算法到 SQLite 约 150 行。

```ts
// 【勘误】Y.Doc 的 'update' 事件产出的是 V1 编码，'updateV2' 才是 V2。
// 核实自 yjs 13.6.32 dist/yjs.mjs:3352/3359 两处 emit。
// 用 on('update') 收到的 V1 payload 去喂 Y.mergeUpdatesV2 会失败。
// 全链路统一走 V2（更省，且 V2 才有 diffUpdateV2 等增量 API）。
ydoc.on('updateV2', (update: Uint8Array, origin) => {
  invoke('note_append_update', { noteId, update })   // 追加进 ydoc_updates
})
```

压缩阈值：累计 200 条或 512 KB 时 `Y.mergeUpdatesV2` 合入 `ydoc_snapshots` 并删旧行。

**版本历史：不用 `Y.snapshot()`，存完整的 `encodeStateAsUpdateV2` 副本。** 这是初稿内部自相矛盾的一处：`Y.snapshot` 要能还原，`Y.Doc` 必须构造为 `{ gc: false }`（yjs 源码里 `createDocFromSnapshot` 的官方示例第一行就是 `new Y.Doc({ gc: false })`），而关掉 GC 正是初稿自己列为高风险的"墓碑膨胀"的成因。

实测这个取舍是压倒性的（同一段 105 字节中文，反复重写后半段）：

| 重写次数 | gc=true 的 V2 体积 | gc=false 的 V2 体积 |
|---|---|---|
| 0 | 130 B (1.2x) | 130 B (1.2x) |
| 10 | 150 B (1.4x) | 570 B (5.4x) |
| 50 | 150 B (1.4x) | 2250 B (21.4x) |
| 200 | 151 B (**1.4x**) | 8551 B (**81.4x**) |

结论：**`gc: true` 下墓碑膨胀几乎不存在**（200 次重写后仅 1.4x），初稿把它列为头号风险是基于 `gc:false` 的假设。所以：Doc 一律 `gc: true`；版本历史用 `note_versions(crdt_state_v2 bytea, content_text text)` 存独立的完整副本，按"同一作者 10 分钟合并成一版 + 每笔记最多保留 50 版 + 手动打标的版本永久保留"裁剪。仍然要监控 `notes.crdt_bytes`，但阈值可以定得很松（单条 > 1 MB 才告警）。

**离线队列（outbox）**：

```sql
CREATE TABLE outbox (
  id INTEGER PRIMARY KEY AUTOINCREMENT,     -- 单调序，FIFO
  idempotency_key TEXT NOT NULL UNIQUE,     -- uuidv7，服务端据此去重
  entity_type TEXT NOT NULL,                -- 'note' | 'attachment'
  entity_id TEXT NOT NULL,
  op TEXT NOT NULL,                         -- 'ydoc_update' | 'blob_upload'（元数据已并入 CRDT，见 3.2.3）
  payload BLOB NOT NULL,
  attempts INTEGER NOT NULL DEFAULT 0,
  next_attempt_at INTEGER NOT NULL DEFAULT 0,
  last_error TEXT,
  status TEXT NOT NULL DEFAULT 'pending'    -- pending | inflight | done | dead
) STRICT;
CREATE INDEX outbox_ready_idx ON outbox (status, next_attempt_at, id);
```

三条设计要点：

1. **op 折叠**——同一 note 的连续 `ydoc_update` 入队时用 `Y.mergeUpdatesV2` 合并成一条 pending 记录，避免离线一小时攒出 5000 条。前面测到的 8.8x 压缩就是这条的收益。
2. **租约认领**防多窗口重复发送：`UPDATE outbox SET status='inflight', attempts=attempts+1 WHERE id IN (SELECT id FROM outbox WHERE status='pending' AND next_attempt_at<=?1 ORDER BY id LIMIT 20) RETURNING *`（SQLite 3.35+ 支持 `UPDATE...RETURNING`；`bundled-sqlcipher` 带的版本远高于此）。
3. **退避**：`next_attempt_at = now + min(2^attempts, 300)s ± 20% jitter`；`attempts > 12` 转 `dead` 并在 UI 上报"N 项未同步"，**绝不静默丢弃**。

### 3.6 Schema 版本与前向兼容（初稿完全漏掉）

这是绿地项目最容易埋、最难拆的雷。ProseMirror 的 schema 是严格的：老版本客户端拿到含未知节点类型（比如 v1.3 才加的 `inkNode`、`table`）的文档时，`Node.fromJSON` 会抛错或静默丢弃该节点——**丢弃后一旦老客户端保存，新内容就在 CRDT 里被真正删掉了**，且因为是合法的 CRDT 删除操作，新客户端也恢复不了。

三条硬规则：

1. `notes.schema_version` 记录该文档用到的最高 schema 版本。客户端启动时上报自己支持的 `max_schema_version`。
2. **服务端对 `schema_version > 客户端支持版本` 的笔记，只下发只读的 `content_text`，不下发 CRDT。** 客户端渲染成"此便笺需要更新到 vX 才能编辑"的只读卡片。宁可暂时不能编辑，也不能静默丢内容。
3. 每次给 schema 加节点/属性，必须同时：bump `schema_version`、写一条迁移记录、给桌面端强制升级窗口（Tauri updater，第 4 章）。

Tiptap schema 的唯一定义放在一个共享 TS 包 `@bianfa/schema`，同时被 WebView（编辑器）、Node 端 projector（投影 + LLM 转换）引用。**Rust 侧永远不解析 PM JSON**——不允许出现第二套 schema 实现，这是把"两端投影结果不一致"这类幽灵 bug 从根上掐掉。`content_text` / `content_bigram` / `checklist_items` 三个投影因此各只有一份实现代码。

### 1.1 先搞清楚：2026 年的 "Windows 便笺" 有两个

不区分这两者，后面所有复刻和迁移决策都会做错。

| | **经典版 Sticky Notes（UWP）** | **新版 Sticky Notes（随 OneNote）** |
|---|---|---|
| 包标识 | `Microsoft.MicrosoftStickyNotes_8wekyb3d8bbwe`，3.x | 内嵌 OneNote 应用，Win32 |
| 技术栈 | UWP / XAML | Win32 |
| 本地数据 | `plum.sqlite`（**已完整核实结构**）+ MSA 云同步 | OneNote 缓存，**无独立可读的私有 DB** |
| 状态 | 仍可运行，微软已停止加新功能 | 微软主推方向 |

**对我们唯一重要的结论**：**经典版有一个我们能读的 SQLite 库，新版没有。** 所以"迁移"这件事天然只对经典版成立——这不是偏好，是唯一可行路径。交互复刻基线也取经典版（无边框窗口 / 7 色 / 快捷键 / 关闭≠删除是十年肌肉记忆），再吸收新版的截图捕获、单条置顶、图片 OCR 搜索三个点子。

> **未核实（egress 受限，交付前请自行确认）**：新版发布/强推的具体时间点、`Win+Alt+S` 是否仍是官方快捷键、OneNote for Windows 10 的退役日期、Cortana 各端退役的具体月份。这些是叙事佐料，**不影响任何技术决策**，写进对外文档前请查一次微软官方支持页。

### 1.2 功能全量清单

**A. 笔记 CRUD 与列表**：新建、编辑（无保存按钮，输入即持久化）、删除（垃圾桶 + 二次确认）。**"关闭"≠"删除"**——点 `×` 只是 `IsOpen=0`，笔记仍在列表里，这是最容易被复刻者做错、也是用户最依赖的一条语义。列表窗口是独立宿主窗口，搜索为纯文本子串匹配（无正则/标签/布尔）。无文件夹、无嵌套、无标签、无排序选项。

**B. 富文本与快捷键**：仅 5 种行内格式。**没有**标题级别、代码块、引用、超链接锚文本、表格、有序列表、缩进层级。

| 快捷键 | 行为 |
|---|---|
| `Ctrl+B` / `Ctrl+I` / `Ctrl+U` | 粗体 / 斜体 / 下划线 |
| `Ctrl+T` | 删除线 |
| `Ctrl+Shift+L` | 项目符号列表切换 |
| `Ctrl+N` | 新建笔记 |
| `Ctrl+F` / `Ctrl+H` | 搜索 / 回到笔记列表 |
| `Ctrl+Z` / `Ctrl+Y` | 撤销 / 重做 |

> 上表来自公开资料与社区整理。`Ctrl+T`=删除线、`Ctrl+Shift+L`=项目符号这两条在不同版本上有出入，**必须在真机上逐个按一遍再定稿**——快捷键错一个就是"你们复刻得不对"的差评。

**C. 颜色主题**：7 色 —— Yellow / Green / Blue / Purple / Pink / Gray / Charcoal。深色模式下便笺变深灰，原色只保留顶部细色带。

**D. 图片与墨迹**：图片存 `LocalState\media\`，`Media` 表记录；Surface Pen 墨迹存 `Stroke` / `StrokeMetadata`。

**E. Insights / Cortana 智能识别 —— 已死**：`plum.sqlite` 里至今仍有 `Insight` 表和 `Note.PendingInsightsScan` 列（已核实），但 Cortana 后端已退役，入口全部失效。**这是遗迹，不是功能。**

**F. 云同步**：MSA 账号同步到微软云，可在 OneNote 移动端、Outlook.com Notes 看到。**无公开 REST/Graph API**。

**G. 窗口行为**：无边框自绘、可拖拽缩放、每条笔记一个独立顶层窗口、共用一个任务栏图标、位置按显示器持久化（`WindowPosition` 列存 `ManagedPosition=DeviceId:...;Position=x,y;Size=w,h`）、`Win+D` 一起最小化。**关键更正：`Note` 表存在 `IsAlwaysOnTop` 列（已核实）**——所以"置顶"在经典版的数据模型里是存在的，迁移时必须一并搬过来，不能像初稿那样断言"旧版没有置顶"。

**H. 缺失能力（我们的机会）**：无导出、无版本历史、无打印、无锁定、无组织结构。

### 1.4 三处对初稿的反驳与最终裁决

#### 反驳一：「版本历史必须 P0」——**部分推翻**

反方：用户从 Windows 便笺迁移过来的动机是**"别再弄丢我的便笺"**，不是"我要回滚到上周三下午的版本"。便笺平均长度不到 200 字，逐次 diff 时间线是给代码和长文档设计的功能，对贴纸形态是过度设计。而且它带来三笔成本：写放大、UI（时间线面板本身就是一个完整的交互）、以及与第 5 章同步方案的冲突（版本快照要不要同步？不同步则换机丢历史，同步则流量×N）。

**裁决：推翻 P0，降为 P1。** 但"数据不丢"这个诉求必须在 P0 满足——用**三条便宜得多的措施**顶上：① 永不硬删，删除进回收站 30 天；② 每日启动时 `VACUUM INTO backups/YYYY-MM-DD.db`，保留 14 份（一行 SQL，约 1 人天）；③ SQLite 开 `journal_mode=WAL` + `synchronous=NORMAL`。这三条合计 1 人天，覆盖了"弄丢便笺"的 95% 场景。逐次时间线留到 v1.1，届时按"每条笔记最多 50 个快照 + 超过 7 天的按天合并"实现。

#### 反驳二：「贴桌面层（图标之上、普通窗口之下）」——**推翻，砍掉**

反方（且已核实）：**Electron 没有这个能力，两个平台都没有。**
- macOS：Electron 的 `type: 'desktop'` 在 `native_window_mac.mm` 里映射到 `[window setLevel:kCGDesktopWindowLevel - 1]`——那是**壁纸层，在桌面图标下面**，不是图标之上。`setAlwaysOnTop` 可选的 level 只有 `normal / floating / torn-off-menu / modal-panel / main-menu / status / pop-up-menu / screen-saver`，**没有 desktop-icon 档**。要做到"图标之上、窗口之下"需要 `kCGDesktopIconWindowLevel + 1`，Electron 未暴露，只能写原生模块。
- Windows：`type` 选项在 Windows 上**只支持 `toolbar`**，没有 `desktop`。WorkerW/`SHELLDLL_DefView` 注入是壁纸层技术（同样在图标**下面**），初稿把它说成"图标之上"是错的；而且它是非公开行为，Windows 大版本更新会失效。

**裁决：砍掉「贴桌面层」，改为两个真实需求的组合**：① 三档置顶（普通 / 置顶 `floating` / 全局置顶开关）；② `Win+D` 豁免开关（Windows 上通过监听 `WM_` + 主动 `showInactive()` 恢复实现，成本 1 人天，且不依赖未文档化 API）。用户真正要的是"便笺别被窗口盖住"和"按显示桌面时别一起消失"，这两条都能干净地满足。**把「贴桌面」写进落地页是可以的，但实现是置顶+豁免，不是伪造窗口层级。**

#### 反驳三：「文件夹 + 标签 + 颜色三维组织」——**部分推翻**

反方：这是 Notion/Obsidian 的思路，不是贴纸的思路。三套组织维度对 1-3 人团队意味着三套 CRUD、三套筛选 UI、三套同步冲突处理，而绝大多数便笺用户的笔记总数在 20-80 条之间——这个量级下文件夹是负资产。

**裁决：砍掉文件夹，只保留标签 + 颜色两维，且降到 P1。** 理由：标签是扁平的（一张 `note_tags` 关联表，同步冲突就是集合并集，无需树形合并算法），文件夹是树形的（移动/重命名/循环引用/同步时的路径冲突，工作量是标签的 4 倍）。P0 阶段用「颜色 + 修改时间倒序 + 全文搜索」三件套完全够用。

### 1.5 数据迁移方案（本章最硬的部分）

#### 1.5.1 定位与安全读取

```
%LocalAppData%\Packages\Microsoft.MicrosoftStickyNotes_8wekyb3d8bbwe\LocalState\
  ├─ plum.sqlite      ← 主库
  ├─ plum.sqlite-wal  ← 必须一起复制，最近编辑都在这里
  ├─ plum.sqlite-shm
  └─ media\           ← 图片附件（注意是小写 media）
```

**权限**：交互用户对自己的包目录通常有读权限。真正的坑是 **Sticky Notes 运行时持有 WAL 锁**。正确姿势已被生产代码验证（BasedHardware/omi 的 `stickyNotes.ts` 就是这么做的）：三个文件一起复制到临时目录 → `readonly` 打开副本 → 绝不写回原库。

```ts
// better-sqlite3@13.0.3（要求 Node >= 22）
import Database from 'better-sqlite3';
import { copyFileSync, existsSync } from 'node:fs';

const SRC = `${process.env.LOCALAPPDATA}\\Packages\\Microsoft.MicrosoftStickyNotes_8wekyb3d8bbwe\\LocalState\\plum.sqlite`;
for (const ext of ['', '-wal', '-shm']) {
  if (existsSync(SRC + ext)) copyFileSync(SRC + ext, TMP + ext);   // 顺序：主库最后? 否 —— 先主库再 wal/shm
}
const db = new Database(TMP, { readonly: true, fileMustExist: true });

// 列集在 3.x 各小版本间漂移，必须按列名匹配，禁止按序号取值
const cols = new Set(db.prepare('PRAGMA table_info(Note)').all().map(c => c.name));
const pick = (...cands) => cands.find(c => cols.has(c)) ?? null;
```

> **列漂移是实测事实，不是假设**：HTB 取证样本上的 `Note` 表是 18 列（无 `PendingInsightsScan`），而 mobiusft 取证工具查询的是 19 列（含 `PendingInsightsScan`）。同一张表在不同机器上列数不同——`PRAGMA table_info` 是唯一安全做法。

#### 1.5.2 `Note` 表完整 DDL（已核实，可直接作为迁移器的契约）

```sql
CREATE TABLE IF NOT EXISTS "Note" (
  "Text"                 varchar,
  "WindowPosition"       varchar,   -- 注意：列名是 WindowPosition，ManagedPosition 是"值的前缀"
  "IsOpen"               integer,
  "IsAlwaysOnTop"        integer,   -- 经典版确实有置顶，务必迁移
  "CreationNoteIdAnchor" varchar,
  "Theme"                varchar,
  "IsFutureNote"         integer,
  "RemoteId"             varchar,
  "ChangeKey"            varchar,
  "LastServerVersion"    varchar,   -- 云端规范化 JSON，富文本真源
  "RemoteSchemaVersion"  integer,
  "IsRemoteDataInvalid"  integer,
  "Type"                 varchar,
  "Id"                   varchar primary key not null,
  "ParentId"             varchar,
  "CreatedAt"            bigint,    -- .NET ticks
  "DeletedAt"            bigint,
  "UpdatedAt"            bigint
);
-- 部分版本额外含 "PendingInsightsScan" integer
```

`Media` 表已核实含：`Id`、`ParentId`、`MimeType`、`LocalFileRelativePath`、`CreatedAt`、`UpdatedAt`。
库内还存在 `Insight`、`User`、`Stroke` 表（SQLECmd 的识别查询以这 5 张表判定 `plum.sqlite`）。初稿提到的 `SyncState` / `UpgradedNote` / `StrokeMetadata` **未在任一权威来源核实到，按"可能不存在"处理**。

#### 1.5.3 字段映射

| plum.sqlite | 格式 | 我们的字段 | 转换 |
|---|---|---|---|
| `Note.Id` | GUID | `external_id` | 幂等键 |
| `Note.LastServerVersion` | JSON | `content_json`（**优先**） | `$.document.blocks[].content[].text` |
| `Note.Text` | 私有行内格式 | `content_json`（降级） | 见 §1.5.4 |
| `Note.Theme` | Yellow/Green/Blue/Purple/Pink/Gray/Charcoal | `color` | 未知值 → Yellow |
| `Note.IsOpen` | 0/1 | `is_open` | 1 → 迁移后自动打开 |
| `Note.IsAlwaysOnTop` | 0/1 | `pinned` | 直接映射 |
| `Note.WindowPosition` | `ManagedPosition=DeviceId:...;Position=x,y;Size=w,h` | `display_id,x,y,w,h` | `/Position=(-?\d+),(-?\d+);Size=(\d+),(\d+)/`（**坐标可为负**，多显示器左侧屏就是负值——初稿的 `\d+` 会漏掉） |
| `Note.CreatedAt/UpdatedAt/DeletedAt` | .NET ticks（100ns，起点 0001-01-01） | ms | `ms = ticks/10000 - 62135596800000` |
| `Media.LocalFileRelativePath` | 相对 `LocalState` | 文件路径 | 拼前缀后拷贝 |
| `Stroke` | 私有墨迹 | — | 打 `has_ink` 标记，提示用户 |

#### 1.5.4 `Text` 是什么格式（别踩坑）

**不是 RTF，不是 HTML，不是标准 Markdown**，是微软私有行内格式：段落以 `\id=<GUID> ` 前缀开头，行内格式在不同版本分别用过 RTF 风格控制字（`\b`、`\i0`、`\ul`、`\strike`、`\par`）和 Markdown 风格标记（`**…**`）。策略：

1. **`LastServerVersion` 非空 → 用它**（唯一有结构的表示，直接映射 block 模型）；
2. **从未同步的笔记 → 解析 `Text`**：先剥 `\id=\S+\s?`，再按两套规则容错分词，无法识别的控制字**丢弃而非原样显示**；
3. **兜底存纯文本，绝不丢内容**，并打 `import_degraded` 标记。

#### 1.5.5 `.snt` 导入（Win7 / Win8 / Win10 < 1607）

路径 `%AppData%\Microsoft\Sticky Notes\StickyNotes.snt`，格式为 OLE2 复合文档（CFBF）。**已核实的结构**：每条便笺一个 storage，其中 **stream `0` 是 RTF**，**stream `3` 是 UTF-16 编码的纯文本**。

三点初稿漏了的工程细节：
- stream `3` 是 **UTF-16**，必须 `.toString('utf16le')`，按 UTF-8 解会全是乱码；
- **OLE storage 自带 ctime/mtime**，这是恢复 `.snt` 便笺创建/修改时间的唯一途径，别丢；
- 识别 storage 靠"**它下面有没有名为 `3` 的 stream**"，不要靠 storage 名的字符模式（取证代码里用的 `name.count("-")==3` 与标准 GUID 的 4 个连字符对不上，不可靠）。

Node 侧用 `cfb@1.2.2`（SheetJS）。**风险已核实：该包最后发布于 2022-04-06，近 3 年 0 更新。** 但 CFBF 是 1990 年代冻结的二进制格式，不会变，且我们只读不写、输入是用户本机文件——判定为**可接受的技术债**，用它，并在解析入口套 try/catch + 单条 storage 失败不中断整批。

#### 1.5.6 导入 UX 与幂等

- 首次启动扫描 `plum.sqlite` / `StickyNotes.snt` / 用户手选路径，扫到后弹「发现 N 条 Windows 便笺，是否导入？」，**预览 + 逐条勾选**，不静默全量导入。
- 幂等键 `UNIQUE(source, external_id)`；重复导入按 `UpdatedAt` 比较，只更新更新的。
- **默认只在桌面打开 `IsOpen=1` 的便笺**，其余进列表——原版关掉的 30 条不该一次性糊满屏幕。
- 导入前把 `plum.sqlite` 三件套原封不动归档到 `imports/`——这本身就是用户从未拥有过的备份。

### 1.6 中文搜索：一个初稿糊弄过去的硬问题

初稿写"FTS5（porter unicode61 + 中文 bigram）"——这句话不可执行：`porter` 和 `unicode61` 是两个互斥的 tokenizer，不能并列；而"中文 bigram"在 SQLite 里**不存在内置实现**，得写 C 扩展。

**已核实的真实情况**：FTS5 内置 `trigram` tokenizer，支持 `case_sensitive` / `remove_diacritics` 参数，能正确处理非拉丁文字（官方测试用例里有泰文）。但它**要求至少 3 个字符**才能产生 token——`fts5_tokenize.c` 里第一个三元组的填充循环在输入不足 3 字符时直接 `return SQLITE_OK`，不产出任何 token。

于是中文有个致命盲区：**"会议"、"报销"、"密码"这类 2 字查询会返回 0 结果**，而这恰恰是中文最高频的查询长度。

**最终方案（不写 C 扩展，1-3 人团队可落地）**：

```sql
CREATE VIRTUAL TABLE note_fts USING fts5(
  plain_text,
  tokenize = 'trigram',
  detail = 'full',
  content = 'notes', content_rowid = 'id'
);
```

查询层做长度分流：

```ts
function search(q: string) {
  const s = q.trim();
  if (s.length >= 3) {
    return db.prepare(`SELECT rowid FROM note_fts WHERE note_fts MATCH ? ORDER BY rank`).all(`"${s}"`);
  }
  // 1-2 字符：走 LIKE 旁路。trigram 索引本身就能加速 LIKE '%x%'，
  // 且便笺总量在 10^2~10^3 量级，全表扫描也在 10ms 内。
  return db.prepare(`SELECT id FROM notes WHERE plain_text LIKE ? ESCAPE '\\'`).all(`%${esc(s)}%`);
}
```

为什么不选竞品常用的 `wangfenjin/simple` 分词扩展：它要编译原生 `.so/.dll/.dylib` 并跨三个平台分发签名，对 1-3 人团队是纯负担；而 trigram + LIKE 旁路零依赖、零编译、覆盖 100% 查询长度。代价是不支持词干化和相关性排序质量略低——便笺场景不需要。

**必须同步维护**：`notes.plain_text` 是从富文本 doc 抽出的纯文本镜像列，写笔记时同步更新，FTS5 用 external-content 模式挂上去（省一份正文存储）。

### 1.7 三个初稿完全没提、但一定会踩的坑

1. **中文输入法与防抖冲突**。TipTap/ProseMirror 在 IME composition 期间的 DOM 是中间态。如果 300ms 防抖在用户还在拼音候选框里选字时触发，会把半成品写进库和撤销栈。**必须监听 `compositionstart` / `compositionend`，composition 期间挂起持久化和 undo 检查点。** 这是所有中文富文本编辑器的第一号 bug，务必在 P0 就做对。

2. **单实例 + 托盘是 P0 不是可选项**。每条便笺一个窗口的模型下，重复启动会产生两套窗口指向同一个库 → SQLite 多进程写冲突 + 用户看到重影。`app.requestSingleInstanceLock()` 是第一行代码。同时所有便笺共用一个任务栏图标意味着：只有列表窗口设 `skipTaskbar: false`，所有便笺窗口设 `skipTaskbar: true`。

3. **空便笺的生命周期**。原版行为：新建后不输入任何内容就关闭，笔记直接消失（不进回收站）。不复刻这条，用户会攒出一堆空白便笺。规则写死：`plain_text.trim() === '' && attachments.length === 0` 时关闭 → 直接物理删除。

### 1.8 竞品速览与差异化定位

| 产品 | 形态 | 强项 | 致命短板 |
|---|---|---|---|
| **Windows 便笺（经典版）** | 免费，内置 | 零安装、贴桌面肌肉记忆 | 无导出、无历史、无组织、搜索弱 |
| **Simple Sticky Notes** | 免费，Win only | 清单、闹钟、分组、主题引擎 | 不支持图片、仅 Windows、无云同步 |
| **Notezilla** | 付费，Win + 移动端 | 提醒、清单、云同步、便笺发同事 | 无 macOS 桌面端、无 AI、无团队空间 |
| **Stickies (Zhorn)** | 免费，Win only | 极轻、可吸附窗口、定时休眠 | UI 陈旧、无云、无移动端、无图片 |
| **Google Keep** | 免费 | 同步好、移动端强、OCR、协作 | **不是桌面应用**，无法贴桌面/置顶 |
| **Obsidian** | 免费 + Sync 订阅 | 本地 Markdown、插件生态、双链 | 是 PKM 不是贴纸；心智负担重 |

> **未核实**：Notezilla 售价、Obsidian Sync 各档价格与容量、Obsidian 商用授权政策、Simple Sticky Notes 是否已加图片支持。初稿写的 "$29.95 一次性"、"Sync $4/用户/月（1GB、1 个月历史）"、"2025-02-20 起商用免费" 这三个数字本次**无法从官网核实（域名被网络策略拦截）**，写进对外文档前必须逐条查官网，否则是法律风险。

**差异化定位**：Windows 便笺的形，本地优先的骨，加上可切换的 LLM。

四个交叉点（前三个是结构性的，不靠数字支撑）：
1. **桌面贴纸形态 + 真跨平台（Win/Mac）** —— Notezilla 无 Mac 桌面端，Keep 非桌面应用，Obsidian 非贴纸。
2. **团队共享便笺空间** —— Notezilla 只有点对点"发送"。
3. **内置多模型可切换 LLM**（第 4 章）—— 竞品全为零。
4. **数据安全偏执**：本地 SQLite 为真源、永不硬删、每日快照、一键全量导出。这是打原版最痛点的四条，也是落地页敢写"从 Windows 便笺迁移"的底气。

迁移话术一句话：**"你现有的便笺，我们一条不丢地搬过来，而且从此再也丢不了。"**
